# Артефакт: карточка машинного контракта ответа

Карточка нужна, когда ответ модели читает программа. Она помогает передать другому
человеку не только промпт и JSON Schema, но и границы гарантии: какие статусы
останавливают процесс, что проверяется машинно, где требуется смысловое review и кто
имеет право принять решение `continue`.

Не заполняй карточку для обычного текста, который читает и оценивает человек. Если
структурированный интерфейс не нужен следующему потребителю, зафиксируй это решение и
не добавляй схему ради формальности.

## 3. Политика отсутствующих и неоднозначных значений

| Поле или ситуация | Допустимо `null`? | Утверждённый default | Нужен review или stop | Почему |
|---|---:|---|---|---|
| … | да / нет | нет / значение и правило | review / stop / нет | … |

Не подставляй удобное значение только для прохождения схемы. Различай:

- факт известен;
- факт отсутствует и может быть `null`;
- без факта продолжать нельзя;
- бизнес заранее утвердил настоящее правило по умолчанию.

## 4. Нормализация ответа провайдера

Зафиксируй, как реальные поля SDK превращаются во внутренний конверт приложения.

| Исход провайдера | Поля конкретного SDK | Нормализованный статус | Действие |
|---|---|---|---|
| Нормальное завершение | … | `completed` | перейти к structure gate |
| Отказ модели | … | `refusal` | stop, сохранить причину |
| Лимит / обрыв | … | `incomplete` | stop или контролируемый retry |
| API error / неизвестный исход | … | `error` | stop, не парсить как ответ модели |

Пример внутреннего конверта:

```python
{"status": "completed", "output_text": "..."}
{"status": "refusal", "reason": "..."}
{"status": "incomplete", "reason": "..."}
```

## 5. Последовательность gates

Порядок является частью контракта. Не проводи позднюю проверку, если ранняя уже
остановила процесс.

| Gate | Проверяемый инвариант | Чем проверяется | Решение при сбое | Что ещё не доказано после успеха |
|---|---|---|---|---|
| Status | вызов нормально завершён | поля SDK / адаптер | stop / retry по правилу | корректность содержимого |
| Structure | объект соответствует контракту | structured output + typed parser / validator | stop | истинность значений |
| Source | evidence существует в источнике | детерминированная проверка / человек | stop / review | правильность интерпретации |
| Meaning | значения следуют из evidence и бизнес-правил | человек / предметное правило / проверенный evaluator | stop / continue | только теперь можно использовать результат |

## 6. Набор проверочных случаев

До первого запуска заполни ожидаемый первый непройденный gate.

| Случай | Вход или мутация | Ожидаемый gate | Ожидаемое решение | Почему |
|---|---|---|---|---|
| Обычный корректный | … | meaning → accepted после review | continue | … |
| Refusal | … | status | stop | … |
| Incomplete | … | status | stop | … |
| Schema-invalid | … | structure | stop | … |
| Evidence отсутствует | … | source | stop | … |
| Schema-valid-but-wrong | … | meaning | stop | … |
| Неоднозначный случай | … | meaning | review / человеку | … |

Сильный набор обязательно содержит schema-invalid и schema-valid-but-wrong пример:
они проверяют разные ошибочные модели.

## 8. 4D и ответственность

| 4D | Решение |
|---|---|
| Delegation | Что именно делегировано модели и что осталось человеку или коду? |
| Description | Где описаны задача, вход, схема, неизвестные значения и failure policy? |
| Discernment | Как различаются JSON, схема, evidence и правильный смысл? |
| Diligence | Допустима ли среда, где хранится трейс и кто отвечает за `continue`? |

## 9. Критерии приёмки карточки

Карточка готова, если другой человек без устных пояснений может:

- объяснить, почему выбран structured output, а не проза или function calling;
- собрать один запрос из трёх раздельных частей;
- проверить поддержку использованных keywords JSON Schema;
- обработать refusal и incomplete до парсинга содержимого;
- воспроизвести по одному структурному и смысловому сбою;
- понять, почему машинный успех заканчивается review, если истина ещё не доказана;
- определить владельца окончательного решения и запрещённый до него следующий шаг.
