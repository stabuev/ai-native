**Requires (только для переноса в реальный API):** платный API-ключ одного провайдера.
Обязательный Build It работает офлайн, без ключей и сети.

В 2.3 мы разделили подготовку статуса на два шага. Сначала модель извлекала из заметок
таблицу фактов, gate проверял её, и лишь затем принятая таблица переходила в редакторский
шаг. Пока процесс выполняет человек в чате, Markdown-таблицы достаточно. Но программа не
должна угадывать, как сегодня модель назвала столбец, чем обозначила неизвестный срок и
добавила ли пояснение перед таблицей.

Теперь промежуточный артефакт становится **машинным интерфейсом**. Мы зададим его
структуру отдельно от инструкции, проверим ответ послойно и остановим даже идеально
оформленный объект, если его смысл не подтверждён заметками.

> **Главная мысль.** Схема ограничивает форму ответа. Источник и правила проверяют его
> смысл. Одно не заменяет другое.

## Почему команды «верни JSON» недостаточно

Допустим, следующий шаг ждёт такой объект:

```json
{
  "facts": [
    {
      "category": "decision",
      "statement": "Пилот запускается 18 сентября для 10% пользователей iOS.",
      "evidence": "Пилот решили запустить 18 сентября для 10% пользователей iOS.",
      "owner": null,
      "deadline": "18 сентября"
    }
  ]
}
```

Если просто дописать к промпту «верни JSON», возможны разные сбои:

- модель обернёт объект в тройные обратные кавычки или добавит вступление;
- вместо массива `facts` вернёт один объект;
- назовёт поле `type`, а не `category`;
- пропустит `owner` либо запишет строку `"не указан"` вместо согласованного `null`;
- сохранит правильную форму, но напишет, что пилот запускается для **всех** пользователей, хотя в источнике указано 10%.

Первые четыре ошибки относятся к форме. Последняя — к смыслу. Они требуют разных
механизмов, поэтому сначала разделим контракт запроса на части.

## Три части одного запроса

### 1. Постоянная инструкция

**Системная инструкция** — правила поведения модели, заданные разработчиком отдельно от
меняющихся пользовательских данных. Часто говорят *system prompt*, но это не одно
универсальное имя поля: у API разные названия.

Для нашего шага постоянная инструкция выглядит так:

```text
Извлекай из заметок только явно сказанные решения, действия, условия,
открытые вопросы и метрики. Не превращай обсуждение в решение.
Для каждого утверждения сохраняй точный подтверждающий фрагмент источника.
Неизвестные owner и deadline возвращай как null: не придумывай значения.
Форма ответа задаётся отдельно переданной JSON Schema.
```

Она описывает **работу и границы смысла**. В неё не нужно копировать всю схему и
заклинание «СТРОГО JSON БЕЗ ЕДИНОЙ ЛИШНЕЙ БУКВЫ»: специальный режим API надёжнее
текстовой просьбы ограничивает форму. Инструкция направляет модель, но не является ни
математической гарантией истины, ни защитной границей от недоверенных данных.

### 2. Динамический вход

Это конкретные заметки встречи, письмо, тикет или другой источник, меняющийся от вызова
к вызову. Он передаётся как пользовательский ввод, а не склеивается с постоянными
правилами без явной границы.

Разделение даёт практическую пользу:

- постоянные правила можно версионировать и сравнивать;
- один и тот же контракт применяется к разным входам;
- исходный текст не маскируется под инструкцию разработчика;
- в трейсе видно, что изменилось: правила, источник или схема.

### 3. Схема ответа

**JSON Schema** — стандартный JSON-документ, описывающий допустимую структуру другого
JSON-документа. Здесь важны шесть конструкций:

- `type` задаёт вид значения: объект, массив, строка или `null`;
- `properties` перечисляет поля объекта и схемы их значений;
- `required` перечисляет поля, которые должны присутствовать;
- `enum` ограничивает значение явным списком допустимых вариантов;
- `anyOf` разрешает соответствие одной из нескольких схем — например, строке или `null`;
- `additionalProperties: false` запрещает незаявленные поля.

Упрощённый фрагмент нашей схемы:

```json
{
  "type": "object",
  "properties": {
    "facts": {
      "type": "array",
      "items": {
        "type": "object",
        "properties": {
          "category": {
            "type": "string",
            "enum": [
              "decision",
              "action",
              "condition",
              "open_question",
              "metric"
            ]
          },
          "statement": {"type": "string"},
          "evidence": {"type": "string"},
          "owner": {
            "anyOf": [{"type": "string"}, {"type": "null"}]
          },
          "deadline": {
            "anyOf": [{"type": "string"}, {"type": "null"}]
          }
        },
        "required": [
          "category",
          "statement",
          "evidence",
          "owner",
          "deadline"
        ],
        "additionalProperties": false
      }
    }
  },
  "required": ["facts"],
  "additionalProperties": false
}
```

Это настоящая JSON Schema, а не учебный словарь вида
`{"priority": {"type": "integer", "required": true}}`. Провайдеры поддерживают не весь
стандарт, а его документированное подмножество, поэтому перед реальным запуском схему
проверяют на выбранном API. В Build It схема уже дана: задача урока — не написать
универсальный интерпретатор стандарта, а построить безопасную границу потребления ответа.

## Четыре режима, которые легко перепутать

**Structured output** — режим API, в котором генерация ограничивается переданной схемой.
Для успешно завершённого ответа поддерживаемая часть схемы обеспечивает нужные поля,
типы и допустимые значения. Это сильнее текстовой просьбы и JSON mode.

**Function calling**, или вызов функции, — другой режим: модель не просто возвращает
данные, а формирует структурированную просьбу приложению вызвать функцию с заданными
аргументами. Приложение может проверить, исполнить или отклонить эту просьбу.

| Механизм | Что он даёт | Чего не даёт |
|---|---|---|
| Просьба «верни JSON» | Направляет обычную генерацию | Не гарантирует даже синтаксически корректный JSON |
| JSON mode | Синтаксически корректный JSON | Не гарантирует конкретные поля, типы и enum |
| Structured output | Соответствие поддерживаемой JSON Schema для нормального завершённого ответа | Не доказывает истинность значений и не отменяет refusal/incomplete |
| Function calling | Структурированную просьбу модели к приложению выполнить функцию | Само приложение всё равно решает, выполнять ли действие; это не просто формат финального ответа |

Function calling понадобится позже, когда модель будет выбирать действие и передавать
аргументы инструменту. Сейчас модель ничего не исполняет: нам нужен структурированный
промежуточный результат. Поэтому основной механизм урока — response structured output,
а не tool use.

OpenAI прямо разделяет function calling и `text.format`; Google — function calling и
форматирование финального ответа; Anthropic — JSON outputs и strict tool use. Значит,
общее слово «схема» ещё не делает эти операции взаимозаменяемыми:
[OpenAI](https://developers.openai.com/api/docs/guides/structured-outputs),
[Google](https://ai.google.dev/gemini-api/docs/structured-output),
[Anthropic](https://platform.claude.com/docs/en/build-with-claude/structured-outputs).

## Почему одной схемы всё равно мало

Полезно рассматривать границу как четыре последовательных gate:

```text
постоянная инструкция + вход + JSON Schema
                     │
                     ▼
                 ответ API
                     │
          1. status: завершён?
                     │
          2. structure: форма верна?
                     │
          3. source: evidence есть в источнике?
                     │
          4. meaning: утверждение действительно следует из evidence?
                     │
                     ▼
             следующий шаг / БД / UI
```

| Gate | Контрольный вопрос | Что останавливает | Что ещё не доказано |
|---|---|---|---|
| Status | Ответ нормально завершён? | отказ, лимит токенов, неизвестный статус | что содержимое корректно |
| Structure | JSON соответствует контракту объекта? | неверный корень, поле, тип, enum, лишние поля | что значения правдивы |
| Source | Доказательство присутствует в исходнике? | выдуманную цитату или потерю источника | что утверждение правильно интерпретирует цитату |
| Meaning | Утверждение подтверждается доказательством и правилами задачи? | подмену масштаба, статуса решения, владельца, срока | только после этого результат можно передать дальше |

### Gate 1: сначала статус, потом парсинг

Structured output действует не во всех исходах вызова. Модель может отказаться
отвечать, а генерация может прерваться из-за лимита или фильтра. Такой результат нельзя
пытаться «дочинить» вызовом `json.loads`.

Например:

```python
{"status": "refusal", "reason": "safety policy"}
{"status": "incomplete", "reason": "max_output_tokens"}
```

Оба ответа должны остановиться на status gate. OpenAI возвращает статус
`incomplete` и отдельные refusal-блоки, Anthropic — `stop_reason` вроде `refusal` или
`max_tokens`; конкретные поля нормализует адаптер приложения. В офлайн-упражнении мы
используем простой общий конверт, чтобы не смешивать причинную модель с каталогом SDK.

### Gate 2: форма — это не самописный стандарт

В реальном приложении используй structured output провайдера и штатный
**типизированный парсер SDK** — функцию, которая превращает ответ в объект языка по
заданному типу и сообщает о несовпадении, — либо зрелую библиотеку проверки JSON
Schema. Не нужно писать собственный универсальный валидатор стандарта.

Однако приложение всё равно отвечает за свою границу:

- проверить статус до доступа к содержимому;
- убедиться, что SDK действительно вернул ожидаемый тип;
- применить ограничения предметной области, которые отсутствуют в схеме или не поддерживаются провайдером;
- корректно обработать сохранённый старый ответ, тестовую фикстуру или данные из другого адаптера.

Поэтому Build It содержит **точную предметную проверку объекта meeting facts**. Она
сознательно не называется реализацией JSON Schema.

### Gate 3: присутствие доказательства

Для каждого факта мы сохраняем поле `evidence` с дословным фрагментом заметок. Простая
детерминированная проверка может убедиться, что этот фрагмент действительно встречается
в исходном тексте.

```text
evidence = "для 10% пользователей iOS"
```

Если такого фрагмента нет, следующий шаг останавливается. Это полезная проверка, но не
доказательство правильной интерпретации.

### Gate 4: правильная форма может скрывать ложь

Рассмотрим объект:

```json
{
  "facts": [
    {
      "category": "decision",
      "statement": "Пилот запускается для всех пользователей iOS.",
      "evidence": "для 10% пользователей iOS",
      "owner": null,
      "deadline": "18 сентября"
    }
  ]
}
```

Он является валидным JSON. Все поля и типы правильные. `category` входит в разрешённый
enum. `evidence` дословно присутствует в заметках. И всё же утверждение ложно: 10%
подменены всеми пользователями.

Именно поэтому успешные машинные проверки возвращают решение `review`, а не
`continue`. Смысл проверяет человек, предметное правило или отдельный надёжно
протестированный механизм. Google прямо рекомендует обрабатывать schema-compliant, но
семантически неверные ответы; OpenAI и Anthropic отдельно документируют refusal и
незавершённые ответы.

## Разбор на сценарии из 2.3

Возьмём те же заметки:

```text
Пилот решили запустить 18 сентября для 10% пользователей iOS.
До запуска служба безопасности должна согласовать схему доступа.
Рита отправит схему доступа на согласование до 12 сентября.
Если согласование не получено к 16 сентября, запуск переносится.
Обсудили перевод всех пользователей на новый поток в сентябре,
но решения по этому вопросу не приняли.
Метрики пилота: доля успешных оплат и число обращений в поддержку.
Ответственный за итоговый отчёт пока не назначен.
```

До запуска предскажем судьбу пяти ответов:

| Ответ | Ожидаемый первый непройденный gate |
|---|---|
| `status=refusal` без JSON | status |
| `status=incomplete`, JSON обрезан | status, до парсинга |
| JSON обёрнут в тройные обратные кавычки | structure/syntax: это не голый JSON structured output |
| Поле `category="plan"` | structure: значение вне enum |
| Все поля верны, но 10% заменены всеми пользователями | meaning |

Последняя строка принципиальна. Если все ошибки объявить «ошибками JSON», студент
научится доверять форме больше, чем источнику.

### Неизвестное значение — не значение по умолчанию

В заметках не назначен ответственный за отчёт. Нельзя молча подставить условного
владельца, `priority=3` или `urgent=false`: валидная схема лишь сделает выдумку аккуратно
оформленной.

Контракт должен явно различать:

- значение известно → передать его;
- значение допустимо не знать → передать `null`;
- без значения продолжать опасно → остановить процесс или поставить `needs_review`;
- бизнес действительно утвердил default → применить его и назвать правило, а не приписывать значение источнику.

В нашей схеме `owner` и `deadline` всегда присутствуют, но могут быть `null`. Так
потребителю не приходится различать «модель забыла поле» и «в источнике нет значения».

## BUILD IT: собери boundary gate

**Задание:** реализуй офлайн-модуль, который принимает нормализованный ответ провайдера,
проводит машинные gates и не разрешает продолжение без зафиксированного смыслового
решения.

> **Перед запуском.** Создай в личном workspace папку `course-work/2.4/`. Из блока
> [«Исходники урока»](#lesson-files) скопируй туда `starter_structured_output.py` под
> именем `structured_output.py`, а рядом — `test_structured_output.py`. Эталонный
> `structured_output.py` пока не открывай. Нужны Python 3 и `pytest`; сеть и API-ключ
> не требуются.

Готовыми даны:

- `SOURCE_NOTES` — заметки из сценария 2.3;
- `SYSTEM_INSTRUCTION` — постоянные правила извлечения;
- `OUTPUT_SCHEMA` — настоящая JSON Schema для передачи провайдеру;
- `ALLOWED_CATEGORIES` и `FACT_FIELDS` — предметные ограничения.

Реализуй четыре функции.

### 1. `validate_structure(data) -> list[str]`

Проверь точный контракт объекта:

- корень — объект только с полем `facts`;
- `facts` — непустой массив;
- каждый элемент — объект ровно с `category`, `statement`, `evidence`, `owner`, `deadline`;
- `category` входит в разрешённый набор;
- `statement` и `evidence` — непустые строки;
- `owner` и `deadline` — непустая строка либо `None`.

Верни все найденные ошибки. Пустой список означает только правильную форму.

### 2. `validate_evidence(data, source) -> list[str]`

Для каждого факта проверь, что `evidence` дословно входит в `source`. Верни путь ошибки
вида `facts[0].evidence: not found in source`.

Не пытайся этой функцией доказать, что `statement` правильно истолковывает цитату. Это
отдельный meaning gate.

### 3. `inspect_response(response, source) -> dict`

Поддержи три нормализованных вида ответа:

```python
{"status": "completed", "output_text": "..."}
{"status": "refusal", "reason": "..."}
{"status": "incomplete", "reason": "..."}
```

Порядок проверок является частью контракта:

1. не-completed ответ → `decision="stop"`, `stage="status"`;
2. completed без корректного голого JSON → `stop/syntax`;
3. ошибка предметной структуры → `stop/structure`;
4. evidence отсутствует в источнике → `stop/source`;
5. все машинные проверки пройдены → `review/meaning`, но не `continue`.

Возвращай единый отчёт:

```python
{
    "decision": "stop | review | continue",
    "stage": "status | syntax | structure | source | meaning | accepted",
    "errors": [],
    "data": None
}
```

### 4. `finish_semantic_review(report, approved, reason) -> dict`

Функцию можно вызвать только для отчёта с `decision="review"`. Непустой `reason`
обязателен и при принятии, и при отклонении:

- `approved=True` → `continue/accepted`;
- `approved=False` → `stop/meaning`;
- попытка пропустить проваленный машинный gate → `ValueError`.

Так в трейсе остаётся не только решение, но и его обоснование.

### Прогон red → green

```bash
python -m pytest course-work/2.4 -q          # сначала красное
python course-work/2.4/structured_output.py  # затем демонстрация двух решений gate
```

**Готово, когда** зелёны 11 тестов. Они проверяют настоящую закрытую JSON Schema,
refusal и incomplete до парсинга, fenced JSON, пропуски и лишние поля, `null`,
доказательство вне источника, обязательный meaning review, отклонение семантически
ложного объекта и запрет обходить проваленный gate.

После зелёного прогона объясни своими словами три утверждения:

1. почему fenced JSON в этом упражнении считается ошибкой, хотя его можно было бы очистить строковым кодом;
2. почему `validate_structure(...) == []` не разрешает продолжение;
3. почему `finish_semantic_review` нельзя применять к incomplete-ответу.

Если ответы непонятны, одних зелёных тестов недостаточно. Эталонное решение и
тесты-ТЗ доступны ниже в [«Исходниках урока»](#lesson-files).

## USE IT: перенеси контракт в один доступный API

Не нужно вызывать всех провайдеров. Выбери один доступный API и сохрани точный model ID,
SDK и дату прогона. Названия полей меняются, но разделение ответственности остаётся.

| Часть контракта | OpenAI Responses | Anthropic Messages | Google Gemini |
|---|---|---|---|
| Постоянная инструкция | `instructions` либо `developer`/`system` message | верхнеуровневый `system` | `system_instruction` |
| Динамический вход | `input` / user message | `messages` с ролью `user` | `input` либо `contents` |
| Схема ответа | `text.format` с `type=json_schema` | `output_config.format` | `response_format` либо schema в generation config |
| Перед парсингом | `status`, incomplete details, refusal content | `stop_reason`, тип content block | finish/status/error поля выбранного API |

Минимальная форма запроса выглядит так; конкретный model ID выбери в актуальном
каталоге своего провайдера:

```python
# OpenAI Responses
response = OpenAI().responses.create(
    model=MODEL_ID,
    instructions=SYSTEM_INSTRUCTION,
    input=SOURCE_NOTES,
    text={"format": {
        "type": "json_schema",
        "name": "meeting_facts",
        "strict": True,
        "schema": OUTPUT_SCHEMA,
    }},
)
```

```python
# Anthropic Messages
response = Anthropic().messages.create(
    model=MODEL_ID,
    max_tokens=2048,
    system=SYSTEM_INSTRUCTION,
    messages=[{"role": "user", "content": SOURCE_NOTES}],
    output_config={"format": {
        "type": "json_schema",
        "schema": OUTPUT_SCHEMA,
    }},
)
```

```python
# Google Interactions API
response = genai.Client().interactions.create(
    model=MODEL_ID,
    system_instruction=SYSTEM_INSTRUCTION,
    input=SOURCE_NOTES,
    response_format={
        "type": "text",
        "mime_type": "application/json",
        "schema": OUTPUT_SCHEMA,
    },
)
```

Эти фрагменты показывают **размещение трёх частей контракта**, а не универсальный
адаптер ответа. Для своего провайдера:

1. сначала обработай отказ, incomplete и API error по его документации;
2. только затем получи структурированное содержимое;
3. нормализуй его в учебный конверт либо передай typed object в предметные проверки;
4. проверь evidence и смысл;
5. сохрани status, model ID, решение gate и причину.

Если API использует Pydantic, Zod или другой typed parser, применяй его вместо
самописной повторной реализации JSON Schema. Собственный код должен добавлять
предметные и смысловые ограничения, а не конкурировать со стандартом.

## Где здесь 4D

| 4D | Решение в машинном контракте |
|---|---|
| **Delegation** | Передать модели извлечение явных фактов, но не право придумывать отсутствующие значения или автоматически публиковать результат |
| **Description** | Разделить постоянную инструкцию, вход и схему; описать `null`, категории, доказательства и статусы без противоречий |
| **Discernment** | Не спутать валидный JSON, соответствие схеме, наличие цитаты и правильность утверждения; проверить самый дорогой смысловой сбой |
| **Diligence** | Не отправлять чувствительные данные в неподходящую среду, сохранить model ID и трейс, обработать refusal/incomplete и отвечать за решение `continue` |

4D здесь не декоративная вставка. Каждая компетенция соответствует отдельному решению:
что делегировать, как описать контракт, по чему принять результат и кто отвечает за его
дальнейшее использование.

## Типичные ошибки

- **Дублировать схему криком в системной инструкции.** Инструкция объясняет задачу и смысловые границы; форма передаётся в schema-параметре.
- **Путать structured output с function calling.** Формат ответа и просьба выполнить действие решают разные задачи.
- **Парсить до проверки статуса.** Refusal или обрезанный ответ не становится обычным результатом только потому, что код вызвал `json.loads`.
- **Называть несколько `isinstance` реализацией JSON Schema.** Предметный валидатор полезен, но не реализует стандарт.
- **Считать schema-valid ответ истинным.** Схема не знает, было в источнике 10% или все пользователи.
- **Придумывать defaults для отсутствующих фактов.** Используй `null`, review или остановку, если бизнес явно не утвердил правило по умолчанию.
- **Сразу писать в БД/API.** Сначала пройди все применимые gates и сохрани основание решения.
- **Тестировать только счастливый путь.** Refusal, incomplete и schema-valid-but-wrong — обязательные случаи этой границы.

## Дополнительное чтение

Читать весь список не нужно: сначала пройди вводный материал по JSON Schema, затем
выбери документацию того API, с которым работаешь. Последние два источника —
необязательная практика и техническое углубление.

- [JSON Schema — Creating your first schema](https://json-schema.org/learn/getting-started-step-by-step) — базовое продолжение урока: прочитай **Introduction to JSON Schema**, **Define properties** и **Validate JSON data against the schema**; обрати внимание на различие между схемой и экземпляром и на то, что `properties` само по себе не делает поля обязательными.
- [OpenAI — Structured model outputs](https://developers.openai.com/api/docs/guides/structured-outputs) — если используешь OpenAI, сопоставь со своей карточкой разделы **When to use Structured Outputs via function calling vs via text.format**, **Structured Outputs vs JSON mode** и **Refusals**; отдельно проверь обработку незавершённого ответа.
- [Anthropic — Structured outputs](https://platform.claude.com/docs/en/build-with-claude/structured-outputs) — если используешь Claude, прочитай **JSON outputs**, **JSON Schema limitations** и **Invalid outputs**; используй актуальный параметр `output_config.format`, а `output_format` считай переходной формой SDK.
- [Google Gemini — Structured outputs](https://ai.google.dev/gemini-api/docs/structured-output) — если используешь Gemini, открой **JSON schema support**, **Structured outputs versus function calling** и **Best practices**; перенеси в свой контракт оговорку о поддерживаемом подмножестве схемы и отдельной проверке значений.
- [Pydantic — JSON Schema](https://docs.pydantic.dev/latest/concepts/json_schema/) — практическое углубление для Python: в разделе **Generating JSON Schema** посмотри, как получить одну схему из типизированной модели и не дублировать контракт вручную; помни, что успешная валидация модели ещё не доказывает истинность данных.
- [Willard, Louf, 2023 — Efficient Guided Generation for Large Language Models](https://arxiv.org/abs/2307.09702) — факультативно о механике constrained decoding: достаточно аннотации и описания метода с регулярными выражениями и контекстно-свободными грамматиками, чтобы понять, почему генератор может гарантировать форму, но не смысл ответа.
