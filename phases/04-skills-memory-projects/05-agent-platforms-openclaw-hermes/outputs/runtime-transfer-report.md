# Артефакт: отчёт о переносе проекта в агентный рантайм

Это заполненный пример для учебного проекта «Помощник по возвратам». Он не подтверждает установку OpenClaw или Hermes: сначала мы проверяем перенос офлайн, а затем при желании повторяем ту же приёмку в выбранной платформе.

## 1. Решение

| Поле | Значение |
|---|---|
| Проект | `returns-assistant` |
| Проверяемый skill | `returns-answer-review` |
| Целевой runtime | `offline-preflight`, учебная версия |
| Результат preflight | `ready` |
| Что разрешено этим решением | Перейти к поведенческой проверке на офлайн-адаптере |
| Что не разрешено | Считать OpenClaw, Hermes или production-развёртывание проверенными |

## 2. Сопоставление артефактов фазы

| Что создано раньше | Что видит runtime | Доказательство |
|---|---|---|
| Skill из 4.1 | Имя `returns-answer-review`; адаптер вывел требование `knowledge.read` из шагов skill | Имя присутствует в `mapping`, а решение адаптера — в `permissions` |
| Управляемая память из 4.2 | Snapshot владельца `support-project`; запись `id=0`, `key=response.format` | Manifest ссылается на неё через `source_ref`, а preflight проверяет запись snapshot |
| Blueprint из 4.3 | Проект `returns-assistant`, решения о доступе и сценарии `P-01`–`P-05` | Проект и сценарии записаны в отчёте |
| Политика контекста из 4.4 | Kept/dropped, бюджет, причины исключения, `source_ref` и P-06 | Manifest сохранён целиком |
| Adapter-контракт 4.5 | Required context IDs, формальные allowlists и одобренные внешние соединения | Для каждого нового поля указан источник решения |

Сопоставление не доказывает качество ответа модели. Оно доказывает, что runtime получил именно те части системы, которые мы намеревались передать.

## 3. Manifest демонстрационного preflight

```text
status: ready

mapping:
  skill: returns-answer-review
  project: returns-assistant
  runtime: offline-preflight
  context_ids:
    - instructions
    - request
    - policy-v2
    - format-preference
  memory_refs:
    - context_id: format-preference
      owner: support-project
      key: response.format
      record_id: 0

context:
  used_units: 22
  input_budget_units: 24
  reserve_units: 6
  dropped:
    - history-summary: budget
    - policy-v1: not_relevant

permissions:
  required_tools:
    - knowledge.read
  allowed_tools:
    - knowledge.read
  available_tools:
    - knowledge.read
  missing_tools: []

data_egress: []
blockers: []
```

Контекстный ID `format-preference` не подменяет ID исходной памяти. Preflight разрешил
`source_ref` в запись `id=0` snapshot, проверил `key`, владельца, active и срок жизни.

## 4. Граница данных

В демонстрационном runtime указана локальная модель, поэтому `data_egress` пуст. Это свойство конкретной конфигурации, а не следствие слова self-hosted.

При переносе в реальную платформу здесь нужно перечислить каждый внешний путь отдельно:

| Соединение | Что может быть отправлено | Внешнее? | Кто одобрил | Решение |
|---|---|---:|---|---|
| Провайдер модели | Запрос и выбранный контекст |  |  |  |
| Мессенджер | Входящее сообщение и ответ |  |  |  |
| Внешний инструмент | Аргументы вызова и его результат |  |  |  |
| Телеметрия / журналирование | Метаданные либо содержимое запуска |  |  |  |

Если внешний путь не описан и не одобрен, preflight должен вернуть `blocked`.

## 5. Разрешения и секреты

- Значения секретов в отчёте не сохраняются: проверяются только имена необходимых переменных или профилей.
- Возможность должна одновременно требоваться skill, быть разрешена проектом и существовать в runtime.
- `available` не означает `allowed`: установленный инструмент нельзя использовать вне границ проекта.
- Успешный preflight не заменяет sandbox, подтверждение опасных действий и полноценную модель угроз из следующих фаз.

## 6. Приёмочные сценарии

После preflight нужно повторить сценарии проекта 4.3 и длинную историю из 4.4.

| ID | Что проверяет | Ожидаемое поведение | Фактическое доказательство | Результат |
|---|---|---|---|---|
| P-01 | Действующий факт | Использовать `policy-returns-v2` |  |  |
| P-02 | Пробел в knowledge | Не додумывать ответ |  |  |
| P-03 | Конфликт версий | Не выбрать архивную `v1` |  |  |
| P-04 | Подмена инструкций | Сохранить правила проекта |  |  |
| P-05 | Выход за scope | Отказать или предложить безопасный маршрут |  |  |
| P-06 | Длинная история | Сохранить обязательное и объяснить исключения |  |  |

`ready` в preflight означает только «конфигурация непротиворечива и запуск можно проверять». Итоговый перенос принят, только если поведенческие сценарии тоже пройдены.

## 7. Повтор в выбранной платформе

| Поле | OpenClaw / Hermes / другой runtime |
|---|---|
| Название и точная версия |  |
| Дата проверки |  |
| Официальный источник установки |  |
| Куда помещён skill |  |
| Как представлены project instructions и knowledge |  |
| Как ограничена и очищается memory |  |
| Где виден фактический context manifest либо чем заменена эта проверка |  |
| Какие tools доступны и кто их разрешил |  |
| Какие внешние соединения обнаружены |  |
| Какие сценарии пройдены |  |
| Какие расхождения с офлайн-preflight найдены |  |

Если платформа не показывает фактически собранный контекст, это не повод объявлять перенос успешным. Зафиксируй ограничение и используй доступные логи, тестовый источник-маркер или другой наблюдаемый способ проверить, что нужный слой действительно применяется.

## 8. Откат

Перед внешним запуском запиши:

1. как отключить skill;
2. как отозвать токен или API-ключ;
3. как закрыть внешний канал;
4. как удалить или экспортировать память;
5. как остановить runtime;
6. где лежат логи и какие данные они содержат.

Перенос завершён, когда другой человек может воспроизвести preflight, увидеть границы данных, повторить сценарии и безопасно отменить подключение.
