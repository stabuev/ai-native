# Урок 4.5 · От проекта к агентному рантайму

**Фаза 4 — Скиллы, память и проекты** · **Результат фазы:** для одного собственного процесса связать проверенный skill, memory snapshot, project blueprint, context manifest и воспроизводимый preflight переноса.
<!-- exercise -->

**Результат урока:** ты сопоставишь skill, память, blueprint проекта и политику контекста с возможностями выбранного рантайма; до запуска увидишь недостающие разрешения и внешние пути данных; затем подтвердишь перенос приёмочными сценариями.

**Requires:** Python 3 и `pytest` для офлайн-практики, а для поведенческой проверки — тот же доступный агент или workspace, который использовался в 4.1 и 4.3. Собственные артефакты 4.1–4.4 не обязательны для первого прохождения Build It: в коде есть готовый учебный набор. Для завершения всей фазы понадобится повторить mapping со своими артефактами, но устанавливать новый runtime не требуется. Для необязательного маршрута с OpenClaw или Hermes понадобятся сеть, поддерживаемая ими среда и выбранный способ доступа к модели.

**Это интеграционный финал фазы.** В 4.1 ты описал повторяемый процесс как skill, в 4.2 отделил управляемую память от истории чата, в 4.3 зафиксировал проект и приёмочные сценарии, а в 4.4 получил manifest фактически выбранного контекста. Теперь нужно доказать, что конкретная среда выполнения не потеряла эти решения при переносе.

Заполненные примеры уроков не обязаны изображать одну предметную систему:
`retrieval-decision-review` из 4.1 и проект возвратов ниже показывают разные применения
тех же контрактов. Сквозная нить фазы — **твой собственный процесс**. `DEMO_*` помогают
понять adapter-контракт, а итоговое досье связывает реальные артефакты студента.

> **Главная мысль.** Успешный импорт файлов ещё не означает успешный перенос поведения. Сначала сделай конфигурацию наблюдаемой, затем разрешай запуск и проверяй сценарии.

## PROBLEM

Представь, что ты переносишь проект «Помощник по возвратам» в постоянно работающего ассистента. Папка skill скопировалась, документы загрузились, модель отвечает — интерфейс выглядит готовым.

Но внутри могли произойти незаметные изменения:

- runtime нашёл `SKILL.md`, но не имеет нужного инструмента чтения knowledge;
- память принадлежит другому пользователю, устарела или была подключена целиком;
- обязательные project instructions не поместились в контекст;
- облачная модель получила запрос и выбранные документы, хотя команда считала установку «полностью локальной»;
- тестовый вопрос прошёл, а конфликт версий и выход за scope никто не проверил.

Это не пять отдельных проблем. Все они возникают на одной границе: **наши проверенные артефакты нужно сопоставить с реальными возможностями и настройками runtime**.

## CONCEPT

### Что такое runtime

**Agent runtime**, или среда выполнения агента, — это работающая программа, которая принимает задачу, собирает доступный контекст, обращается к модели и при необходимости даёт ей инструменты. OpenClaw и Hermes — примеры готовых runtime, но в уроке нас интересует не устройство конкретного продукта, а проверяемая граница переноса.

Полноценный агентный цикл, tool use, MCP и model routing появятся в фазах 6, 7 и 9. Здесь мы не строим их уменьшенные копии.

### Четыре новых слова

- **Adapter, или адаптер переноса** — явное сопоставление наших артефактов с сущностями конкретного runtime: где находится skill, откуда берутся инструкции, какая память подключена и какие возможности доступны.
- **Preflight** — проверка перед запуском. Она ничего не исполняет, а отвечает: конфигурация готова или запуск нужно заблокировать.
- **Run manifest** — отчёт одного preflight: что выбрано, что исключено, какой бюджет использован, какие разрешения нужны и какие блокеры найдены.
- **Data egress, или внешний путь данных** — передача данных с нашей машины внешнему получателю: провайдеру модели, мессенджеру, API инструмента или системе журналирования.

Preflight похож на предполётную проверку: чек-лист не управляет самолётом, но не даёт начать полёт с незакрытой дверью или отсутствующим топливом.

### Что именно соединяет финал фазы

```text
4.1 validated skill ──────────────┐
4.2 governed memory snapshot ─────┤
4.3 project scope + permissions ──┼─> runtime preflight ─> ready / blocked
4.4 context manifest ─────────────┤          │
runtime capabilities + endpoints ─┘          └─> transfer report
                                                     │
                                                     └─> acceptance scenarios
```

Каждый слой отвечает на отдельный вопрос:

| Слой | Вопрос перед запуском | Доказательство |
|---|---|---|
| Skill, 4.1 | Какой процесс нужен? | Имя, назначение и поведенческая проверка skill |
| Memory, 4.2 | Какая управляемая запись породила кандидат? | Snapshot с владельцем, `key`, числовым `record_id`, active и сроком жизни |
| Project, 4.3 | Где границы процесса и что разрешено? | Scope, решения о возможностях и сценарии |
| Context, 4.4 | Что реально выбрано для этого вызова? | Kept/dropped, причины, бюджет, резерв и `source_ref` |
| Runtime, 4.5 | Может ли выбранная среда выполнить этот контракт без скрытого расхождения? | Возможности, имена секретов, соединения и итоговый статус |

### Какие поля переносим, а какие создаёт адаптер

Preflight не получает готовую машинную конфигурацию из воздуха. Часть полей переносится
из предыдущих артефактов, а часть впервые формализуется на границе runtime:

| Поле preflight | Откуда берётся |
|---|---|
| `skill.name`, назначение | Проверенный skill 4.1 |
| `required_tools`, `required_secrets` | Вывод адаптера 4.5 из шагов, зависимостей и выбранного runtime; передаются только имена |
| `memory_snapshot` | `MemoryStore.snapshot()` из 4.2 без изменения владельца и IDs |
| `project.name`, scope, решения о возможностях, acceptance IDs | Blueprint 4.3 |
| `required_context_ids` | Обязательные кандидаты, формализованные при переносе политики 4.4 |
| `approved_external_connections` | Новое решение владельца при переносе в 4.5 |
| `context_manifest` и `source_ref` | Фактический результат планировщика 4.4 |
| Возможности и endpoints | Наблюдаемая конфигурация выбранного runtime |

### Почему мы не пишем ещё один загрузчик SKILL.md

Формат и поведенческая проверка skill уже разобраны в 4.1. Кроме того, настоящий Agent Skills frontmatter — YAML с обязательными и необязательными полями, ограничениями имён и зависимыми от реализации расширениями. Самодельный разбор строк вида `key: value` создаст ложное ощущение совместимости.

В Build It мы передаём в preflight имя проверенного skill и явно выведенные адаптером
требования runtime. `required_tools` и `required_secrets` не обязаны буквально находиться
во frontmatter 4.1: это часть mapping 4.5, которую нужно обосновать шагами skill. Чтение
пакета и исполнение инструкций остаются ответственностью выбранного runtime.

### Self-hosted не означает «данные не покидают машину»

**Self-hosted** означает, что сам runtime запущен в инфраструктуре, которую контролируешь ты или твоя организация. Из этого не следует, что все остальные компоненты локальны.

Например:

```text
Telegram ──> self-hosted runtime ──> облачный провайдер модели
                    │
                    └──────────────> внешний API инструмента
```

В этом варианте процесс runtime и его локальные файлы находятся у тебя, но сообщения, выбранный контекст и аргументы инструментов могут уходить внешним сервисам. Поэтому preflight проверяет не ярлык «self-hosted», а каждый настроенный endpoint.

## РАЗБОР ПО ШАГАМ

Возьмём уже знакомый проект возвратов.

### Шаг 1. Сопоставляем skill и возможности

Проверенный skill `returns-answer-review` требует логическую возможность `knowledge.read`. Preflight сравнивает три списка:

```text
skill requires:     knowledge.read
project allows:     knowledge.read
runtime provides:   knowledge.read
```

Возможность пригодна только на пересечении `требуется ∩ разрешено ∩ доступно`. Если runtime предоставляет инструмент, но проект его не разрешает, использовать его нельзя. Если проект разрешает, но runtime не предоставляет, выполнить контракт невозможно.

### Шаг 2. Проверяем manifest контекста

Политика 4.4 сохранила:

```text
kept:    instructions, request, policy-v2, format-preference
dropped: history-summary → budget
         policy-v1       → not_relevant
budget:  22 / 24 входных единиц + 6 в резерве
```

Blueprint требует, чтобы `instructions` и `request` никогда не исчезали молча. Preflight не выбирает контекст заново: он проверяет уже принятое решение. Если обязательного ID нет или `used_units > input_budget_units`, статус становится `blocked`.

### Шаг 3. Проверяем выбранную память

Источник `format-preference` помечен как `memory`. Значит, для него должна существовать управляемая запись из 4.2:

```text
context candidate:
  id: format-preference
  source_ref:
    owner: support-project
    key: response.format
    record_id: 0

memory snapshot:
  owner: support-project
  items:
    - id: 0
      key: response.format
      active: true
      expires_at: null
```

Строковый ID кандидата и числовой ID записи решают разные задачи: первый делает
manifest читаемым, второй сохраняет идентичность исходной памяти. Отсутствующая,
неактивная, просроченная, принадлежащая другому владельцу или имеющая другой `key`
запись блокирует запуск. Preflight не сохраняет весь входящий разговор как «память» и
не оживляет архивные версии.

### Шаг 4. Показываем внешние пути

Учебная конфигурация использует условную локальную модель:

```text
connection: local-model
external: false
```

Поэтому `data_egress` пуст. Если заменить её облачной моделью, preflight запишет получателя и поля, которые ему отправляются:

```text
name: cloud-model
kind: model
sends: request, selected_context
```

Внешнее соединение не является автоматической ошибкой. Ошибка — использовать его, не сопоставив с решением проекта. Пока `cloud-model` не внесён в `approved_external_connections`, статус будет `blocked`.

### Шаг 5. Правильно читаем статус

`ready` означает:

- обязательный контекст присутствует и помещается;
- выбранная память разрешается по `owner + key + record_id`, принадлежит нужному владельцу и действует;
- необходимые возможности одновременно требуются, разрешены и доступны;
- внешние соединения перечислены и одобрены;
- можно переходить к поведенческим сценариям.

`ready` **не означает**, что модель даст правильный ответ, prompt injection нейтрализован, sandbox надёжен или система готова к production. Preflight проверяет целостность переноса, а не всё качество будущего агента.

## BUILD IT

**Задание: собери офлайн-preflight переноса** — функцию, которая принимает краткие представления артефактов 4.1–4.4 и конфигурацию runtime, а возвращает `ready` или `blocked` с наблюдаемыми причинами.

> **Перед запуском.** Работай в своей папке `ai-native-work`, созданной в фазе 0. Клонировать курс не нужно: скопируй со страницы урока тесты в `course-work/phase-4/runtime-transfer/code/` и создай файл по сигнатуре ниже. Если личные артефакты 4.1–4.4 ещё неудобно привести к этому формату, сначала используй встроенные `DEMO_*`.

Создай `runtime_preflight.py` и реализуй:

```python
def prepare_run(
    skill,
    project,
    memory_snapshot,
    context_manifest,
    runtime,
    now=None,
):
    ...
```

Входы:

| Вход | Минимальное содержание |
|---|---|
| `skill` | `name` из 4.1; `required_tools` и имена `required_secrets`, выведенные адаптером |
| `project` | `name`, решения blueprint, обязательные context IDs, разрешённые tools, владелец памяти, одобренные при переносе внешние соединения, acceptance IDs |
| `memory_snapshot` | Неизменённый snapshot 4.2: `schema_version`, `owner`, `items` с числовыми ID, key, active и expires_at |
| `context_manifest` | `kept`, `dropped`, `used_units`, `input_budget_units`, `reserve_units` и memory `source_ref` из 4.4 |
| `runtime` | имя, доступные tools, имена доступных секретов и список соединений |

Не передавай значения API-ключей. Preflight проверяет только наличие имени секрета, например `MODEL_API_KEY`.

До реализации предскажи пять результатов:

1. Полная локальная конфигурация из `DEMO_*` должна дать `ready`.
2. Удаление `knowledge.read` из runtime должно дать `missing_tool`.
3. Удаление `instructions` из kept должно дать `required_context_missing`.
4. Добавление неодобренного `cloud-model` должно показать его в `data_egress` и заблокировать запуск.
5. Подмена `key` внутри memory `source_ref` должна дать `memory_key_mismatch`.

**Готово, когда** тесты подтверждают:

- все четыре артефакта фазы видны в mapping и manifest;
- отсутствующая возможность блокирует запуск;
- обязательный контекст нельзя молча потерять или переполнить;
- memory-кандидат трассируется до исходной записи по `owner + key + record_id`;
- неподходящая память не проходит проверку владельца, ключа и срока жизни;
- внешний путь данных наблюдаем и требует решения проекта;
- повреждённый вход не превращается в убедительный, но ложный отчёт.

```bash
pytest code -q
python code/runtime_preflight.py
```

После зелёных тестов прочитай напечатанный JSON глазами и ответь:

- Из какого предыдущего урока пришёл каждый блок?
- Какой факт позволяет назвать статус `ready`?
- Какой важный риск этот отчёт сознательно не проверяет?

Внизу, в [«Исходниках урока»](#lesson-files), находятся тесты-ТЗ, эталон и три способа пройти упражнение.

## USE IT

Обязательный маршрут не требует устанавливать новую платформу. Сначала выполни офлайн-preflight, затем повтори приёмочные сценарии в том доступном агенте или workspace, где уже проверял skill и проект в 4.1 и 4.3. Новый runtime подключай только если он действительно нужен и это безопасно для выбранных данных.

### Маршрут A. Проверить перенос в уже доступном агенте

1. Замени `DEMO_SKILL` кратким контрактом своего skill из 4.1.
2. Перенеси в `DEMO_PROJECT` scope, разрешения и IDs сценариев из blueprint 4.3.
3. Передай snapshot своего `MemoryStore` 4.2 без переименования владельца, ключей и числовых IDs.
4. Подставь реальный manifest 4.4 и проверь, что каждый memory `source_ref` указывает на запись этого snapshot.
5. Опиши уже используемого агента через его возможности и endpoints; если часть конфигурации не видна, зафиксируй это как ограничение наблюдаемости.
6. Исправляй блокеры по одному и сохраняй отчёт до и после исправления.
7. В чистых сессиях повтори P-01–P-06 и приложи существенные результаты к отчёту.

### Маршрут B. Повторить проверку в OpenClaw или Hermes

[OpenClaw](https://github.com/openclaw/openclaw) и [Hermes Agent](https://github.com/NousResearch/hermes-agent) — развивающиеся open-source runtime с поддержкой skills, памяти, моделей и каналов. Их интерфейсы и требования меняются, поэтому не копируй команду установки из статичного урока: открой актуальный официальный quickstart, зафиксируй дату и версию, прочитай действие команды до запуска.

Выбери **одну** платформу и заполни таблицу сопоставления:

| Наш артефакт | Где он представлен в выбранном runtime | Как проверить |
|---|---|---|
| Skill 4.1 | Папка или реестр skills | Положительный, отрицательный и граничный сценарии выбора |
| Project instructions 4.3 | Workspace / system instructions / конфигурация агента | Подмена правил не меняет границы проекта |
| Knowledge 4.3 | Файлы, resources или доступный инструмент | Ответ ссылается на активную версию |
| Memory 4.2 | Хранилище или memory-файлы runtime | Владелец, срок жизни, замена и удаление наблюдаемы |
| Context policy 4.4 | Настройки загрузки, hooks либо адаптер до вызова модели | Видно, что kept/dropped соответствуют manifest |
| Permissions | Tool allowlist, sandbox или подтверждения | Запрещённая возможность недоступна |
| Connections | Model, channel, external APIs, telemetry | Для каждого записано, что именно отправляется |

Совпадение структуры `SKILL.md` помогает переносу, но не гарантирует одинакового поведения. [Спецификация Agent Skills](https://agentskills.io/specification) допускает требования совместимости, а поддержка некоторых полей и инструментов зависит от реализации. После импорта всегда повторяй сценарии.

[Hermes предлагает отдельный маршрут миграции конфигурации из OpenClaw](https://hermes-agent.nousresearch.com/docs/guides/migrate-from-openclaw/), но наличие команды импорта также не заменяет повторную приёмку: перенесённый файл и сохранённый контракт поведения — не одно и то же.

### 4D на границе переноса

- **Delegation:** отдай runtime только исполнение явно ограниченного процесса; не включай все доступные инструменты «на будущее».
- **Description:** передай skill, project instructions, knowledge registry, memory policy и manifest как разные слои, а не как одну длинную инструкцию.
- **Discernment:** сравни обещания интерфейса с фактическим mapping, data egress и результатами сценариев.
- **Diligence:** сохрани версию, отчёт preflight, доказательства прогонов и процедуру отката; ответственность за решение о запуске остаётся у тебя.

## SHIP IT

**Артефакт урока:** проверенный отчёт о переносе → [`outputs/runtime-transfer-report.md`](../outputs/runtime-transfer-report.md)

В отчёте должны быть:

- выбранный runtime и точная версия либо явная пометка `offline-preflight`;
- mapping артефактов 4.1–4.4;
- сохранённый manifest со статусом и блокерами;
- карта разрешений и внешних путей данных;
- результаты сценариев P-01–P-06;
- обнаруженные расхождения между исходным проектом и runtime;
- процедура отключения, отзыва доступа и удаления памяти.

Артефакт принят, когда другой человек может понять, почему запуск разрешён или заблокирован, повторить проверки и безопасно отменить подключение. Скриншот работающего чата без manifest и сценариев не является доказательством переноса.

### Когда завершена вся Фаза 4

Зелёный прогон `DEMO_*` завершает Build It этого урока, но ещё не доказывает, что
собственный постоянный слой собран. Для выхода из фазы скопируй

## ТИПИЧНЫЕ ОШИБКИ

- **Считать установленный skill работающим skill.** Импорт подтверждает наличие файлов, но не правильный выбор, доступ к зависимостям или сохранение поведения; повтори сценарии 4.1.
- **Путать available и allowed.** Runtime может предоставлять инструмент, который проект не разрешает; usable-возможность должна пройти обе границы.
- **Называть любой список сообщений памятью.** В manifest могут попасть только управляемые записи нужного владельца, действующей версии и срока жизни.
- **Подменять ID записи удобным названием кандидата.** `format-preference` помогает читать manifest, но исходную память доказывает `source_ref` с `owner`, `key` и числовым `record_id`.
- **Собирать контекст заново внутри preflight.** Решение уже приняла политика 4.4; здесь нужно проверить и передать manifest, а не скрыть его новым эвристическим выбором.
- **Считать self-hosted синонимом offline.** Локальный runtime может отправлять данные облачной модели, каналу, инструменту и telemetry.
- **Считать `ready` доказательством качества ответа.** Это разрешение перейти к сценариям, а не сертификат корректности или безопасности.
- **Обещать универсальную переносимость.** Стандарт переносит ядро формата, но tools, permissions, memory и расширения runtime требуют нового mapping и тестов.
- **Сразу подключать мессенджер.** Новый внешний вход расширяет круг недоверенных данных и адресатов ответа; сначала проверь локальный сценарий и границы доступа.

## ЧТО СОЗНАТЕЛЬНО ОСТАЛОСЬ ЗА ГРАНИЦЕЙ

- Парсинг полного Agent Skills YAML и продуктовые расширения: формат skill и его валидация уже разобраны в 4.1.
- Function calling, схемы tools и MCP: это фаза 6.
- Цикл reason → act → observe, планирование, human-in-the-loop и agent evals: это фаза 7.
- Автоматический model routing, fallback и FinOps: это фаза 9.
- Полная модель угроз, sandbox и защита от prompt injection: это фаза 11; здесь мы только не разрешаем скрывать границы.
- Обязательная установка VPS, мессенджера или конкретной платформы: outcome урока — проверяемый перенос, а не владение одним продуктом.

## ПЕРЕХОД В ФАЗУ 5

Фаза 4 дала постоянный слой рабочей системы: повторяемый skill, управляемую память, проект с источниками и правила сборки контекста. Урок 4.5 добавил границу переноса: теперь видно, что конкретная среда действительно получила и что она может отправить наружу.

## Дополнительное чтение

Материалы ниже факультативны. Читать всё не нужно: для минимального продолжения открой спецификацию и документацию только выбранного runtime. Ветку безопасности используй перед подключением внешней модели, канала, инструмента или стороннего skill.

### Стандарт и граница переносимости

- [Agent Skills — Specification](https://agentskills.io/specification) — открой разделы `Frontmatter`, `Compatibility`, `allowed-tools` и `Validation`: стандарт переносит ядро пакета, но не гарантирует одинаковые tools, permissions и расширения в разных runtime.

### Выбранный runtime

- [OpenClaw — Skills](https://docs.openclaw.ai/tools/skills) — ветка для OpenClaw: каталоги установки, dependency gates, runtime-specific metadata, проверка источника и граница доверия для сторонних skills.
- [Hermes — Skills System](https://hermes-agent.nousresearch.com/docs/user-guide/features/skills) — ветка для Hermes: progressive disclosure, platform-specific metadata, требования к toolsets и approval изменений, созданных самим агентом.
- [Hermes — Migrate from OpenClaw](https://hermes-agent.nousresearch.com/docs/guides/migrate-from-openclaw) — практический mapping двух runtime: что переносится напрямую, что архивируется без эквивалента, как обрабатываются secrets и что нужно проверить после миграции.

### Безопасность и границы данных

- [OpenClaw — Security](https://docs.openclaw.ai/gateway/security) — официальный preflight для реальной установки: trust boundary, входящие каналы, tool blast radius, разрешения и команда `openclaw security audit`.
- [Cisco — Personal AI Agents like OpenClaw Are a Security Nightmare](https://blogs.cisco.com/ai/personal-ai-agents-like-openclaw-are-a-security-nightmare) — конкретный разбор стороннего skill с prompt injection и эксфильтрацией данных; показывает, почему успешная установка не равна безопасному переносу.
- [Simon Willison — The Lethal Trifecta for AI Agents](https://simonwillison.net/2025/Jun/16/the-lethal-trifecta/) — независимая модель сочетания приватных данных, недоверенного содержимого и внешнего канала; сопоставь её со своим `data_egress`.
