# Урок 4.1 · Skills и SKILL.md

**Фаза 4 — Скиллы, память и проекты** · **Результат фазы:** для одного собственного
процесса связать проверенный skill, memory snapshot, project blueprint, context manifest
и воспроизводимый preflight переноса.

**Результат урока:** после урока студент сможет выбрать повторяемый рабочий процесс,
которому подходит формат skill, описать его в переносимом `SKILL.md`, установить в
выбранного в 0.3 агента и проверить на реальных запросах, что skill применяется в нужных
ситуациях, не вмешивается в соседние задачи и выполняет процесс по заданным критериям.

**Опоры:** в 0.3 ты установил готовые диагностические skills и выбрал каталог своего
агента; в 3.1 подключил готовый `editor`; в 3.4 собрал папку `doc-assistant` с инструкцией
и исполняемыми файлами; в 3.5 сравнивал baseline и candidate на одинаковых случаях. ·
**Дальше:** в 4.2 к переиспользуемому способу действия добавится память, а в 4.3 skill,
память, роль и знания соберутся в рабочий проект.

**Requires:** выбранный и настроенный в 0.3 агент, доступ к его проектной папке и
возможность создать текстовый файл. Python, `pytest`, API-ключ и клонирование курса не
нужны.

> **Главная мысль.** Хороший skill — не просто сохранённый промпт. Это проверенный
> контракт: для каких задач включаться, какой процесс выполнить, где остановиться и по
> каким признакам принять результат.

## От рабочего процесса к переиспользуемому умению

В Фазе 3 ты научил агента делать полезную работу с текстами и документами:

```text
редакторская инструкция
+ код обработки документов
+ правила сохранения смысла и provenance
+ проверочные запросы
+ критерии принятия или отклонения результата
```

Но эти части пока разбросаны по карточкам, файлам и страницам уроков. В новом разговоре
приходится снова объяснять:

- какой процесс выбрать;
- какие шаги нельзя пропускать;
- какие сведения нужно сохранить;
- какие файлы использовать;
- как понять, что результат непригоден.

В 3.1 эту проблему временно решил готовый `editor`: ты установил чужой, уже написанный
skill. В 3.4 ты получил более сложный `doc-assistant`: его `SKILL.md` не только задаёт
правила, но и объясняет агенту, какие скрипты запускать. До сих пор ты был **пользователем**
готовых skills. Теперь переходишь в роль автора.

Фаза 3 отвечала на вопрос «как построить и проверить рабочий процесс». Фаза 4 отвечает
на вопрос «как сделать этот процесс постоянной частью рабочей среды»:

```text
работающий процесс из Фазы 3
→ skill хранит способ действия
→ memory хранит историю и состояние
→ project объединяет роль, знания, skills и память
→ агент использует всё это в следующих задачах
```

## Когда нужен skill, а когда — другой механизм

**Skill** — папка с инструкцией для условно применимого, повторяемого действия. Агент
видит краткое описание доступных skills, выбирает подходящий под текущую задачу и только
тогда читает полную инструкцию.

Это не универсальный контейнер для любых указаний. Сначала реши, какой срок жизни и
область действия нужны правилу.

| Ситуация | Подходящий механизм | Почему |
|---|---|---|
| «Один раз сократи это письмо до пяти пунктов» | Обычный запрос | Правило нужно для одной задачи |
| «В этом репозитории всегда используй Python 3.12 и запускай `ruff`» | Проектная инструкция | Правило действует почти на любую работу в проекте |
| «Когда я прошу проверить редактуру, запускай один и тот же процесс с gates» | Skill | Процесс повторяется, но нужен только для определённого класса запросов |
| «Запомни, что бюджет проекта согласован 12 марта» | Память | Сохраняется факт или состояние, а не способ действия |
| «Рассчитай налог строго по формуле» | Скрипт или инструмент | Нужен детерминированный расчёт; skill может объяснить агенту, когда и как его вызвать |

Хороший кандидат на первый skill одновременно отвечает четырём условиям:

1. Процесс уже приходилось объяснять больше одного раза.
2. Можно назвать запросы, где он нужен, и похожие запросы, где он не нужен.
3. У процесса есть наблюдаемый результат и критерии качества.
4. Основные правила достаточно стабильны, чтобы переиспользовать их в следующих задачах.

Если правило нужно всегда, не прячь его в условно загружаемый skill. Если действие проще
надёжно выполнить кодом, не проси модель каждый раз изобретать вычисление: положи скрипт
рядом, а в skill опиши условия и порядок его запуска.

## Как агент находит skill

Skill — это папка с обязательным файлом `SKILL.md`. Первая версия может состоять только
из него:

```text
my-skill/
└── SKILL.md
```

В начале файла находится **YAML frontmatter** — небольшой блок метаданных между двумя
строками `---`. После него идёт обычный Markdown с инструкцией:

```markdown
---
name: my-skill
description: Проверяет рабочий процесс по критериям качества. Использовать, когда нужно провести повторяемое ревью процесса или диагностировать первый непройденный шаг.
---

# My skill

1. Уточни цель и входные данные.
2. Проверь процесс по критериям.
3. Назови первый обнаруженный дефект.
4. Предложи исправление и повторную проверку.
```

Для переносимого ядра формата нужны два поля:

- `name` — короткое машинное имя: от 1 до 64 строчных латинских букв, цифр и дефисов;
  дефис не ставят в начале или конце и не повторяют дважды; имя должно совпадать с
  названием родительской папки;
- `description` — что skill делает **и когда его применять**, не более 1024 символов.

Текст после frontmatter — тело skill. В нём находятся необходимые агенту правила:
порядок действий, входы, критерии, границы, примеры и обработка ошибок. Заголовки не
магические: агенту важна ясная инструкция, а не наличие раздела с определённым названием.

### Постепенное раскрытие

Если загрузить тела сотни skills заранее, они займут контекст и начнут конкурировать с
самой задачей. Поэтому применяется **progressive disclosure — постепенное раскрытие**:

```text
1. Метаданные name + description
   доступны агенту для выбора подходящего skill

2. Тело SKILL.md
   читается, когда skill выбран

3. references/, scripts/, assets/ и другие файлы
   открываются или запускаются по инструкции и только при необходимости
```

Отсюда следуют разные требования к частям папки:

- `description` должен помогать **правильно выбрать** skill;
- тело должно помогать **правильно выполнить** задачу;
- дополнительные файлы нужны только тогда, когда без них нельзя надёжно выполнить
  конкретный шаг.

Большая папка сама по себе не обязательно тратит контекст: проблема возникает, если
`SKILL.md` велит читать всё без разбора или сам перегружен деталями. Держи основной файл
как короткую карту действий, а крупные справочники и редкие ветки выноси в отдельные
файлы с явным объяснением, когда их открывать.

## `description`: граница применимости, а не мешок ключевых слов

Сравни три описания:

```yaml
description: Помогает с документами.
```

По нему непонятно, какие документы, какое действие и когда оно нужно. Skill может
пропускать нужные задачи или вмешиваться почти в любую работу с файлами.

```yaml
description: Редактирует тексты, письма, отчёты, документы, заметки, сообщения, резюме и любые другие материалы.
```

Здесь объектов много, но граница всё ещё размыта. Перечень синонимов не заменяет условия
применения.

```yaml
description: Проверяет резюмирование, редактуру и адаптацию тона без потери чисел, условий и ответственности. Использовать, когда нужно сократить или переписать рабочий текст и проверить сохранение смысла.
```

Теперь видны:

- **действие** — проверяет преобразование текста;
- **объект** — рабочий текст;
- **момент применения** — просьба сократить или переписать;
- **критический результат** — не потерять числа, условия и ответственность.

Агент выбирает skill не учебным пересечением слов, а по смыслу доступного ему описания и
текущего запроса. Поэтому не нужно угадывать все возможные синонимы. Нужна достаточно
конкретная граница: что входит в ответственность skill, а что остаётся соседним задачам.

Отрицательная граница обычно лучше работает в теле:

```markdown
Не применяй этот процесс для проверки фактической достоверности источника:
он контролирует сохранение переданного смысла, но не доказывает истинность исходных данных.
```

Так агент понимает не только момент старта, но и предел обещаний.

## Разбери два знакомых skill

Перед созданием собственного сравни два уже знакомых артефакта.

### `editor`: инструкция без кода

Открой готовый [`editor`](../../../03-text-and-documents/01-summarization-editing-tone/outputs/editor/SKILL.md).
Найди в нём:

1. Фразы в `description`, по которым агент отличит редактуру от других задач.
2. Условия, которые нужно уточнить до преобразования текста.
3. Защищённые сведения и gates.
4. Ситуацию, в которой агент должен остановиться, а не выдать гладкий текст.

Затем ответь: какое правило относится к **выбору** skill, а какое — к **выполнению**
редакторского процесса? Если всё поместить в `description`, каталог skills станет
тяжёлым и неясным. Если оставить в описании только «редактор», агент не увидит границу
применения.

### `doc-assistant`: инструкция плюс исполняемые файлы

Открой [`doc-assistant`](../../../03-text-and-documents/04-vector-stores/outputs/doc-assistant/SKILL.md).
Его `SKILL.md` не реализует vector store заново. Он объясняет агенту:

- когда нужен поиск по пользовательскому корпусу;
- какие команды запустить;
- как интерпретировать `evidence_found` и `insufficient_context`;
- когда отказаться от генерации;
- по каким сценариям проверить результат.

Это важное разделение ответственности:

```text
SKILL.md решает: когда и по какому процессу действовать
скрипт решает: как детерминированно выполнить вычисление
тестовый сценарий решает: можно ли принять совместный результат
```

Дополнительный скрипт нужен не каждому skill. Добавляй его только для вычисления,
преобразования или проверки, которые должны воспроизводиться точнее свободной инструкции.

## Основная практика: создай skill с нуля

Создавай не демонстрационный `my-skill`, а умение, которое пригодится после урока.
Работай в собственной папке, настроенной в 0.3; репозиторий курса клонировать не нужно.

Если у тебя уже есть повторяемый процесс, выбери его. Если подходящего процесса пока нет,
используй продолжение Фазы 3: skill для ревью решения о retrieval-конфигурации. Он должен
проверять, что baseline и candidate сравнивались на одинаковых случаях, no-answer не
сломался, регрессии показаны по отдельным запросам, а решение следует из доказательств.

### Шаг 1. Зафиксируй контракт до написания

Создай рядом с будущим skill короткий черновик:

```markdown
# Контракт skill

Повторяемая задача:
Пользовательские формулировки, при которых skill нужен:
Похожие задачи, при которых skill не нужен:
Что skill получает на входе:
Какой результат возвращает:
Три обязательных правила:
Условие остановки или эскалации:
Как пользователь проверит результат:
```

Не начинай с `name`. Сначала убедись, что существует цельный процесс. Если ответы
распадаются на несколько несвязанных задач, сузь skill. Если невозможно назвать
отрицательный случай, граница пока слишком широкая.

### Шаг 2. Выбери каталог

Используй **проектный** каталог того агента, которого выбрал в 0.3:

| Агент | Папка skill в проекте |
|---|---|
| Claude Code | `.claude/skills/<name>/SKILL.md` |
| Cursor | `.cursor/skills/<name>/SKILL.md` |
| Codex | `.agents/skills/<name>/SKILL.md` |

Не создавай сразу три копии. Сначала добейся правильного поведения в одной среде.
Переносимость проверишь после того, как базовая версия станет рабочей.

Назови папку по формату `lowercase-with-hyphens`, например
`retrieval-decision-review`. Это же значение запиши в поле `name`.

### Шаг 3. Напиши минимальную рабочую версию

Создай `SKILL.md`:

```markdown
---
name: <имя папки>
description: <что делает skill и когда его применять>
---

# <Понятное название>

<Одно предложение о результате и его границе.>

## Процесс

1. <Что проверить или сделать сначала>
2. <Следующее решение>
3. <Как проверить результат>
4. <Когда остановиться, запросить данные или передать решение человеку>

## Критерии результата

- <Наблюдаемый критерий 1>
- <Наблюдаемый критерий 2>

## Не применять

- <Соседний случай, который не входит в ответственность skill>
```

Это стартовая форма, а не обязательное оглавление стандарта. Объедини или переименуй
разделы, если так процесс будет понятнее. Не добавляй `scripts/`, `references/` и
`assets/` заранее: сначала покажи, какой шаг без них невозможно выполнить надёжно.

### Шаг 4. Проверь файл до запуска

Проведи ручную приёмку:

- папка содержит `SKILL.md`;
- `name` совпадает с именем папки;
- frontmatter начинается и заканчивается отдельной строкой `---`;
- `description` называет и действие, и ситуацию применения;
- тело не требует неизвестных файлов или инструментов;
- ожидаемый результат можно проверить;
- секретов, токенов и чувствительных данных внутри нет.

Если используешь валидатор выбранной платформы или открытой спецификации, его зелёный
результат подтверждает только структуру. Он не доказывает, что агент выберет skill в
нужный момент и правильно выполнит работу.

### Шаг 5. Проверь поведение

В 3.5 ты не принимал новый retriever по факту запуска: сравнивал его с baseline на
заранее определённых случаях. Здесь действует тот же принцип.

Создай в папке skill файл `tests.md` с таблицей:

```markdown
| Запрос | Должен примениться? | Ожидаемое поведение | Фактическое поведение | Решение |
|---|---|---|---|---|
| <прямой запрос> | да | <критерии> | | |
| <другая формулировка той же задачи> | да | <критерии> | | |
| <похожая, но чужая задача> | нет | <что должен сделать агент без skill> | | |
```

Перед запуском заполни первые три столбца. Затем открой **новый разговор** в том же
проекте и отправь запросы по одному. Новый разговор уменьшает риск, что агент продолжает
следовать инструкции только потому, что вы обсуждали её при создании.

Проверяй два разных свойства:

1. **Выбор.** Skill применяется к двум целевым формулировкам и не вмешивается в соседнюю
   задачу. Если интерфейс не показывает факт загрузки, используй наблюдаемый признак из
   процесса: обязательный формат, проверку или явно требуемый шаг.
2. **Исполнение.** Агент соблюдает правила тела, обрабатывает условие остановки и выдаёт
   результат по критериям.

Не проси модель раскрывать скрытые рассуждения. Нужны наблюдаемые действия и результат:
какие данные она запросила, какие проверки выполнила, где остановилась и что вернула.

### Шаг 6. Исправь первый обнаруженный дефект

| Наблюдение | Вероятная причина | Что менять |
|---|---|---|
| Skill не применяется к прямому запросу | Описание слишком абстрактно или не называет ситуацию | Уточнить действие, объект и момент применения в `description` |
| Skill включается в соседней задаче | Граница слишком широкая | Сузить `description`, добавить явное «не применять» |
| Skill выбран, но пропускает важный шаг | Проблема в теле, а не в обнаружении | Усилить порядок, критерий или условие остановки |
| Агент не находит файл | Ссылка неясна или файл лежит не там | Использовать относительный путь и прямо указать, когда открыть файл |
| Результат выглядит убедительно, но его нельзя принять | Нет проверяемых критериев | Добавить рубрику, ожидаемый формат или проверочный шаг |

После изменения повтори **все три** исходных сценария. Исправление одного запроса может
создать регрессию в другом. Добавляй новый тест только для реально найденной ошибки, а
не ради количества.

## Переносимость без обещания полной идентичности

`SKILL.md` имеет открытое переносимое ядро, но агенты различаются:

- используют разные проектные и личные каталоги;
- по-разному показывают автоматическое или явное применение skill;
- могут поддерживать дополнительные поля frontmatter;
- дают разные инструменты, права, сеть и среду исполнения.

Поэтому «переносимый skill» означает:

1. Базовая папка следует открытому формату.
2. Основная инструкция не зависит без необходимости от одного интерфейса.
3. Требования к среде записаны явно.
4. На каждой целевой платформе skill устанавливается и проверяется отдельно.

Не объявляй переносимость по факту копирования файла. После переноса повтори минимум
прямой и отрицательный сценарии из `tests.md`. Если добавляешь платформенное расширение,
отдели его от базового контракта и назови ограничение.

Загрузка ZIP в веб-интерфейс, регистрация skill через API, плагины и распространение по
организации полезны, но не нужны для первого авторского цикла. Их интерфейсы отличаются
и меняются быстрее самого формата. Сначала создай и проверь skill локально в выбранном
агенте.

## Безопасность: skill устанавливается как программный пакет

Skill может содержать не только текст, но и скрипты, зависимости, сетевые обращения и
команды для инструментов. Поэтому стороннюю папку нельзя считать безопасной только
потому, что в ней лежит Markdown.

Перед установкой чужого skill:

1. Проверь источник и лицензию.
2. Просмотри **все** файлы, а не только `SKILL.md`.
3. Найди команды, сетевые адреса, зависимости и обращения к файловой системе.
4. Сопоставь запрашиваемые действия с заявленной задачей.
5. Не выдавай лишние права и не передавай секреты через текст skill.
6. Сначала запускай на нечувствительных данных в ограниченной рабочей папке.

Если назначение — «редактировать текст», а скрипт отправляет файлы на неизвестный адрес,
это не расширенная возможность, а причина остановить установку.

Для собственного skill действует та же дисциплина: документируй зависимости, используй
минимальные права, не зашивай ключи и оставляй опасные или необратимые действия под
явным подтверждением человека.

## Переносимый результат

После урока у тебя остаётся папка:

```text
<skill-name>/
├── SKILL.md
├── tests.md
├── references/   # только если понадобились
├── scripts/      # только если понадобились
└── assets/       # только если понадобились
```

В качестве заполненного примера изучи
[`retrieval-decision-review`](../outputs/retrieval-decision-review/SKILL.md): он
превращает сравнительный процесс 3.5 в instruction-only skill. Рядом лежит
[`tests.md`](../outputs/retrieval-decision-review/tests.md) с заранее заданными
положительными, отрицательным и граничным сценариями.

Пример не нужно копировать, если твой рабочий процесс другой. Его задача — показать
связь между `description`, телом, условием остановки и поведенческой приёмкой.

Skill готов, когда:

- решает одну названную повторяемую задачу;
- установлен в выбранного агента;
- проходит два целевых и один соседний сценарий;
- выполняет процесс по наблюдаемым критериям;
- после найденного дефекта исправлен и повторно проверен;
- не содержит скрытых зависимостей, секретов и необоснованных полномочий;
- его ограничения понятны следующему пользователю.

## Где здесь 4D

| 4D | Решение автора skill |
|---|---|
| **Delegation** | Выбрать устойчивый процесс, который полезно делегировать, и оставить человеку решения, требующие полномочий или предметной ответственности |
| **Description** | Ясно задать ситуацию применения, входы, последовательность, критерии результата и условия остановки |
| **Discernment** | Отличить ошибку обнаружения от ошибки исполнения, прогнать положительные и отрицательный сценарии, заметить регрессию |
| **Diligence** | Проверить файлы и зависимости, ограничить права, не хранить секреты, зафиксировать тесты и повторить их после изменения |

Четыре компонента образуют один цикл. Хорошо описанный, но не проверенный skill ещё не
готов; удачно сработавший один раз, но небезопасный или слишком широкий — тоже.

## Дополнительное чтение

Материалы ниже не обязательны для завершения урока. Выбирайте ветку по интересу:
точный стандарт, устройство skill, рекомендации по авторингу, особенности выбранного
агента, production-примеры, распространение или безопасность.

- [Anthropic — Agent Skills overview](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/overview) — для концептуальной модели: устройство skill, progressive disclosure, ограничения среды выполнения и базовые риски.
- [Agent Skills specification](https://agentskills.io/specification) — для точного переносимого контракта: откройте разделы `Frontmatter`, `File references` и `Validation`. Само ядро формата переносимо, но установка, расширения и поведение зависят от конкретного агента.
- [Anthropic — Agent Skills best practices](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices) — для углубления в `description`, структуру инструкций, оценивание и итерации после найденного дефекта.
- Документация выбранного в практике агента: [Claude Code](https://code.claude.com/docs/en/skills), [Cursor](https://cursor.com/docs/skills) или [Codex](https://learn.chatgpt.com/docs/build-skills) — откройте только свою ветку и уточните каталоги установки, способы явного и неявного вызова и платформенные расширения.
- [anthropics/skills](https://github.com/anthropics/skills) — для чтения production-примеров: сравните границы задачи, `description`, дополнительные файлы и встроенные ограничения; не устанавливайте незнакомый skill без проверки содержимого.
- [Anthropic — Equipping agents for the real world with Agent Skills](https://www.anthropic.com/engineering/equipping-agents-for-the-real-world-with-agent-skills) — для более глубокой архитектурной логики: progressive disclosure, выбор между инструкцией и кодом, проектирование от проверочных сценариев.
- [Claude Code — Create plugins](https://code.claude.com/docs/en/plugins) — отдельная ветка для тех, кому нужно распространять skill в экосистеме Claude: упаковка, версии, неймспейсы и marketplace.
- [Thoughtworks — Skills as executable onboarding documentation](https://www.thoughtworks.com/en-us/radar/techniques/skills-as-executable-onboarding-documentation) — независимый взгляд на skills как исполняемую документацию команды и на риск устаревания такой документации.
- [Simon Willison — “Claude Skills are awesome, maybe a bigger deal than MCP”](https://simonwillison.net/2025/Oct/16/claude-skills/) — независимый разбор силы простого формата и сравнение Skills с MCP; полезный горизонт для следующих уроков, но не источник контракта установки.
- [Snyk — ToxicSkills: malicious AI agent skills](https://snyk.io/blog/toxicskills-malicious-ai-agent-skills-clawhub/) — ветка про безопасность: модель угроз, признаки опасного skill и действия перед установкой. Численные оценки статьи относятся к исследованным каталогам, а не ко всем Agent Skills.
