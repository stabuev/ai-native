## Ситуация: нужный фрагмент существует, но модель его ещё не видит

В 3.2 мы превратили учебный отчёт о пилоте в записи такого вида:

```json
{
  "id": "sample_report.md#chunk-0002",
  "source": "sample_report.md",
  "word_start": 120,
  "word_end": 190,
  "text": "Если согласование не получено к 16 сентября, запуск переносится..."
}
```

Теперь представь ассистента по этому отчёту. Пользователь спрашивает:

> Что произойдёт, если согласование безопасности не будет получено к 16 сентября?

Модель не получает весь корпус автоматически. Есть три плохих варианта:

1. не передать ей документ — тогда ответ будет опираться на встроенные знания и догадку, а не на внутренний отчёт;
2. каждый раз передавать весь корпус — на большом наборе документов это расходует контекст и затрудняет проверку источника;
3. передать первые несколько чанков — нужное условие может оказаться в другом месте.

Нужна отдельная операция: по вопросу выбрать несколько подходящих записей и только
после этого собирать запрос модели. Эта операция называется **retrieval**, или
извлечение релевантных фрагментов.

Слово **релевантный** здесь не означает «вообще похожий на тему». Фрагмент релевантен
конкретному вопросу, если содержит доказательство, полезное для ответа на него. Раздел
про метрики относится к тому же пилоту, но не отвечает на вопрос о согласовании.

## Где retrieval находится внутри RAG

**RAG** — retrieval-augmented generation, то есть генерация с контекстом, найденным
перед ответом. Для этого урока полезно разделять три операции:

```text
вопрос
  │
  ▼
RETRIEVE: найти записи корпуса
  │        результат: чанки + ID + источник + score
  ▼
AUGMENT: собрать из них пакет контекста и инструкции
  │        результат: проверяемый промпт
  ▼
GENERATE: получить ответ по переданному контексту
           результат: ответ со ссылками на ID
```

Это разделение нужно не ради терминов, а ради диагностики:

| Наблюдение | Где искать сбой |
|---|---|
| Нужного ID нет среди найденных чанков | retrieval не нашёл доказательство |
| ID найден, но потерялся при сборке промпта | augmentation отбросил доказательство |
| Доказательство есть в промпте, но ответ ему противоречит | generation или инструкция ответа |

Промпт не исправит отсутствующий чанк. Более сильная модель тоже не докажет факт,
который retrieval ей не показал. Поэтому в этом уроке мы сначала проверяем поиск
отдельно от качества ответа.

## Как сравнить вопрос и чанк без нейросети

Человек видит связь по смыслу. Компьютеру нужен способ превратить вопрос и текст в
сопоставимые числа. Мы начнём с **лексического** подхода: совпадение возникает, когда
в вопросе и чанке встречаются одинаковые слова.

Учебный механизм состоит из четырёх шагов:

```text
текст
→ токены
→ TF-IDF-вектор
→ косинусная близость вопроса и каждого чанка
→ ранжирование и решение «вернуть / не вернуть»
```

### Шаг 1. Токены и стоп-слова

**Токен** в этом упражнении — последовательность букв, цифр или `_`, найденная
регулярным выражением `\w+`. Мы приводим токены к нижнему регистру:

```text
"Запуск переносится 16 сентября"
→ ["запуск", "переносится", "16", "сентября"]
```

Очень частые служебные слова вроде «и», «в», «на» редко помогают выбрать чанк. Мы
удаляем их по короткому, видимому списку `STOP_WORDS`. Это не универсальный
лингвистический анализ: список пригоден для учебного русского корпуса, но для другого
языка или домена его нужно проверить заново.

Мы также не приводим слова к нормальной форме. Поэтому `перенос`, `переносится` и
`перенести` остаются разными токенами. Эта ограниченность позже станет наблюдаемым
типичным сбоем.

### Шаг 2. TF-IDF: вес слова внутри корпуса

После токенизации каждому слову нужен вес. Простое «слово встретилось» плохо различает
характерный термин и слово, которое есть почти везде. **TF-IDF** соединяет две величины.

**TF — term frequency**, частота слова в одном чанке:

```text
TF(term, chunk) = число term в чанке / число оставшихся токенов чанка
```

Если `запуск` встречается два раза среди 20 токенов, `TF = 2 / 20 = 0.1`.

**DF — document frequency**, количество чанков корпуса, содержащих слово хотя бы один
раз. Если `запуск` встретился в трёх чанках, `DF = 3`, даже если в одном из них слово
повторено пять раз.

**IDF — inverse document frequency**, коэффициент редкости слова по корпусу. В коде
используется сглаженная формула:

```text
IDF(term) = log((N + 1) / (DF + 1)) + 1
```

`N` — количество чанков. Чем меньше `DF`, тем выше IDF и тем сильнее редкое совпадение
влияет на поиск.

Наконец:

```text
TF-IDF(term, chunk) = TF(term, chunk) × IDF(term)
```

Важная точность: в выбранной сглаженной формуле слово, которое есть во всех чанках,
получает `IDF = 1`, а не ноль. IDF уменьшает влияние частых слов относительно редких,
но сам по себе не обязан удалить «и» или «в». Поэтому мы отдельно используем
`STOP_WORDS`; говорить, что эта формула «почти зануляет» любое частое слово, было бы
неверно.

### Шаг 3. Разреженный вектор

Весь словарь корпуса можно представить как набор координат:

```text
["16", "безопасность", "запуск", "метрики", "пилот", ...]
```

Для каждого чанка TF-IDF задаёт значение по каждой координате. Большинство слов в
конкретном чанке отсутствует, поэтому хранить тысячи нулей незачем. Используем
**разреженный вектор** — словарь только ненулевых весов:

```python
{
    "16": 0.08,
    "безопасность": 0.12,
    "запуск": 0.06,
}
```

Это всё ещё вектор, просто компактно записанный как `{слово: вес}`. Слова запроса,
которых вообще нет в словаре корпуса, получают вес `0` и не создают совпадения.

TF-IDF превращает текст в вектор, но в современном RAG словом `embedding` обычно
называют обученное плотное представление. Чтобы не спутать механизмы, наш учебный
вектор будем называть точнее: **разреженное лексическое представление**. Плотные
нейросетевые embeddings появятся как другой способ построить вектор, а не как другое
определение retrieval.

### Шаг 4. Косинусная близость

Нужно сравнить направление вектора вопроса с направлением вектора чанка. Для этого
используется **косинусная близость**:

```text
cosine(a, b) = (a · b) / (||a|| × ||b||)
```

- `a · b` — скалярное произведение: сумма произведений совпадающих координат;
- `||a||` и `||b||` — длины векторов;
- результат `1` означает одинаковое направление;
- результат `0` означает отсутствие общих ненулевых координат.

Мини-пример по двум словам:

```text
a = [1, 0]
b = [1, 1]

a · b = 1×1 + 0×1 = 1
||a|| = 1
||b|| = √2 ≈ 1.41
cosine(a, b) = 1 / 1.41 ≈ 0.71
```

Деление на длины важно: без него длинный чанк мог бы получать большой score только
из-за большего числа слов. Но cosine не является вероятностью правильного ответа.
`0.33` не означает «33% уверенности», а значения из разных корпусов нельзя механически
сравнивать.

## От score к решению

После вычисления cosine для каждого чанка retriever сортирует записи по убыванию.
**Top-k** означает «не больше `k` первых результатов».

Однако top-k сам по себе не гарантирует релевантность. Если все scores равны нулю,
«лучшие три» всё равно были бы случайными тремя чанками. Поэтому контракт `search`
двухступенчатый:

1. отбросить score `0` и всё ниже `min_score`;
2. вернуть не больше `k` оставшихся записей.

При `min_score=0` функция принимает любое **положительное** лексическое совпадение, но
никогда не возвращает нулевое. Это безопаснее слепого top-k, но ещё не доказывает, что
фрагмент отвечает на вопрос: одно совпавшее слово может быть шумом.

Универсального `min_score` нет. Он зависит от корпуса, разбиения, запросов и
представления. Порог выбирают не по красивому числу, а по примерам, где заранее
известно, что должно быть найдено и где правильный результат — ничего не вернуть.

`k` тоже является решением с ценой:

- слишком маленький `k` может не включить второй необходимый фрагмент;
- слишком большой `k` добавляет шум и расходует контекст;
- изменение `k` не исправляет нулевое совпадение синонимов.

## Предскажи результаты до запуска

В исходниках есть семь чанков того же `sample_report.md`, подготовленных в 3.2 с
`size=70` и `overlap=10`.

Сначала не запускай код. Для каждого запроса предскажи результат:

| Запрос | Ожидание |
|---|---|
| `согласование получено 16 сентября запуск переносится` | первым должен быть `chunk-0002` |
| `какой рекламный бюджет` | `[]`: таких слов и факта в корпусе нет |
| `кто автор финального документа` | лексический промах: в корпусе написано «ответственный за итоговый отчёт» |
| `и в на` | `[]`: после удаления стоп-слов запрос пуст |

Реальный результат первого запроса:

```text
0.331  sample_report.md#chunk-0002
0.205  sample_report.md#chunk-0001
```

Первым найден чанк с точным условием переноса. Соседний `chunk-0001` тоже содержит
слова о согласовании и безопасности, а overlap повторил границу между чанками. Это не
ошибка: иногда для ответа нужны оба фрагмента. Их ID и позиции позволяют увидеть
повторение и не выдавать два соседних чанка за два независимых доказательства.

Нерелевантный запрос и запрос только из стоп-слов возвращают `[]`. Запрос про «автора
финального документа» тоже возвращает `[]`, но по другой причине: доказательство в
корпусе есть, однако слова запроса и документа не совпали. Первый случай — правильное
воздержание, второй — ошибка лексического retrieval. Одинаковая пустая выдача требует
разной интерпретации, и различить их можно только по размеченным ожиданиям.

## Минимальная оценка retrieval

Создадим маленький набор случаев:

```python
EVAL_CASES = [
    {
        "query": "когда запускается пилот iOS",
        "expected_ids": ["sample_report.md#chunk-0000"],
    },
    {
        "query": "какой рекламный бюджет",
        "expected_ids": [],
    },
]
```

Непустой `expected_ids` означает: среди первых `k` должен встретиться хотя бы один из
этих ID. Так мы получаем учебный **Hit@k**:

```text
Hit@k = доля ответимых запросов,
        где top-k содержит хотя бы один ожидаемый ID
```

Пустой `expected_ids` означает no-answer случай: успешен только пустой результат.
`evaluate()` считает его отдельно как точность воздержания. Смешивать эти два типа в
одну красивую цифру опасно: retriever, который всегда возвращает `[]`, идеально
«воздерживается», но ничего не находит.

Этот набор не доказывает production-качество. Он нужен, чтобы:

- воспроизвести конкретный удачный и неудачный запрос;
- сравнить `k` и `min_score` на одних ожиданиях;
- не улучшить один пример ценой незаметной поломки другого;
- локализовать лексический промах до вызова модели.

Полные метрики precision/recall, reranking и оценка ответа появятся в 3.5. Здесь одного
простого Hit@k достаточно, чтобы сделать решение наблюдаемым.

4. эталонный `retriever.py` до первой собственной попытки не открывай.

Используй только стандартную библиотеку Python.

### 1. `_tokens(text)`

Функция должна:

- принимать строку, иначе выбрасывать `TypeError`;
- находить `\w+` в нижнем регистре;
- удалять токены из заданного `STOP_WORDS`;
- возвращать `list[str]`;
- для пустой строки и строки из стоп-слов возвращать `[]`.

### 2. `_tfidf(tokens, idf)` и `_cosine(a, b)`

`_tfidf` должна:

- считать TF как долю токена среди оставшихся токенов;
- умножать TF на IDF из словаря;
- игнорировать слово, которого нет в `idf`;
- для пустого входа возвращать `{}`.

`_cosine` должна:

- принимать два разреженных словаря;
- считать скалярное произведение только по общим ключам;
- делить его на произведение норм;
- возвращать `0.0`, если хотя бы одна норма равна нулю.

### 3. `build_index(chunks)`

Каждый чанк обязан содержать непустые строки `id`, `source`, `text`. Функция должна:

- отклонять строку вместо коллекции записей;
- отклонять запись без обязательного поля;
- отклонять повторяющиеся ID;
- сохранить **все** поля исходной записи, включая позиции;
- токенизировать `text`;
- посчитать DF по `set(tokens)` каждого чанка;
- построить сглаженный IDF и TF-IDF-векторы;
- вернуть `{"chunks": ..., "idf": ..., "vectors": ...}`.

### 4. `search(query, index, k=3, min_score=0.0)`

Функция должна:

- требовать положительный целый `k`, причём `True` не считается допустимым числом;
- требовать числовой `min_score` в диапазоне `[0, 1]`;
- построить TF-IDF-вектор запроса по словарю корпуса;
- вернуть `[]` для пустого запроса, запроса только из стоп-слов и полностью неизвестного запроса;
- ранжировать по cosine;
- при равных scores сохранять исходный порядок чанков;
- отбросить нулевые scores и всё ниже `min_score`;
- вернуть не больше `k` копий исходных записей с добавленным округлённым `score`.

Сравнивай с порогом полный score, а округляй только значение для выдачи. Иначе число
`0.04996`, округлённое до `0.05`, может пройти или не пройти порог из-за формата
отображения.

### 5. `evaluate(cases, index, k=3, min_score=0.0)`

Для каждого случая:

- запусти `search`;
- сохрани `expected_ids` и реальные `retrieved_ids`;
- для ответимого запроса поставь `passed=True`, если множества пересекаются;
- для `expected_ids=[]` поставь `passed=True` только при пустой выдаче.

Итог должен отдельно содержать:

- `answerable.hit_rate_at_k`;
- `no_answer.accuracy`;
- подробности каждого случая, включая провалы.

искусственные `100%`.

## SHIP IT: пакет доказательств для mini-RAG

**Артефакт:** [`outputs/mini_rag.py`](../outputs/mini_rag.py)

Скрипт не копирует реализацию retrieval, а импортирует готовые `build_index` и
`search`. Он добавляет две операции:

```text
prepare_request
  ├─ нет hits → status=insufficient_context, prompt=None
  └─ есть hits → evidence с provenance + проверяемый prompt

answer_with
  ├─ insufficient_context → фиксированный ответ, модель не вызывается
  └─ evidence_found → один вызов переданного generate(prompt)
```

Пакет контекста включает `id`, `source`, позиции, score и текст. Инструкция просит
указывать ID после проверяемых утверждений. Это не делает ответ автоматически верным,
но позволяет увидеть, на какой фрагмент он опирается.

Здесь важны два уровня отказа:

1. retriever не нашёл ни одного положительного совпадения — генератор не вызывается;
2. retriever нашёл тематически похожий текст, но в нём нет ответа — инструкция модели требует сказать «Недостаточно контекста для ответа».

Второй уровень нельзя надёжно проверить одним cosine-score: это уже проверка содержания
ответа, к которой мы вернёмся в 3.5.

## Что изменится с нейросетевыми embeddings

TF-IDF видит совпадение поверхностных форм слов. **Плотный нейросетевой embedding**
строит вектор фиксированной длины из обученного представления текста. Такой retriever
часто лучше находит перефразы и смысловую близость, поэтому может связать «автора
финального документа» с «ответственным за итоговый отчёт».

Но слово «может» здесь принципиально:

- модель embeddings может плохо знать язык или домен;
- короткий запрос может иметь несколько смыслов;
- плохой chunking портит вход для любого представления;
- top-k всё равно может пропустить нужный фрагмент;
- высокий score не является доказательством ответа.

Поэтому смена TF-IDF на нейросетевой способ представления не отменяет `expected_ids`,
негативные запросы, provenance и решение «ничего не найдено». В 3.4 мы заменим
одноразовый словарь на сохраняемое хранилище и подключим готовые embeddings; сам
контракт проверки останется тем же.

## Типичные ошибки

- **Индексировать строки без ID и источника.** Найденный текст нельзя связать с местом документа и проверить.
- **Всегда возвращать ровно `k` записей.** При нулевых scores это случайные чанки, а не доказательства.
- **Считать score вероятностью истины.** Cosine измеряет близость представлений и ничего не гарантирует о правильности будущего ответа.
- **Назначить универсальный порог.** `0.3` не становится хорошим значением без проверки на запросах конкретного корпуса.
- **Подбирать порог по одному удачному вопросу.** Так легко улучшить демонстрацию и сломать остальные случаи.
- **Считать пустую выдачу всегда правильной.** Иногда вопрос действительно вне корпуса, а иногда лексический retriever пропустил существующий синоним.
- **Оценивать только финальный ответ.** Без ожидаемых ID невозможно понять, поиск не нашёл доказательство или генератор проигнорировал его.
- **Считать соседние overlap-чанки независимыми подтверждениями.** Проверяй позиции и повторяющийся текст.
- **Переходить к vector DB до проверки retrieval.** Хранилище ускорит и сохранит индекс, но не исправит неверный критерий релевантности.

## Что сознательно осталось за границей

Сначала выполни Build It. Затем выбирай источник под конкретный вопрос:

- [Stanford IR Book — Tf-idf weighting](https://nlp.stanford.edu/IR-book/html/htmledition/tf-idf-weighting-1.html) — сверь определение `TF × IDF`, влияние частоты по документу и корпусу и вопрос о слове, встречающемся во всех документах.

- [Lewis et al., 2020 — Retrieval-Augmented Generation](https://arxiv.org/abs/2005.11401) — прочитай abstract и введение, чтобы увидеть исходную связку внешнего индекса, provenance и генерации; детали обучения модели для этого урока необязательны.
- [Thakur et al., 2021 — BEIR](https://arxiv.org/abs/2104.08663) — углубление про оценку retrieval на разных доменах и про то, почему один тип retriever не побеждает во всех задачах.
- [Vicki Boykis — What are embeddings?](https://vickiboykis.com/what_are_embeddings/) — необязательный независимый разбор для перехода от разреженных представлений к плотным; начни с секций для high-level intro, не пытайся пройти весь материал до 3.4.
