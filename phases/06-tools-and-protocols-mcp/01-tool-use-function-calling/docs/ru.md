# Урок 6.1 · Tool use / function calling изнутри

**Фаза 6 — Инструменты и протоколы (MCP)** · **Результат фазы:** Объяснить tool use изнутри и поднять собственный MCP-сервер с контролем доступа.
<!-- exercise -->

**Результат урока:** собрать офлайн client-side tool-use runtime, в котором модель
получает пользовательский запрос и публичные схемы, возвращает связанный идентификатором
`tool_call`, а локальный код проверяет allowlist и аргументы до исполнения, возвращает
`tool_result` и останавливает цикл по финалу или лимиту; затем доказать границу исполнения
успешным и отклонённым trace.

**Requires:** обязательный маршрут работает с Python 3 и `pytest`, без сети и API-ключа.
Сопоставление с одним реальным provider API в конце факультативно и требует только того
доступа, который у тебя уже есть.

**Это вход в Фазу 6 — переход от локальных функций к инструментам модели.** В 5.5
Python-код сам вызывал `validate_packet`, `detect_current_anomaly` и `build_report`.
Модель могла предложить объяснение, но не выбирала эти функции и не формировала запрос на
их исполнение. Теперь между моделью и локальным кодом появится явный протокол.

> **MOTTO.** Модель предлагает вызов; runtime решает, можно ли его исполнить.

## PROBLEM — почему «модель сходила в базу» мешает отладке

Фраза «модель вызвала функцию и получила решение отчёта» склеивает несколько разных
действий. Из-за этого трудно ответить на практические вопросы:

- кто видел пользовательский запрос;
- откуда модель узнала о доступных инструментах;
- кто проверил имя и аргументы;
- какой код действительно исполнился;
- к какому вызову относится результат;
- что произойдёт при ошибке или бесконечном повторе.

Для **пользовательского client-side инструмента** модель не получает Python-функцию и не
исполняет её. Приложение передаёт модели только публичное описание. Модель возвращает
структурированное предложение вызова, а контролируемая часть приложения — далее будем
называть её **runtime** — проверяет предложение и лишь затем может вызвать разрешённую
функцию.

У провайдеров бывают и server-side инструменты, которые исполняет их инфраструктура.
Это другой маршрут. В Build It мы сознательно собираем client-side вариант: именно в нём
видна граница между недетерминированным предложением модели и локальным исполнением.

## CONCEPT — шесть объектов одного цикла

### 1. Пользовательский запрос

Цикл начинается не с пустой истории, а с задачи человека. Например:

```text
Какое решение у запуска phase-5-paid-revenue-q2?
```

Без этого объекта учебная «модель» может заранее знать, что надо вызвать, и практика
скроет выбор инструмента внутри stub-кода.

### 2. Публичная спецификация инструмента

**Инструмент** в этом уроке — разрешённая runtime операция, которую модель может
предложить вызвать. Модель видит только:

- `name` — стабильное имя;
- `description` — что операция делает и когда её выбирать;
- `input_schema` — допустимую форму аргументов.

```json
{
  "name": "get_release_decision",
  "description": "Получить сохранённое решение quality gate по точному run_id",
  "input_schema": {
    "type": "object",
    "properties": {
      "run_id": {"type": "string"}
    },
    "required": ["run_id"],
    "additionalProperties": false
  }
}
```

Схема опирается на JSON Schema из 2.4, но учебный валидатор 6.1 поддерживает только
объявленное подмножество верхнего уровня: `type: object`, `properties`, `required`,
`additionalProperties` и `enum`. Мы не называем небольшой Python-код универсальной
реализацией стандарта.

### 3. Локальный реестр

**Реестр**, или allowlist, — словарь разрешённых инструментов внутри приложения. В нём
публичный контракт связан с настоящей Python-функцией:

```text
get_release_decision
├── description
├── input schema
└── fn = _get_release_decision    ← остаётся только в runtime
```

Модель не должна получать `fn`. Иначе учебный интерфейс перестаёт показывать границу
доверия: публичная схема смешивается с исполняемым объектом процесса.

### 4. `tool_call`

Если модель считает инструмент нужным, она возвращает не результат, а предложение:

```json
{
  "type": "tool_call",
  "id": "call-release-1",
  "name": "get_release_decision",
  "arguments": {"run_id": "phase-5-paid-revenue-q2"}
}
```

`id` нужен не для красоты. Один ответ может содержать несколько вызовов, а история —
много результатов. Идентификатор позволяет доказать, какому вызову соответствует
конкретный `tool_result`. В обязательной практике вызовы последовательные, но связь уже
явная.

### 5. Проверка и исполнение в runtime

**Dispatcher** — функция-переключатель между предложением модели и локальным кодом. До
исполнения она последовательно проверяет:

```text
есть непустой call ID?
→ имя находится в локальном allowlist?
→ arguments имеют форму object?
→ обязательные поля присутствуют?
→ типы, enum и запрет лишних полей соблюдены?
→ только после этого fn(**arguments)
```

Схема не доказывает, что действие разрешено пользователю, безопасно для данных или
семантически разумно. Полный контроль прав, write-операций и подтверждений будет в 6.5.
Здесь схема решает более узкую задачу: кривой вызов не должен дойти до Python-функции.

### 6. `tool_result` и следующий ход

После успешного исполнения runtime создаёт связанный результат:

```json
{
  "type": "tool_result",
  "call_id": "call-release-1",
  "ok": true,
  "content": {
    "decision": "publish",
    "metric_id": "paid_revenue",
    "as_of": "2026-07-01"
  }
}
```

Этот объект добавляется в историю и снова передаётся модели. Теперь она может вернуть:

- новый `tool_call`, если нужен ещё один разрешённый шаг;
- `final`, если данных достаточно;
- исправленный вызов, если предыдущий результат был `ok: false`.

Runtime, а не модель, считает число вызовов. Если новый вызов превышает
`max_tool_calls`, он блокируется **до** исполнения.

## Полный инвариант

```text
user request
    │
    ├── public tool specs: name + description + input_schema
    ▼
model_fn(history, tool_specs)
    │
    ├── final ─────────────────────────────────────────────► stop
    │
    └── tool_call(id, name, arguments)
              │
              ▼
       runtime / dispatcher
       1. call ID
       2. local allowlist
       3. declared schema subset
       4. max_tool_calls
              │
       rejected│                         accepted
              ▼                             ▼
 tool_result(ok=false, error)    fn(**arguments)
              │                             │
              └──────────────┬──────────────┘
                             ▼
                 tool_result(call_id, ...)
                             │
                             └──────────────► model_fn
```

У разных провайдеров поля называются по-разному, но проверяемый инвариант одинаков:
**публичный контракт → связанный вызов → контролируемое исполнение → связанный
результат → продолжение или финал**.

## ПРЕДСКАЖИ TRACE ДО КОДА

Не запускай демо сразу. Сначала ответь:

1. Получит ли модель Python-функцию `_get_release_decision`?
2. Что исполнится раньше: проверка `run_id` или тело функции?
3. Какие два поля должны совпасть у вызова и результата?
4. Увидит ли модель результат, если runtime не добавит его в историю?
5. Может ли `publish` из 5.5 быть придуман моделью заново?

Правильная модель:

- модель видит спецификацию, но не callable;
- аргументы проверяются до исполнения;
- `tool_call.id == tool_result.call_id`;
- невозвращённый результат для следующего хода не существует;
- инструмент только читает сохранённое решение, а policy 5.5 остаётся
  детерминированной.

## РАЗБОР УСПЕШНОГО TRACE

В эталонном демо есть два инструмента: `add` как простая проверка механики и
`get_release_decision` как мост из Фазы 5. Детерминированный **stub** заменяет LLM:
это тестовый двойник, который всегда возвращает известные ответы. Он не измеряет качество
реальной модели, зато позволяет проверить runtime без сети.

```text
1. history = [user request]
2. model_fn получает history и public specs без fn
3. model_fn → tool_call(id=call-release-1,
                        name=get_release_decision,
                        arguments={run_id: phase-5-paid-revenue-q2})
4. dispatch → allowlist PASS → schema PASS → локальная функция
5. runtime → tool_result(call_id=call-release-1, ok=true, content=...)
6. model_fn видит result → final("Решение: publish ...")
```

Модель не вычислила quality gate. Она выбрала read-only инструмент и сформировала
аргументы. Решение `publish` взято из локальной проверенной фикстуры.

## РАЗБОР ОТКЛОНЁННОГО ВЫЗОВА

Пусть модель забудет обязательный `run_id`:

```json
{
  "type": "tool_call",
  "id": "call-bad",
  "name": "get_release_decision",
  "arguments": {}
}
```

Dispatcher не вызывает функцию и возвращает в историю:

```json
{
  "type": "tool_result",
  "call_id": "call-bad",
  "ok": false,
  "error": "невалидные аргументы: нет обязательного аргумента: run_id"
}
```

Следующий ход модели может предложить исправленный вызов с новым ID. В тесте отдельно
проверяется, что функция реально исполняется только один раз — после исправления. Так
мы отличаем красивое сообщение об ошибке от доказанного отсутствия побочного эффекта.

### Шаг 1. Отдели public specs от локального реестра

Создай `Tool(name, description, schema, fn)` и функцию:

```python
public_tool_specs(registry) -> list[dict]
```

Она возвращает только `name`, `description` и глубокую копию `input_schema`.
`Callable` не должен попасть в список, передаваемый модели; изменение возвращённой схемы
не должно менять локальный реестр.

### Шаг 2. Реализуй ограниченный валидатор

```python
validate_args(args, schema) -> list[str]
```

Поддержи только явно нужное уроку подмножество:

- `type: object` для всего `arguments`;
- `properties` верхнего уровня;
- `required`;
- простые типы `string`, `number`, `integer`, `boolean`, `array`, `object`, `null`;
- `enum`;
- `additionalProperties: false`.

Учти Python-ловушку: `isinstance(True, int)` возвращает `True`, но JSON boolean не должен
проходить как `integer` или `number`. `NaN` и бесконечность тоже не являются допустимым
JSON number для этого runtime.

### Шаг 3. Построй dispatcher

```python
dispatch(tool_call, registry) -> tool_result
```

До `fn(**arguments)` проверь ID, имя, allowlist и аргументы. Успех возвращает
`{type, call_id, ok, content}`. Неизвестный инструмент и невалидный вызов поднимают
`ToolError`. Failure-тест с функцией-шпионом должен доказать, что её тело не выполнялось.

### Шаг 4. Собери bounded loop

```python
run(model_fn, registry, user_request, *, max_tool_calls=3)
    -> (answer, trace)
```

Требования:

1. История начинается с явного `user_request`.
2. `model_fn` получает копии history и public specs.
3. Допустимы только `tool_call` и `final`.
4. Вызов записывается отдельно от связанного результата.
5. Ошибка allowlist или schema превращается в `tool_result(ok=false)` и может быть
   исправлена следующим вызовом.
6. Исключение внутри уже разрешённой Python-функции не маскируется под schema error.
7. Новый вызов сверх `max_tool_calls` блокируется до исполнения.

### Критерий готовности к переносу

```bash
python -m pytest course-work/phase-6/6.1-tool-use/code -q
python course-work/phase-6/6.1-tool-use/code/function_calling.py
```

Зелёными должны быть **11 behavioral tests**. Они проверяют public/private границу,

отсутствие исполнения после отказа, явный user request, порядок trace, исправленный
повтор, неизвестный envelope и лимит вызовов.

После тестов объясни своими словами:

1. почему schema compliance ещё не является разрешением на действие;
2. почему `call_id` входит в корректность, а не только в логирование;
3. какое утверждение доказывает failure-тест с функцией-шпионом;
4. что stub доказывает о runtime и чего не доказывает о реальной модели.

## САМОСТОЯТЕЛЬНЫЙ ПЕРЕНОС

`add` и `get_release_decision` показывают механизм. Теперь спроектируй **один собственный
read-only инструмент**, не копируя их контракт.

Предпочтительный перенос из своей работы Фазы 5:

- `get_failed_checks(run_id)` — вернуть сохранённые проваленные проверки;
- `get_metric_definition(metric_id)` — прочитать локальный semantic contract;
- другой безопасный lookup над собственной нечувствительной фикстурой.

Если Фаза 5 пройдена офлайн без сохранённых данных, создай маленькую вымышленную фикстуру
`lookup_status(item_id)`. Не подключай реальную БД и не копируй чувствительные данные:
в этом уроке оценивается протокол, а не интеграция.

Для собственного инструмента:

1. сформулируй ситуацию, когда его нужно и не нужно выбирать;
2. напиши public spec без callable;
3. добавь его в локальный allowlist;
4. сохрани один успешный trace;
5. намеренно сломай аргумент и сохрани отклонённый trace;
6. докажи, что при отказе функция не исполнилась;
7. вернись к корректному вызову и повтори прогон.

Если делегируешь проектирование ИИ, используй рамку 4D:

- **Delegation:** отдай черновик `description`, схемы или тестовых случаев, но не решение о фактическом исполнении.
- **Description:** передай назначение функции, реальные доступные поля, read-only границу, поддерживаемое подмножество схемы и формат trace.
- **Discernment:** проверь, не выдуманы ли поля, ловит ли описание неверный выбор, связаны ли call/result и доказан ли отказ до side effect.
- **Diligence:** реализуй принятый контракт локально, запусти success/failure tests и сохрани ответственность за allowlist.

## ФАКУЛЬТАТИВНО — сопоставь core envelope с одним API

Обязательный результат уже доказан офлайн. Если у тебя есть подходящий API-ключ, выбери
**одного** провайдера и сопоставь его поля с учебным envelope. Не пытайся запускать все
варианты.

| Инвариант урока | Anthropic Messages | OpenAI Responses | Google Gemini |
|---|---|---|---|
| публичный контракт | `tools` + `input_schema` | function tool + `parameters` | function declaration + `parameters` |
| предложение вызова | `tool_use` с `id`, `name`, `input` | `function_call` с `call_id`, `name`, `arguments` | `function_call` с ID, name и arguments |
| связанный результат | `tool_result` + `tool_use_id` | `function_call_output` + `call_id` | `function_result` + `call_id` |
| продолжение | следующий Messages request | следующий Responses request | следующая interaction / history |

Точные payload и SDK меняются. Поэтому эта таблица фиксирует места адаптации, а
официальная документация в дополнительном чтении остаётся источником текущего контракта.
Не смешивай `role: tool` из OpenAI Chat Completions с `function_call_output` из Responses.

Если запускаешь реальный вызов, используй только read-only инструмент на синтетических
данных и сохрани нормализованный trace рядом с офлайн-прогоном. API-ветка не заменяет
локальные failure-тесты.

## ЧАСТЫЕ ОШИБКИ

- **Начинать history пустой.** Тогда stub скрыто хранит исходную задачу, и студент не видит полный интерфейс цикла.
- **Передавать модели реестр вместе с `fn`.** Модели нужен публичный контракт, а callable остаётся в доверенной части процесса.
- **Называть мини-валидатор JSON Schema validator.** Он проверяет только задокументированное подмножество и не заменяет промышленную библиотеку.
- **Исполнять до проверки.** Сообщение об ошибке после побочного эффекта уже не делает вызов безопасным.
- **Не связывать call и result ID.** При двух вызовах результаты можно перепутать даже при правильных значениях.
- **Считать `bool` числом из-за Python.** Типы runtime должны следовать JSON-контракту, а не случайной иерархии классов языка.
- **Не возвращать failure result модели.** Без структурированной ошибки она не может исправить аргументы в следующем ходе.
- **Считать stub проверкой качества LLM.** Детерминированный двойник проверяет оркестрацию; выбор инструментов реальной моделью требует отдельного eval.
- **Делать API-ветку обязательной.** Контракт урока должен завершаться без платного доступа и сети.
- **Переносить право решения quality gate в модель.** Инструмент может прочитать решение 5.5, но не переписать policy или объявить `publish` без gate.

## Дополнительное чтение

Читать всё не требуется. Выбери одну ветку по своему вопросу: сопоставить учебный
цикл с выбранным API, освежить JSON Schema, понять происхождение идеи или посмотреть,
как качество tool calling измеряют на практике.

**Сопоставить цикл с API одного провайдера**

- [Anthropic — How tool use works](https://platform.claude.com/docs/en/agents-and-tools/tool-use/how-tool-use-works) — открой разделы про client tools и agentic loop: сравни `tool_use.id`, исполнение в приложении и возврат связанного `tool_result` с учебным конвертом урока.
- [OpenAI — Function calling](https://developers.openai.com/api/docs/guides/function-calling) — прочитай `How it works` и `Handling function calls`: обрати внимание на `call_id` и `function_call_output` в Responses API, не смешивая их с форматом Chat Completions.
- [Google Gemini — Function calling](https://ai.google.dev/gemini-api/docs/function-calling) — пройди шаги объявления функции, `function_call`, локального исполнения и `function_result`; это третья реализация того же инварианта с другими именами полей.

**Освежить контракт входных аргументов**

- [JSON Schema — Creating your first schema](https://json-schema.org/learn/getting-started-step-by-step) — вернись к `type`, `properties` и `required` и отдели настоящий стандарт от ограниченного учебного валидатора; остальную страницу можно не читать.

**Понять происхождение идеи**

- [Schick et al., 2023 — Toolformer](https://arxiv.org/abs/2302.04761) — прочитай abstract и introduction, чтобы увидеть исследовательскую постановку: как модель учится решать, какой инструмент вызвать, когда и с какими аргументами; это не руководство по современному API.
- [Patil et al., 2023 — Gorilla](https://arxiv.org/abs/2305.15334) — сосредоточься на ошибках выбора API и аргументов и на роли актуальной документации; статья даёт исторический контекст, а не текущий provider contract.

**Посмотреть, как проверяют качество tool calling**

- [Berkeley Function-Calling Leaderboard (BFCL V4)](https://gorilla.cs.berkeley.edu/leaderboard.html) — изучи категории и методологию, а не только места моделей: leaderboard показывает, почему одного успешного вызова недостаточно для оценки надёжности.
