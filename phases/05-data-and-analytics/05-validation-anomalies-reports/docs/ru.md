## От trace к решению о выпуске

В конце 5.4 BI-планировщик остановился со статусом `ready_for_review`. Он сохранил такой
путь:

```text
paid_revenue: Q1 270 → Q2 200, delta −70
└── region=Питер, delta −50
    └── product=Pro, delta −40
```

Этот trace уже лучше одиночной фразы «выручка упала»: каждый шаг можно увидеть и
повторить. Но воспроизводимость пути ещё не доказывает корректность входных чисел.
Например:

- в observation могла остаться версия semantic contract `0.9`, хотя политика выпуска требует `1.1`;
- обязательный фильтр `status=paid` мог исчезнуть;
- один регион мог потеряться при подготовке декомпозиции;
- delta строки могла не совпасть с `focus − baseline`;
- сумма региональных вкладов могла не дать общий delta;
- корректное число `200` могло оказаться необычным относительно сопоставимой истории.

Последний пункт принципиально отличается от остальных. Несходящаяся арифметика — уже
доказанный дефект пакета. Необычное значение — только сигнал: возможно, данные сломаны,
а возможно, бизнес действительно резко изменился.

Поэтому перед отчётом нужен не один `if`, а **контрольный шлюз** — дальше будем называть
его английским термином **quality gate**. Это функция, которая получает пакет результата
и политику выпуска, сохраняет результаты проверок и принимает ограниченное решение.

```text
результат investigate() из 5.4
        │
        ├── semantic contract
        ├── run_id и as_of
        └── сопоставимая история
                    │
                    ▼
       детерминированный адаптер
                    │
                    ▼
            validation packet
        │
        ├── контракт и обязательные поля
        ├── контрольные значения
        ├── полнота сегментов
        ├── арифметика и сверки
        ├── подтверждение evidence path
        └── сигнал по историческому ряду
                    │
                    ▼
          publish / review / block
                    │
                    ▼
       отчёт + результаты проверок + основание решения
```

## Пять объектов, которые нельзя смешивать

### 1. Пакет расследования

**Пакет** — это переносимое представление результата 5.4, а не сам результат
`investigate()`. Функция `build_validation_packet(...)` переносит status, observations
и evidence path из trace; semantic contract добавляет единицу и обязательные фильтры;
`run_id`, `as_of` и сопоставимая история передаются отдельно. В пакете находятся не
сырые строки заказов, а уже полученные observations и сведения, необходимые для их
проверки:

- `run_id` и `as_of` — какой это запуск и на каком срезе данных;
- `trace_status` — дошло ли расследование до `ready_for_review`;
- `semantic_version`, `metric_id`, периоды и фильтры;
- общие итоги Q1 и Q2;
- декомпозиции по регионам и продуктам;
- evidence path;
- история той же метрики для проверки необычности текущего значения.

Адаптер не должен угадывать отсутствующие значения по финальной фразе расследования.
Поля `run_id` и `as_of` не доказывают корректность чисел: они отвечают, какой именно
запуск мы проверяли и можно ли позже воспроизвести решение. История тоже не возникает из
trace 5.4 — её сопоставимость по метрике, версии определения и периодичности должен
подтвердить владелец policy.

### 2. Политика выпуска

**Политика выпуска** — заранее согласованный контракт проверки. Она не извлекается из
самого отчёта и не придумывается после того, как мы увидели удобный результат.

В учебном примере политика требует:

```python
{
    "semantic_version": "1.1",
    "metric_id": "paid_revenue",
    "required_filters": {"status": "paid"},
    "baseline": "Q1",
    "focus": "Q2",
    "expected_focus_value": 200.0,
    "expected_segments": {
        "region": ["Москва", "Питер", "Казань"],
        "product|region=Питер": ["Basic", "Pro"],
    },
}
```

Зачем перечислять ожидаемые сегменты? Равенство сумм само по себе не доказывает полноту.
Можно потерять Казань и одновременно получить арифметически красивый результат из двух
оставшихся регионов. Поэтому полнота и сверка — разные проверки.

### 3. Жёсткая проверка

**Жёсткая проверка** отвечает на вопрос, соблюдён ли известный контракт. У неё есть:

- стабильный ID, например `contract.required_filters`;
- результат `passed: true/false`;
- понятное сообщение;
- evidence — ожидаемое и фактическое значение;
- действие при провале — в этом уроке `block`.

Примеры жёстких проверок:

| Проверка | Что ловит | Почему блокируем |
|---|---|---|
| `contract.semantic_version` | метрика рассчитана по другой версии смысла | числа нельзя сравнивать как одно и то же определение |
| `totals.finite` | `NaN`, бесконечность, строку вместо числа | дальнейшая арифметика недостоверна |
| `region.segments` | пропущенный или повторённый регион | декомпозиция неполна |
| `region.row_arithmetic` | `delta ≠ focus − baseline` | строка внутренне противоречива |
| `region.reconciliation` | сумма вкладов не равна общему изменению | объяснение не покрывает общий результат |
| `evidence_path.supported` | финальная фраза ссылается на несуществующий вклад | вывод не подтверждён trace |

Жёсткая проверка не спрашивает, «похоже ли число на нормальное». Она сравнивает пакет с
тем, что уже было зафиксировано в контракте.

### 4. Сигнал аномалии

**Аномалия** — наблюдение, которое необычно относительно выбранной истории. Это не
синоним ошибки и не объяснение причины.

В уроке используется простой z-score:

```text
z = (current − mean(baseline)) / std(baseline)
```

- `baseline` — только предыдущие сопоставимые точки;
- `mean` — их среднее;
- `std` — типичное расстояние точек от среднего, стандартное отклонение;
- `current` — новая точка, которую мы проверяем;
- если `|z| > threshold`, точка получает сигнал `review`.

Текущая точка намеренно **не включается** в baseline. Иначе большой выброс сам изменит
среднее и стандартное отклонение и ослабит собственный сигнал.

Есть четыре результата детектора:

- `clear` — порог не пересечён;
- `review` — значение необычно, нужен человек;
- `insufficient_history` — данных мало, поэтому «аномалий нет» утверждать нельзя;
- `invalid` — история имеет неверную форму, тип, `NaN` или бесконечность.

В учебной политике нужно минимум пять прошлых точек. Это не универсальный статистический
закон, а явное решение владельца проверки. Для дневной метрики, сезонного бизнеса или
разных дней недели понадобится другая история и другой метод.

### 5. Решение о выпуске

Quality gate принимает решение по таблице, а не по тону текста модели:

| Условие | Решение | Что делать |
|---|---|---|
| хотя бы одна жёсткая проверка провалена | `block` | исправить пакет или расчёт и повторить проверки |
| история имеет неверный формат | `block` | восстановить корректный вход |
| жёсткие проверки пройдены, но есть аномалия | `review` | передать пакет человеку, не публиковать автоматически |
| жёсткие проверки пройдены, но истории мало | `review` | получить больше контекста или принять явное решение человеком |
| проверки пройдены и сигнал `clear` | `publish` | можно выпускать ограниченный доказательствами вывод |

`Publish` не означает «мы доказали причину падения». Он означает: пакет соответствует
известному контракту, арифметика сходится, evidence path подтверждён, а политика выпуска
не нашла причины для блокировки или ручного ревью.

## Три прогона одного и того же gate

### Случай A: пакет согласован — `publish`

В эталонном пакете:

```text
Q1 = 270
Q2 = 200
delta = 200 − 270 = −70

регионы: −20 − 50 + 0 = −70
продукты Питера: −10 − 40 = −50
```

Исторические значения Q2-подобного среза равны `198, 203, 201, 197, 202`, а текущая
точка — `200`. Среднее baseline равно `200.2`, стандартное отклонение примерно `2.32`,
поэтому:

```text
z = (200 − 200.2) / 2.32 ≈ −0.09
```

Все жёсткие проверки проходят, `|−0.09| < 2`, решение — `publish`.

### Случай B: арифметика не сходится — `block`

Представим, что для Москвы записали `delta = −19`, хотя `150 − 170 = −20`.

Тогда одновременно провалятся как минимум две проверки:

- `region.row_arithmetic` — неверна сама строка;
- `region.reconciliation` — сумма вкладов больше не равна `−70`.

Даже если итог `Q2 = 200` выглядит правдоподобно, отчёт блокируется. Проверка одного
финального числа не заменяет проверку пути, которым оно объясняется.

### Случай C: арифметика сходится, но значение необычно — `review`

Теперь оставим пакет неизменным, но сравним `200` с прошлой историей около `270`:

```text
268, 272, 269, 271, 270 → current 200
```

Контракт, сегменты и суммы по-прежнему корректны. Но текущая точка далеко от baseline,
поэтому detector вернёт `review`. Из этого нельзя заключить «данные сломаны». Правильный
вывод: число корректно прошло известные проверки, но необычно и требует объяснения
человека до автоматической публикации.

## Что именно автоматизировано

В этом уроке **автоотчёт** означает повторяемый единичный запуск:

```text
один входной пакет
→ одна версия политики
→ одинаковый набор проверок
→ детерминированное решение
→ отчёт с доказательствами
```

Такой запуск уже можно безопасно повторять на новом срезе. Но реальный cron, облачный
планировщик, доставка уведомлений, ретраи и мониторинг самого job здесь не настраиваются.
Это инфраструктура распространения, а не механизм проверки результата.

### Шаг 1. Преобразуй результат 5.4 в validation packet

В файле даны три разных входа:

- `DEMO_INVESTIGATION` — сохранённый результат `investigate()` из 5.4;
- `DEMO_SEMANTIC` — версия определения метрики, единица и обязательный фильтр;
- история — отдельный набор сопоставимых прошлых точек и текущая точка последней.

Реализуй:

```python
build_validation_packet(
    investigation,
    semantic,
    *,
    run_id,
    as_of,
    history,
) -> dict
```

Функция должна:

1. взять status и state из результата 5.4;
2. извлечь общие итоги и breakdowns из observations;
3. сопоставить каждый шаг finding с единственной поддерживающей декомпозицией;
4. взять единицу и обязательные фильтры из semantic contract, а не из текста finding;
5. добавить переданные `run_id`, `as_of` и историю;
6. отклонить несовпадающие версии, Metric ID, периоды или неизвестный тип observation.

Эталонный результат адаптера должен точно совпасть с `DEMO_PACKET`. Незавершённый
результат со статусом `step_budget_exhausted` не может превратиться в
`ready_for_review`: gate обязан вернуть `block`.

До запуска кода предскажи решения:

1. эталонный пакет;
2. пакет без `status=paid`;
3. пакет с историей из трёх точек;
4. пакет с корректной арифметикой, но необычным текущим значением.
5. пакет, собранный из незавершённого расследования.

Запиши прогнозы. Иначе зелёный тест покажет только совпадение реализации с тестом, но не
твоё понимание таблицы решений.

### Шаг 2. Реализуй жёсткие проверки

Функция `validate_packet(packet, policy)` должна вернуть список структурированных
результатов. Проверь:

- наличие обязательных полей;
- `ready_for_review`;
- semantic version, metric ID, периоды и обязательные фильтры;
- конечность чисел;
- контрольный итог Q2 = `200`;
- полный набор регионов и продуктов;
- `delta = focus − baseline` в каждой строке;
- `−20 − 50 + 0 = −70`;
- `−10 − 40 = −50`;
- подтверждение каждого шага evidence path;
- совпадение последней исторической точки с Q2.

Не возвращай только `True` или `False`. Ревьюеру нужны ID проверки, сообщение и
evidence, иначе причину блокировки придётся восстанавливать вручную.

### Шаг 3. Реализуй сигнал аномалии

`detect_current_anomaly(history, minimum_baseline_points=5, z_threshold=2.0)` должна:

1. проверить форму и конечность всех значений;
2. отделить последнюю точку от baseline;
3. отличить недостаточную историю от чистого результата;
4. отдельно обработать постоянный baseline с `std == 0`;
5. вернуть статус, пояснение, число baseline-точек и z-score, если он определён.

### Шаг 4. Реализуй решение и отчёт

- `decide_release(checks, anomaly)` применяет таблицу `publish/review/block`;
- `build_report(...)` обязательно включает решение, все PASS/FAIL, сигнал аномалии, evidence path и следующее действие;
- `run_quality_gate(packet, policy)` связывает шаги и возвращает переносимый пакет результата.

## USE IT — где уместен ИИ

Детерминированные проверки нельзя заменять просьбой «посмотри, всё ли нормально».
Доступный AI-инструмент можно использовать в двух ограниченных ролях:

1. предложить недостающую проверку для твоей предметной области;
2. подготовить понятное человеку объяснение уже рассчитанных PASS/FAIL и anomaly signal.

Пример запроса:

```text
Ты помогаешь улучшить политику проверки аналитического отчёта.

Metric: paid_revenue — сумма оплаченной выручки.
Обязательный фильтр: status=paid.
Периоды: Q1 → Q2.
Уже проверяем: версию semantic contract, конечность чисел, полноту сегментов,
delta каждой строки, сверку вкладов, evidence path и историческую аномалию.

Предложи не более трёх дополнительных проверок.
Для каждой укажи:
- какую правдоподобную ошибку она ловит;
- какие данные ей нужны;
- должна ли ошибка вести к block или review;
- как проверить правило локальным кодом.

Не выдумывай доступные поля. Если данных недостаточно, так и напиши.
```

Затем примени знакомую рамку AI Fluency 4D:

- **Delegation:** отдай ИИ предложение новых проверок или объяснение уже вычисленных результатов, но не решение `publish / review / block`.
- **Description:** передай определение метрики, реальные поля пакета, существующую policy и формат ожидаемого предложения.
- **Discernment:** проверь, ловит ли правило правдоподобную ошибку и можно ли вычислить его только из доступных данных.
- **Diligence:** реализуй принятое правило локально, добавь failure-тест, версионируй policy и сохрани ответственность за выпуск.

API-ключ не требуется: используй любой уже доступный инструмент или пропусти этот
вариант. Обязательный результат доказывается локальными тестами.

`course-work/phase-5/phase-5-dossier.md`: там ты свяжешь пять собственных результатов,
сохранишь один успешный прогон, воспроизведёшь один FAIL с исправлением и ответишь на
вопросы рефлексии по результату фазы.

## Как этим уроком закрывается Фаза 5

После 5.5 результаты фазы связываются в один процесс:

```text
5.1  AnalysisPlan и проверяемый аналитический brief
 ↓
5.2  execution trace и карточка проверки исполнения
 ↓
5.3  semantic contract и разрешённый intent → SQL
 ↓
5.4  многошаговый BI trace и evidence path
 ↓
     build_validation_packet(trace, semantic, run metadata, history)
 ↓
5.5  validation packet → quality gate → release decision и проверенный отчёт
```

Это ещё не автономная production-система. Но теперь каждый переход оставляет объект,
который можно проверить, передать следующему шагу и воспроизвести без доверия к одной
уверенной фразе ИИ.

## Частые ошибки

- **Переписывать trace 5.4 в пакет вручную.** Так легко изменить status, потерять сегмент или приписать finding обязательный фильтр, которого в нём нет. Используй адаптер и передавай semantic contract, metadata и историю отдельными входами.
- **Проверять только финальное число.** Q2 может совпасть с `200`, а декомпозиция — не сходиться. Проверяй и результат, и путь.
- **Считать красивую сумму доказательством полноты.** Сначала сравни фактический набор сегментов с ожидаемым, затем сверяй их вклады.
- **Терять проваленные проверки при сборке отчёта.** Report bundle обязан содержать все PASS/FAIL, иначе решение нельзя перепроверить.
- **Называть аномалию ошибкой.** Необычное число может быть реальным событием. Аномалия ведёт к `review`, а не автоматически к исправлению данных.
- **Писать «аномалий нет» при короткой истории.** Недостаток данных — отдельный результат `insufficient_history`.
- **Включать текущую точку в baseline без осознанной причины.** Выброс изменит параметры, с которыми сравнивается, и может ослабить собственный сигнал.
- **Оставлять правила анонимными лямбдами.** Без стабильного ID, сообщения и evidence невозможно понять, что сломалось и как менялась политика.
- **Считать `publish` доказательством причины.** Gate проверяет локализацию изменения, а не гипотезы о запасах, цене, спросе или поведении клиентов.
- **Называть локальный скрипт агентом.** Здесь решение принимает явная policy. Возможность модели запрашивать функции появится только после изучения tool use.
- **Смешивать проверку и доставку.** Cron может повторить ошибочный процесс идеально по расписанию. Сначала нужен корректный единичный запуск.

## Что сознательно не входит в урок

- реальный MCP-коннектор и доступ к БД — Фаза 6;
- автономный выбор инструментов моделью — Фаза 7;
- cron, ретраи, доставка уведомлений и мониторинг job — Production-фаза;
- доказательство причинности — для него нужны дополнительные данные и дизайн проверки;
- сезонные модели, Isolation Forest и другие промышленные детекторы — факультативное углубление;
- универсальная политика качества: владелец каждой метрики должен определить свою.

## Переход в Фазу 6

Сейчас Python-код сам вызывает `validate_packet`, `detect_current_anomaly` и
`build_report`. Модель не может запросить эти функции и не управляет их исполнением.

В 6.1 мы разберём следующий механизм: модель возвращает структурированный `tool_call`,
локальный диспетчер проверяет аргументы и вызывает разрешённую функцию, а результат
возвращается модели как `tool_result`. Quality gate 5.5 станет хорошим примером
инструмента, но его policy и право блокировать выпуск останутся в детерминированном коде.

## Дополнительное чтение

Читать всё не требуется. Выбери одну ветку по своей следующей задаче: перенести
quality gate в готовый инструмент, глубже разобраться в аномалиях или увидеть более

**Перенести проверки урока в готовые инструменты**

- [Great Expectations — GX Core overview](https://docs.greatexpectations.io/docs/core/introduction/gx_overview/) — сопоставь `Expectation → Validation Result → Checkpoint/Action` с нашей цепочкой `check → decision → report`.
- [Pandera — DataFrame Schemas](https://pandera.readthedocs.io/en/latest/dataframe_schemas.html) — открой разделы про обязательные и строгие колонки, пользовательские checks и накопление нескольких ошибок; это развитие проверок структуры пакета, а не замена release policy.
- [Evidently — Data Summary](https://docs.evidentlyai.com/metrics/preset_data_summary) — посмотри, как сравнивать текущий набор с reference dataset, получать pass/fail-тесты качества и собирать отчёт для регулярного мониторинга.

**Разобраться в детекции аномалий и её ограничениях**

- [scikit-learn — Novelty and Outlier Detection](https://scikit-learn.org/stable/modules/outlier_detection.html) — начни с различия между поиском выбросов внутри обучающей выборки и проверкой новой точки относительно чистой истории: в уроке используется второй сценарий.
- [NIST — Detection of Outliers](https://itl.nist.gov/div898/handbook/eda/section3/eda35h.htm) — разбери, почему обычный z-score может быть ненадёжен на короткой истории и как несколько выбросов способны маскировать друг друга.

**Увидеть более широкую систему мониторинга данных**

- [O'Reilly — Data Quality Fundamentals, глава 4](https://www.oreilly.com/library/view/data-quality-fundamentals/9781098112035/ch04.html) — углубись в построение мониторинга и anomaly detection для data pipelines; полный текст может требовать доступа к книге.
- [Monte Carlo — Data Quality Anomaly Detection](https://montecarlo.ai/blog-data-quality-anomaly-detection-everything-you-need-to-know/) — дополнительный взгляд поставщика data-observability-платформы на различие правил, статистических мониторов и контроля пайплайна.
