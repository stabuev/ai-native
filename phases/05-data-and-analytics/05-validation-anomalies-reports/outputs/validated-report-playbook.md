# Артефакт: плейбук выпуска проверенного аналитического отчёта

Этот плейбук задаёт границу между завершённым BI-расследованием и публикацией его
результата. Он не заменяет код quality gate: код вычисляет проверки и решение, а документ
позволяет владельцу метрики, аналитику и ревьюеру согласовать правила.

## 1. Паспорт процесса

| Поле | Значение |
|---|---|
| Вход | validation packet, детерминированно собранный из результата `investigate()` 5.4 |
| Metric ID | `paid_revenue` |
| Определение | сумма оплаченной выручки |
| Unit | `RUB` |
| Semantic version | `1.1` |
| Обязательный фильтр | `status=paid` |
| Baseline → focus | `Q1 → Q2` |
| Контрольный focus | `Q2 = 200` |
| Допустимые решения | `publish`, `review`, `block` |
| Владелец policy | владелец метрики |
| Исполнитель | детерминированный `run_quality_gate(...)` |

## 2. Контракт входного пакета

Результат 5.4 и пакет 5.5 — разные контракты. Функция
`build_validation_packet(...)` переносит `status`, state, observations и finding из
trace; semantic contract добавляет единицу и обязательные фильтры; `run_id`, `as_of` и
сопоставимая история передаются отдельно. Адаптер не извлекает эти факты из финальной
формулировки расследования и не придумывает отсутствующие значения.

Обязательные поля:

```text
run_id
as_of
trace_status
semantic_version
metric_id
unit
baseline
focus
filters
totals
breakdowns
evidence_path
history
```

Пакет допускается к содержательным проверкам только после заполнения этих полей. Если
поле отсутствует, решение — `block`, а не попытка угадать значение.

## 3. Реестр жёстких проверок

| Check ID | Условие PASS | Что означает FAIL | Решение |
|---|---|---|---|
| `packet.required_fields` | все обязательные поля присутствуют | пакет нельзя воспроизвести | `block` |
| `trace.ready_for_review` | статус равен `ready_for_review` | расследование не завершено | `block` |
| `contract.semantic_version` | версия равна `1.1` | смысл метрики не совпадает | `block` |
| `contract.metric` | metric ID равен `paid_revenue` | проверяется другая метрика | `block` |
| `contract.periods` | периоды равны `Q1 → Q2` | сравниваются другие окна | `block` |
| `contract.required_filters` | фильтры равны `status=paid` | в расчёт попали другие строки | `block` |
| `totals.finite` | Q1 и Q2 — конечные числа | дальнейшая арифметика недостоверна | `block` |
| `totals.focus_control` | Q2 равен `200` | пакет расходится с контрольным итогом | `block` |
| `region.segments` | есть Москва, Питер и Казань без дублей | декомпозиция неполна | `block` |
| `region.row_arithmetic` | delta каждой строки равна Q2 − Q1 | строка противоречит сама себе | `block` |
| `region.reconciliation` | `−20 − 50 + 0 = −70` | вклады не объясняют общий delta | `block` |
| `product|region=Питер.segments` | есть Basic и Pro без дублей | детализация Питера неполна | `block` |
| `product|region=Питер.row_arithmetic` | delta каждой строки равна Q2 − Q1 | строка противоречит сама себе | `block` |
| `product|region=Питер.reconciliation` | `−10 − 40 = −50` | продукты не объясняют delta Питера | `block` |
| `evidence_path.supported` | каждый шаг найден в декомпозиции с тем же delta | вывод не подтверждён trace | `block` |
| `history.current_matches_focus` | последняя точка истории равна Q2 | anomaly detector проверяет другое число | `block` |

## 4. Контракт anomaly signal

История передаётся от старых точек к новой. Последняя точка — `current`; все предыдущие
сопоставимые точки — `baseline`.

```text
minimum_baseline_points = 5
z_threshold = 2.0
z = (current − mean(baseline)) / pstdev(baseline)
```

| Статус | Значение | Действие |
|---|---|---|
| `clear` | порог не пересечён | перейти к таблице выпуска |
| `review` | точка необычна либо отличается от постоянного baseline | передать человеку |
| `insufficient_history` | прошлых точек меньше пяти | не заявлять «аномалий нет», передать человеку |
| `invalid` | неверная форма, тип, `NaN` или бесконечность | блокировать пакет |

Аномалия не доказывает ошибку данных и не объясняет причину изменения.

## 5. Таблица решений

Применять сверху вниз:

| Приоритет | Условие | Решение |
|---:|---|---|
| 1 | есть хотя бы один FAIL жёсткой проверки | `block` |
| 2 | anomaly status = `invalid` | `block` |
| 3 | anomaly status = `review` | `review` |
| 4 | anomaly status = `insufficient_history` | `review` |
| 5 | все checks PASS и anomaly status = `clear` | `publish` |

Решение модели, формулировка отчёта или уверенность автора не могут переопределить эту
таблицу без новой версии policy.

## 6. Эталонная сверка

### Общий результат

```text
Q1 = 270
Q2 = 200
delta = 200 − 270 = −70
```

### Вклады регионов

| Регион | Q1 | Q2 | Delta |
|---|---:|---:|---:|
| Москва | 170 | 150 | −20 |
| Питер | 80 | 30 | −50 |
| Казань | 20 | 20 | 0 |
| **Сумма** | **270** | **200** | **−70** |

### Продукты внутри Питера

| Продукт | Q1 | Q2 | Delta |
|---|---:|---:|---:|
| Basic | 30 | 20 | −10 |
| Pro | 50 | 10 | −40 |
| **Питер** | **80** | **30** | **−50** |

### Evidence path

```text
paid_revenue: Q1 270 → Q2 200, delta −70
└── region=Питер, delta −50
    └── product=Pro, delta −40
```

Допустимый вывод:

> Снижение paid_revenue на 70 RUB в основном локализовано в Питере (−50 RUB), а внутри
> Питера — в продукте Pro (−40 RUB).

Недопустимый вывод:

> Выручка упала, потому что в Питере закончился продукт Pro.

Второй вывод требует данных о запасах и не подтверждается текущим пакетом.

## 7. Действие для каждого решения

### `publish`

1. Сохранить пакет входа, policy version, checks и anomaly result.
2. Выпустить только формулировку, поддержанную evidence path.
3. Не добавлять причинное объяснение без отдельной проверки.

### `review`

1. Не распространять отчёт автоматически.
2. Передать человеку весь пакет, а не только предупреждение.
3. Указать конкретный anomaly status и основание.
4. После решения человека сохранить его действие и повторить gate при изменении входа.

### `block`

1. Не публиковать бизнес-вывод.
2. Найти все FAIL по стабильным check IDs.
3. Исправить источник, пакет или расчёт.
4. Перезапустить полный gate; нельзя вручную заменить `block` на `publish` в Markdown.

## 8. Критерии приёмки одного запуска

- вход содержит `run_id` и `as_of`;
- версия semantic contract и обязательные фильтры совпадают с policy;
- все числовые значения конечны;
- ожидаемые сегменты присутствуют без дублей;
- delta каждой строки проверена отдельно;
- вклады сходятся на обоих уровнях;
- evidence path подтверждён наблюдениями;
- anomaly status отличается от жёсткого FAIL;
- недостаток истории не назван чистым результатом;
- отчёт содержит все PASS/FAIL и основание решения;
- вывод не превращает локализацию в причинное объяснение.
