# Досье завершения Фазы 5

Досье связывает пять результатов фазы в один проверяемый маршрут. Это не шестой урок и
не новый отчёт: здесь ты показываешь, что один вопрос, одна метрика и одна доказательная
цепочка действительно проходят через разные границы без скрытой подмены смысла.

Скопируй шаблон в:

```text
ai-native-work/course-work/phase-5/phase-5-dossier.md
```

Можно оставить синтетический сценарий `paid_revenue` из курса или использовать один
безопасный рабочий пример. Для рабочего примера не загружай данные во внешний сервис без
разрешения и не заполняй пробелы догадками.

| Поле | Значение |
|---|---|
| Бизнес-вопрос | |

Если эти поля различаются между уроками, сначала объясни и версионируй изменение. Не
исправляй старые артефакты задним числом так, будто перехода не было.

## 2. Пять доказательств

Укажи путь к своему файлу или сохранённому результату, а не к эталону на странице курса.

| Урок | Что приложить | Путь | Что проверил самостоятельно |
|---|---|---|---|
| 5.1 | `AnalysisPlan` и аналитический brief | | Вопрос, grain, фильтры, метрика, read / used / excluded и полный итог |
| 5.2 | Execution trace и карточка проверки | | Вход, код, среда, результат и решение `accept / reject / needs clarification` |
| 5.3 | Semantic contract, intent, SQL и params | | Metric ID, обязательный фильтр, read-only исполнение и сверка |
| 5.4 | Результат `investigate()` | | Каждый следующий action intent следует из observation; stop и evidence path сохранены |
| 5.5 | Validation packet и результат `run_quality_gate()` | | Все PASS/FAIL, anomaly status, решение и граница доказательств попали в report bundle |

## 3. Проверка интерфейсов между уроками

Заполни фактическими значениями из своих файлов.

| Передача | Что должно сохраниться | Фактическое доказательство |
|---|---|---|
| 5.1 → 5.2 | источник, grain, период, фильтры, метрика и ожидаемый итог | |
| 5.2 → 5.3 | принятый смысл расчёта, но новый исполнитель и новый контракт доступа | |
| 5.3 → 5.4 | Metric ID и обязательные фильтры; изменение semantic version объяснено | |
| 5.4 → 5.5 | `status`, периоды, observations, breakdowns и evidence path преобразованы адаптером | |
| 5.5 → 6.1 | функции gate остаются детерминированными; модели ещё не разрешено вызывать их | |

Для синтетического маршрута должны сохраниться контрольные значения:

```text
paid_revenue, status=paid, RUB
Q1 270 → Q2 200, delta −70
region=Питер, delta −50
product=Pro, delta −40
```

сопоставимой историей, затем вызови `run_quality_gate(...)`.

Приложи команду запуска и её фактический вывод. Досье не принимается по фразе «код
работает» без сохранённого решения и проверок.

## 5. Правдоподобный сбой и восстановление

Выбери один сбой:

- удали обязательный фильтр `status=paid`;
- удали один ожидаемый сегмент;
- измени delta строки так, чтобы она не равнялась `focus − baseline`;
- оборви расследование статусом `step_budget_exhausted`.

| Шаг | Запись |
|---|---|
| Что изменено | |
| Какой FAIL или stop ожидался | |
| Какой результат получен | |
| Почему выпуск заблокирован | |
| Что исправлено | |
| Результат повторного запуска | |

Не меняй Markdown-вердикт вручную. Исправь вход, trace или policy и повтори полный gate.

## 6. Рефлексия по результату фазы

Ответь своими словами:

1. Где в твоём маршруте ИИ предлагает решение, а где не имеет права принимать его?
2. Какое доказательство не позволяет перепутать успешное исполнение с корректным анализом?
3. Какое предположение оказалось самым опасным: grain, фильтр, источник, semantic version, полнота сегментов или история?
4. Что ещё потребуется для реального подключения к данным, но сознательно начинается только в Фазе 6?

## 7. Критерии готовности

- [ ] Один вопрос и Metric ID прослеживаются через все пять уроков.
- [ ] Изменение semantic contract с `1.0` на `1.1` объяснено, а не скрыто.
- [ ] Результат 5.4 превращён в пакет 5.5 функцией-адаптером.
- [ ] Сохранены validation packet, все PASS/FAIL, anomaly status и report bundle.
- [ ] Один реалистичный сбой воспроизведён, заблокирован и исправлен повторным запуском.
- [ ] Evidence path не назван доказательством причины.
- [ ] Ответы рефлексии разделяют роль модели, детерминированного кода и человека.
- [ ] Для следующей фазы ясно, какие функции можно будет оформить как tools, а какие policy нельзя отдавать модели.

Фаза завершена, если другой человек может пройти по этим доказательствам от исходного
вопроса до решения `publish / review / block`, воспроизвести хотя бы один запуск и
объяснить, почему решение следует из сохранённых проверок.
