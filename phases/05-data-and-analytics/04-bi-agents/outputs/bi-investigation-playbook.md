# Артефакт: плейбук проверяемого BI-расследования

Этот плейбук задаёт границы многошагового расследования: какие действия разрешены,
как наблюдение влияет на следующий шаг, когда агент обязан остановиться и что человек
получает для проверки.

## Паспорт

| Поле | Значение |
|---|---|
| Вопрос | Почему `paid_revenue` снизилась в Q2 относительно Q1? |
| Metric ID | `paid_revenue` |
| Определение | сумма оплаченной выручки; обязательный фильтр `status=paid` |
| Единица | RUB |
| Baseline / focus | Q1 / Q2 |
| Semantic contract | версия `1.1`, владелец `course-team` |
| Разрешённые измерения | сначала `region`, затем `product` |
| Бюджет | не более трёх исполненных intents |
| Выход | trace, статус остановки, evidence path для ревью |

Версия `1.1` сохраняет определение `paid_revenue` из 5.3 и добавляет разрешённое
измерение `product`. Агент не может самостоятельно придумать другую метрику, колонку
или порядок детализации.

## Что считается шагом

Каждый шаг содержит четыре части:

```text
policy_reason → intent → observation → решение о продолжении
```

- `policy_reason` — короткое проверяемое основание выбора действия;
- `intent` — структурированный запрос из разрешённого каталога;
- `observation` — результат доверенного исполнителя с версией контракта;
- решение — следующий intent либо явный `stop`.

Внутренние рассуждения модели не являются доказательством. В trace сохраняются только
решение, его краткое основание, исполненный intent и наблюдаемый результат.

## Каталог разрешённых действий

### `compare_periods`

Проверить исходную посылку вопроса.

```json
{
  "action": "compare_periods",
  "metric_id": "paid_revenue",
  "baseline": "Q1",
  "focus": "Q2",
  "group_by": null,
  "filters": {},
  "semantic_version": "1.1"
}
```

### `breakdown_delta`

Разложить изменение текущего среза по одному разрешённому измерению.

```json
{
  "action": "breakdown_delta",
  "metric_id": "paid_revenue",
  "baseline": "Q1",
  "focus": "Q2",
  "group_by": "product",
  "filters": {"region": "Питер"},
  "semantic_version": "1.1"
}
```

Свободный SQL, неизвестные Metric ID и Dimension ID, смена версии контракта и
неограниченное число шагов запрещены.

## Таблица решений policy

| Наблюдение | Решение |
|---|---|
| Trace пуст | выполнить `compare_periods` |
| `delta >= 0` | `premise_not_supported`: падение не подтверждено |
| `delta < 0`, доступен `region` | разложить изменение по регионам |
| Сумма вкладов сегментов не равна изменению среза | `observation_mismatch` |
| Сегменты отсутствуют | `insufficient_data` |
| Найден крупнейший отрицательный вклад и доступно следующее измерение | зафиксировать сегмент фильтром и продолжить |
| Все разрешённые измерения пройдены | `ready_for_review` |
| Следующий запрос превысит бюджет | `step_budget_exhausted` |

## Эталонный trace

### Шаг 1. Существовало ли падение

| Период | `paid_revenue` |
|---|---:|
| Q1 | 270 |
| Q2 | 200 |
| Изменение | **−70** |

Q2 равен проверенному итогу предыдущих уроков: `150 + 30 + 20 = 200`. Значение
Q1 = 270 — новый baseline сценария, а не ошибочный Q2 без фильтра `status=paid`.

### Шаг 2. Кто дал отрицательный вклад

| Регион | Q1 | Q2 | Изменение |
|---|---:|---:|---:|
| Москва | 170 | 150 | −20 |
| Питер | 80 | 30 | **−50** |
| Казань | 20 | 20 | 0 |
| **Итого** | **270** | **200** | **−70** |

Москва остаётся крупнейшим регионом в Q2, но основной отрицательный вклад дал Питер.
Policy поэтому выбирает Питер, а не максимум текущего периода.

### Шаг 3. Что произошло внутри Питера

| Продукт | Q1 | Q2 | Изменение |
|---|---:|---:|---:|
| Basic | 30 | 20 | −10 |
| Pro | 50 | 10 | **−40** |
| **Питер целиком** | **80** | **30** | **−50** |

## Evidence path

```text
paid_revenue: Q1 270 → Q2 200, delta −70
└── region=Питер, delta −50
    └── product=Pro, delta −40
```

Допустимый вывод:

> Падение оплаченной выручки на 70 RUB в основном локализовано в Питере
> (−50 RUB), а внутри Питера — в продукте Pro (−40 RUB).

Недопустимый вывод:

> Выручка упала, потому что в Питере закончился продукт Pro.

Второе утверждение называет причину, которой нет в наблюдениях. Для неё понадобятся
данные об остатках, ценах, клиентах или другом возможном механизме.

## Передача в 5.5

Сохрани полный результат `investigate()` как `investigation-result.json`. В 5.5
детерминированный адаптер перенесёт из него status, state, observations и finding в
validation packet; semantic contract, `run_id`, `as_of` и сопоставимая история будут
явными отдельными входами.

Quality gate следующего урока должен проверить:

1. сходится ли Q2 с контрольным итогом `200`;
2. сходятся ли `−20 − 50 + 0 = −70`;
3. сходятся ли `−10 − 40 = −50` внутри Питера;
4. нет ли пропущенных сегментов и аномальных значений;
5. можно ли публиковать локализацию падения без неподтверждённой причинной формулировки.

## Критерии приёмки плейбука

- вопрос, metric ID, периоды и версия контракта указаны явно;
- каждый intent принадлежит разрешённому каталогу;
- следующий шаг действительно зависит от observation;
- есть бюджет и безопасные stop conditions;
- trace позволяет воспроизвести путь без догадок;
- вклады на каждом уровне сходятся с родительским изменением;
- evidence path отделён от гипотезы о причине;
- результат сохранён в форме, которую адаптер может передать в автоматическую валидацию 5.5.
