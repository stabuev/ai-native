Урок 5.3 · NL→SQL и семантический слой

Фаза 5 — Данные и аналитика · Результат фазы: анализировать данные с ИИ, превращать вопросы на естественном языке в SQL-запросы и делать автоотчёты с валидацией результатов.

Результат урока: после урока студент сможет преобразовать аналитический вопрос в проверяемое структурированное намерение (intent), получить из согласованных бизнес-определений запрос только для чтения (SELECT) с отдельно переданными значениями, исполнить его на учебной БД и принять либо отклонить результат по intent, SQL, параметрам и сверке с AnalysisPlan.

Опоры: в 5.1 ты зафиксировал grain, фильтры, метрику и ожидаемый итог; в 5.2 отделил модель, код, исполнителя и решение человека. · Дальше: в 5.4 один проверяемый запрос превратится в последовательность шагов BI-расследования.

Requires: для обязательной практики нужны только Python 3 и его стандартная библиотека sqlite3; API-ключ, сеть, установленный pytest и клонирование курса не нужны. Для USE IT подойдёт любой доступный AI-инструмент, но при его отсутствии можно использовать готовые intents из урока.

Главная мысль. Модель переводит вопрос в ограниченный intent. Проверенный код переводит intent в SQL. База исполняет SQL в режиме только для чтения. Человек сверяет смысл и результат. Ни один слой не заменяет остальные.

Новая проблема: тот же расчёт, другой исполнитель

В 5.1–5.2 мы отвечали на вопрос:

Какие регионы принесли больше оплаченной выручки в Q2?

И работали с шестью заказами:

order_idquarterregionstatusamount
o-1Q2Москваpaid100
o-2Q2Москваpaid50
o-3Q2Питерpaid30
o-4Q2Питерrefunded70
o-5Q2Казаньpaid20
o-6Q1Москваpaid999

Утверждённый AnalysisPlan требует:

Источник: sales.
Grain: одна строка = один заказ.
Период: quarter = Q2.
Метрика: paid_revenue = SUM(amount), RUB.
Обязательный фильтр метрики: status = paid.
Разрез: region.
Ожидаемо: Москва=150, Питер=30, Казань=20; полный итог=200.

Теперь данные лежат не в переданном модели CSV, а в базе данных. Модель больше не должна сама загружать файл и считать строки: она предлагает запрос, а база выполняет его.

Появляется знакомый по 5.2 риск:

SELECT region, SUM(amount)
FROM sales
WHERE quarter = 'Q2'
GROUP BY region

Этот запрос корректен как программа и успешно исполнится. Но он забыл status = 'paid', поэтому вернёт Питер 100 и полный итог 270. Работающий SQL не равен правильному анализу.

База данных и SQL обычными словами

База, таблица, строка и колонка

База данных хранит данные и исполняет запросы к ним. В учебной базе есть одна таблица sales, похожая на лист электронной таблицы:

  • строка — один заказ;
  • колонка — одно свойство заказа, например region или status;
  • имя таблицы и набор колонок образуют минимальную схему, то есть описание доступной структуры.

Схема отвечает на вопрос «какие данные технически существуют», но не определяет бизнес-смысл. Колонка amount ещё не говорит, считать ли возвраты выручкой.

Что такое SQL

SQL — язык запросов к базе данных. В этом уроке нужен только один безопасный для чтения тип запроса — SELECT.

SELECT region, SUM(amount) AS paid_revenue
FROM sales
WHERE quarter = ? AND status = ?
GROUP BY region
ORDER BY region

Прочитаем его сверху вниз:

ЧастьОбычными словами
SELECT region, SUM(amount)вернуть регион и сумму amount
AS paid_revenueназвать вычисленную колонку paid_revenue
FROM salesчитать таблицу sales
WHERE ...оставить только строки, прошедшие фильтры
GROUP BY regionсобрать отдельную сумму для каждого региона
ORDER BY regionвернуть группы в стабильном порядке

Знаки ? — места для параметров. Текст SQL и значения передаются базе отдельно:

SQL:    ... WHERE quarter = ? AND status = ?
params: ("Q2", "paid")

Так значение остаётся данными и не может дописать свою SQL-команду. Имена таблиц, колонок и выражения нельзя параметризовать тем же способом, поэтому они должны приходить только из проверенного списка.

Почему одного промпта со схемой недостаточно

Схема позволяет модели увидеть, что в sales существуют quarter, region, status и amount. Но схема не отвечает:

  • означает ли «выручка» все заказы или только оплаченные;
  • в какой валюте измеряется amount;
  • можно ли группировать по региону;
  • какой период обязателен;
  • кто согласовал определение;
  • как проверить изменение определения.

Если каждый раз писать модели «придумай SQL», она снова принимает эти решения. Даже одинаково звучащие вопросы могут получить разные фильтры.

Нужен дополнительный договор о смысле — семантический контракт.

Минимальный семантический контракт

Промышленные semantic layers могут описывать связи между таблицами, временные измерения, права и много типов метрик. В этом уроке строится только необходимый минимум:

SEMANTIC = {
    "version": "1.0",
    "owner": "course-team",
    "table": "sales",
    "grain": "одна строка = один заказ",
    "metrics": {
        "paid_revenue": {
            "expression": "SUM(amount)",
            "unit": "RUB",
            "required_filters": {"status": "paid"},
        }
    },
    "dimensions": {
        "region": {"column": "region"},
        "quarter": {"column": "quarter"},
    },
    "filters": {
        "quarter": {"column": "quarter"},
        "status": {"column": "status"},
    },
}

ID — устойчивое техническое имя объекта в контракте. Например, paid_revenue является Metric ID, а region — Dimension ID. Пользователь может формулировать вопрос разными словами, но модель должна выбрать одно из известных IDs либо запросить уточнение.

Метрика — не просто колонка

Метрика — согласованный способ получить число. Для paid_revenue нужны сразу три части:

агрегат: SUM
колонка: amount
обязательный фильтр: status = paid

Если оставить только SUM(amount), смысл изменится. Поэтому обязательный фильтр хранится рядом с выражением метрики и добавляется компилятором автоматически.

Измерение — допустимый разрез

Измерение отвечает на вопрос «по чему разбить число». region позволяет получить отдельную выручку по каждому региону, а quarter — по каждому кварталу.

Наличие колонки в таблице не означает, что модель автоматически получает право использовать её как измерение. Список разрешённых измерений является частью контракта.

Единое — не значит вечное

Семантический слой не высечен в камне. Определения меняются, поэтому им нужны область применения, владелец и версия.

Если компания различает валовую, оплаченную и чистую выручку, нужно создать три явно названные метрики. Общее слово «выручка» остаётся неоднозначным и требует уточнения.

Intent: промежуточный договор с моделью

Intent, или намерение запроса, — структурированная запись того, как понят пользовательский вопрос:

{
  "metric": "paid_revenue",
  "dimensions": ["region"],
  "filters": {
    "quarter": "Q2"
  }
}

Intent нужен, чтобы не прятать смысл внутри длинной SQL-строки:

  • человек видит выбранную метрику;
  • компилятор проверяет IDs по контракту;
  • обязательный status = paid не зависит от памяти модели;
  • неизвестное измерение приводит к ошибке;
  • один intent можно скомпилировать под нужный SQL-диалект позже.

В этом уроке человек или LLM предлагает intent. Детерминированный код проверяет и компилирует его. Мы сознательно не строим собственный NLP-парсер по подстрокам: русская морфология — отдельная задача и не должна определять надёжность аналитики.

Полный путь от вопроса до решения

вопрос
  ↓
модель или человек предлагает intent
  ↓
контракт проверяет metric / dimensions / filters
  ↓
компилятор добавляет обязательные фильтры и создаёт SQL + params
  ↓
read-only исполнитель запускает SELECT
  ↓
человек сверяет SQL, параметры, группы и полный итог
  ↓
accept / reject / needs clarification

Разберём каждую границу.

1. Модель предлагает, но не исполняет

Для ясного вопроса ожидаем:

Вопрос: оплаченная выручка по регионам в Q2
Intent: paid_revenue × region; quarter=Q2

Для вопроса «выручка по регионам» надёжный ответ может быть needs clarification: не указаны вид выручки и период.

2. Компилятор проверяет IDs

compile_query(intent) разрешает только:

  • существующую метрику;
  • существующие измерения;
  • существующие фильтры;
  • простые значения фильтров;
  • поля intent из известного контракта.

Если модель предлагает dimensions=["manager"], компилятор не ищет похожую колонку и не удаляет разрез молча. Он останавливается.

3. Компилятор добавляет смысл метрики

Intent содержит период Q2, но не повторяет status=paid: этот фильтр уже принадлежит paid_revenue.

requested filters: quarter=Q2
required filters:  status=paid
effective filters: quarter=Q2 AND status=paid

Если intent явно требует status=refunded для paid_revenue, это не альтернативная формулировка, а конфликт смысла. Запрос отклоняется.

4. Значения становятся параметрами

Компилятор возвращает:

sql:
SELECT region, SUM(amount) AS paid_revenue
FROM sales
WHERE quarter = ? AND status = ?
GROUP BY region
ORDER BY region

params:
("Q2", "paid")

Строка вроде Q2' OR 1=1 -- останется одним значением параметра. Она не превратится в продолжение запроса.

5. Исполнитель получает минимальные полномочия

Учебный run_read_only():

  1. создаёт временную SQLite только с синтетическими данными;
  2. загружает шесть известных строк;
  3. включает PRAGMA query_only = ON;
  4. разрешает один SELECT;
  5. возвращает именованные строки результата.

Это демонстрация принципа минимальных полномочий: исполнитель получает только те возможности, которые нужны задаче. В рабочей БД query_only из учебной SQLite не заменяет отдельную read-only роль, разрешённые схемы, timeout, row limit, cost limit и журнал доступа.

6. Человек сверяет результат

Исполнение возвращает:

Казань  → 20
Москва  → 150
Питер   → 30

До запуска из 5.1–5.2 уже известен ожидаемый полный итог:

20 + 150 + 30 = 200 RUB

reconcile_total() подтверждает:

{
  "expected_total": 200.0,
  "actual_total": 200.0,
  "matches": true
}

Совпадение не доказывает всё автоматически. Для решения accept также нужны правильный источник, версия semantic contract, параметры и допустимые права исполнителя.

Три решения вместо слепого запуска

СитуацияРешениеСледующий шаг
Intent, контракт, SQL, параметры и сверка согласованыacceptСохранить доказательства запуска
Пропущен обязательный фильтр или итог не сходитсяrejectИсправить причину и повторить
Неясна метрика, период или неизвестно измерениеneeds clarificationЗадать один конкретный вопрос

needs clarification — не ошибка процесса. Это корректный результат, когда бизнес-вопрос ещё нельзя однозначно превратить в запрос.

Перед реализацией

Не запускай тесты сразу. Сначала письменно предскажи:

  1. Какой фильтр должен появиться, хотя его нет в intent?
  2. Какие параметры получит SQLite?
  3. Почему возврат 70 не попадёт в Питер?
  4. Каким будет полный итог?
  5. Что должно произойти с dimensions=["manager"]?

Ожидаемая модель: status=paid; параметры ("Q2", "paid"); возврат исключён фильтром; итог 200; неизвестное измерение отклонено.

Реализуй три функции и демонстрацию

  • compile_query(intent, semantic) проверяет структуру, разрешённые IDs и конфликт обязательных фильтров, затем возвращает SQL и params.
  • run_read_only(compiled, rows) исполняет один SELECT на учебной SQLite в режиме query_only.
  • reconcile_total(compiled, result, expected_total) складывает группы и сравнивает их с ожидаемым итогом.
  • Демонстрация в __main__ показывает intent, SQL, params, результат и сверку.

Проверь поведение

Из каталога nl-to-sql/ запусти:

python3 -m unittest discover -s code -p 'test_*.py' -v
python3 code/nl_to_sql.py

Десять тестов проверяют:

  • автоматическое добавление status=paid;
  • точный результат 150 / 30 / 20 и итог 200;
  • запрет переопределить обязательный фильтр;
  • отказ для неизвестных метрики, измерения и фильтра;
  • отказ принимать объект вместо строкового ID измерения;
  • отделение подозрительного значения от SQL-текста;
  • отказ исполнять UPDATE;
  • правильный общий итог без группировки.

После зелёного прогона объясни своими словами, почему тест на UPDATE и параметризацию не делает этот учебный модуль полноценной защитой производственной базы.

USE IT

Используй любой доступный AI-инструмент только для перевода естественного языка в intent. Загружать рабочие данные и давать модели доступ к БД для этой практики не нужно.

Шаг 1. Передай контракт, а не данные

Ты переводишь аналитический вопрос в intent, но не пишешь и не исполняешь SQL.

Разрешено:
- metrics: paid_revenue, paid_orders;
- dimensions: region, quarter;
- filters: quarter, status;
- paid_revenue и paid_orders всегда требуют status=paid.

Если метрика, период или измерение неоднозначны либо отсутствуют в контракте,
верни status="needs_clarification" и один конкретный question.

Иначе верни только JSON:
{
  "status": "ready",
  "intent": {
    "metric": "...",
    "dimensions": ["..."],
    "filters": {"...": "..."}
  }
}

Шаг 2. Проверь три вопроса

  1. «Покажи оплаченную выручку по регионам в Q2».
  2. «Покажи выручку по регионам».
  3. «Покажи оплаченную выручку по менеджерам в Q2».

Сильный процесс:

  • для первого возвращает ready и допустимый intent;
  • для второго уточняет вид выручки и период;
  • для третьего не выдумывает manager, а сообщает, что измерение отсутствует.

Шаг 3. Компилируй локально

Передай в compile_query() только intent со статусом ready. Если инструмент вернул сырой SQL, не исполняй его: сначала восстанови и проверь metric, dimensions и filters либо повтори запрос к модели.

Реалистичные ошибки

  • Считать метрикой одно SQL-выражение. SUM(amount) без status=paid считает другой набор строк.
  • Позволить модели вернуть произвольный SQL и сразу его исполнить. Между языком и БД должна быть проверяемая граница.
  • Вставлять значения в SQL через форматирование строк. Значения должны передаваться параметрами.
  • Разрешить любую колонку из схемы. Технически существующая колонка ещё не является согласованным измерением.
  • Молча выбрать метрику для слова «выручка». Несколько допустимых определений требуют уточнения.
  • Считать semantic contract вечным. Определениям нужны владелец, область и версия.
  • Считать совпавший итог достаточным. Ещё проверяются источник, параметры, версия контракта и полномочия исполнителя.
  • Назвать SQLite query_only полной защитой. Это учебная иллюстрация; производственная БД применяет собственные роли и лимиты.
  • Проверить только счастливый путь. Надёжность видна по отказу для неизвестных и конфликтующих intents.

Что сознательно осталось за границей

  • Полный курс SQL: соединения таблиц, оконные функции, вложенные запросы и оптимизация.
  • Самостоятельное распознавание русского естественного языка.
  • Производственный SQL-парсер и доказательство безопасности произвольного запроса.
  • Настройка dbt Semantic Layer, Cube или другого конкретного продукта.
  • Диалекты конкретных БД и автоматическое переписывание SQL между ними.
  • Аутентификация, сетевые политики и администрирование производственной БД.
  • Оценивание качества NL→SQL на Spider, BIRD и других бенчмарках.
  • Многошаговое расследование и выбор следующего запроса: это 5.4.
  • Полная валидация аналитических результатов и аномалий: это 5.5.

→ изучить результат
→ выбрать следующий intent или явно остановиться

Semantic contract остаётся границей каждого шага: агент может выбирать согласованные metric IDs и dimensions, но не должен заново изобретать смысл выручки. Артефакт этого урока становится входом для сценария BI-расследования, а каждый исполненный intent — частью проверяемого trace.

ПРОВЕРЬ СЕБЯ

Вопросы проверяют обязательные фильтры метрик, отказ от неизвестных измерений, параметризацию, минимальные полномочия, сверку результата и корректную работу с неоднозначностью.

code/nl_to_sql.pyПоказать решение
"""Минимальный semantic contract и детерминированный intent→SQL-компилятор.

Естественный язык здесь намеренно не разбирается самодельными правилами. Модель или
человек предлагают структурированный intent, а этот модуль проверяет его по разрешённым
метрикам, измерениям и фильтрам, компилирует SQL и исполняет его на учебной SQLite.
"""

from __future__ import annotations

import sqlite3
from collections.abc import Mapping, Sequence
from typing import Any


SEMANTIC = {
    "version": "1.0",
    "owner": "course-team",
    "table": "sales",
    "grain": "одна строка = один заказ",
    "metrics": {
        "paid_revenue": {
            "label": "Оплаченная выручка",
            "expression": "SUM(amount)",
            "unit": "RUB",
            "required_filters": {"status": "paid"},
        },
        "paid_orders": {
            "label": "Число оплаченных заказов",
            "expression": "COUNT(*)",
            "unit": "orders",
            "required_filters": {"status": "paid"},
        },
    },
    "dimensions": {
        "region": {"label": "Регион", "column": "region"},
        "quarter": {"label": "Квартал", "column": "quarter"},
    },
    "filters": {
        "quarter": {"column": "quarter"},
        "status": {"column": "status"},
    },
}


DEMO_ROWS = [
    ("o-1", "Q2", "Москва", "paid", 100.0),
    ("o-2", "Q2", "Москва", "paid", 50.0),
    ("o-3", "Q2", "Питер", "paid", 30.0),
    ("o-4", "Q2", "Питер", "refunded", 70.0),
    ("o-5", "Q2", "Казань", "paid", 20.0),
    ("o-6", "Q1", "Москва", "paid", 999.0),
]


def compile_query(
    intent: Mapping[str, Any],
    semantic: Mapping[str, Any] = SEMANTIC,
) -> dict[str, Any]:
    """Проверить intent и собрать SELECT с параметрами.

    Ожидаемая форма:
    {
        "metric": "paid_revenue",
        "dimensions": ["region"],
        "filters": {"quarter": "Q2"},
    }
    """

    if not isinstance(intent, Mapping):
        raise ValueError("intent должен быть объектом")

    allowed_fields = {"metric", "dimensions", "filters"}
    unknown_fields = set(intent) - allowed_fields
    if unknown_fields:
        names = ", ".join(sorted(unknown_fields))
        raise ValueError(f"неизвестные поля intent: {names}")

    metric_id = intent.get("metric")
    metric_spec = semantic["metrics"].get(metric_id)
    if metric_spec is None:
        raise ValueError(f"неизвестная метрика: {metric_id!r}")

    dimension_ids = intent.get("dimensions", [])
    if (
        not isinstance(dimension_ids, Sequence)
        or isinstance(dimension_ids, (str, bytes))
    ):
        raise ValueError("dimensions должен быть списком")
    if any(not isinstance(dimension_id, str) for dimension_id in dimension_ids):
        raise ValueError("каждое измерение должно быть строковым ID")
    if len(set(dimension_ids)) != len(dimension_ids):
        raise ValueError("dimensions не должен содержать повторы")

    dimension_columns = []
    for dimension_id in dimension_ids:
        dimension_spec = semantic["dimensions"].get(dimension_id)
        if dimension_spec is None:
            raise ValueError(f"неизвестное измерение: {dimension_id!r}")
        dimension_columns.append(dimension_spec["column"])

    requested_filters = intent.get("filters", {})
    if not isinstance(requested_filters, Mapping):
        raise ValueError("filters должен быть объектом")

    effective_filters = dict(metric_spec.get("required_filters", {}))
    for filter_id, value in requested_filters.items():
        if filter_id not in semantic["filters"]:
            raise ValueError(f"неизвестный фильтр: {filter_id!r}")
        if filter_id in effective_filters and effective_filters[filter_id] != value:
            required = effective_filters[filter_id]
            raise ValueError(
                f"метрика {metric_id!r} требует {filter_id}={required!r}"
            )
        if not isinstance(value, (str, int, float)):
            raise ValueError(f"неподдерживаемое значение фильтра: {filter_id!r}")
        effective_filters[filter_id] = value

    select_parts = [
        *dimension_columns,
        f'{metric_spec["expression"]} AS {metric_id}',
    ]
    sql = f'SELECT {", ".join(select_parts)} FROM {semantic["table"]}'

    clauses = []
    params = []
    for filter_id, filter_spec in semantic["filters"].items():
        if filter_id in effective_filters:
            clauses.append(f'{filter_spec["column"]} = ?')
            params.append(effective_filters[filter_id])
    if clauses:
        sql += " WHERE " + " AND ".join(clauses)
    if dimension_columns:
        joined = ", ".join(dimension_columns)
        sql += f" GROUP BY {joined} ORDER BY {joined}"

    return {
        "sql": sql,
        "params": tuple(params),
        "metric": metric_id,
        "dimensions": list(dimension_ids),
        "filters": effective_filters,
        "unit": metric_spec["unit"],
        "semantic_version": semantic["version"],
    }


def run_read_only(
    compiled: Mapping[str, Any],
    rows: Sequence[tuple[Any, ...]] = DEMO_ROWS,
) -> list[dict[str, Any]]:
    """Исполнить один SELECT на учебной SQLite и вернуть именованные строки."""

    sql = str(compiled.get("sql", "")).strip()
    if not sql.upper().startswith("SELECT ") or ";" in sql:
        raise ValueError("разрешён только один SELECT без точки с запятой")

    connection = sqlite3.connect(":memory:")
    try:
        connection.execute(
            """
            CREATE TABLE sales (
                order_id TEXT PRIMARY KEY,
                quarter TEXT NOT NULL,
                region TEXT NOT NULL,
                status TEXT NOT NULL,
                amount REAL NOT NULL
            )
            """
        )
        connection.executemany(
            "INSERT INTO sales VALUES (?, ?, ?, ?, ?)",
            rows,
        )
        connection.execute("PRAGMA query_only = ON")
        cursor = connection.execute(sql, tuple(compiled.get("params", ())))
        columns = [item[0] for item in cursor.description]
        return [dict(zip(columns, row, strict=True)) for row in cursor.fetchall()]
    finally:
        connection.close()


def reconcile_total(
    compiled: Mapping[str, Any],
    result: Sequence[Mapping[str, Any]],
    expected_total: float,
) -> dict[str, Any]:
    """Сверить сумму групп с заранее ожидаемым полным итогом."""

    metric_id = compiled["metric"]
    actual_total = sum(float(row[metric_id]) for row in result)
    return {
        "metric": metric_id,
        "expected_total": float(expected_total),
        "actual_total": actual_total,
        "matches": abs(actual_total - float(expected_total)) < 1e-9,
    }


if __name__ == "__main__":
    demo_intent = {
        "metric": "paid_revenue",
        "dimensions": ["region"],
        "filters": {"quarter": "Q2"},
    }
    demo_query = compile_query(demo_intent)
    demo_result = run_read_only(demo_query)
    demo_check = reconcile_total(demo_query, demo_result, expected_total=200)

    print("intent:", demo_intent)
    print("semantic_version:", demo_query["semantic_version"])
    print("sql:", demo_query["sql"])
    print("params:", demo_query["params"])
    print("result:", demo_result)
    print("reconciliation:", demo_check)

# Артефакт: минимальный семантический контракт

Этот контракт связывает бизнес-вопрос с разрешёнными метриками, измерениями, фильтрами и проверочными примерами. Это учебный переносимый формат, а не конфигурация конкретного промышленного продукта.

## 1. Паспорт

| Поле | Значение |
|---|---|
| Область | Учебный анализ заказов |
| Статус | Approved for synthetic dataset |
| Версия | `1.0` |
| Владелец определения | Указать роль или человека |
| Дата проверки | Указать дату |
| Потребители | Intent→SQL-компилятор 5.3; сценарий BI-расследования 5.4 |

Изменение определения метрики создаёт новую версию контракта. «Единое определение» означает согласованное определение для указанной области и версии, а не неизменность навсегда.

## 2. Источник и grain

| Поле | Значение |
|---|---|
| Таблица | `sales` |
| Grain | Одна строка = один заказ |
| Row ID | `order_id` |
| Колонки | `order_id`, `quarter`, `region`, `status`, `amount` |
| Валюта | RUB |
| Допустимые статусы в синтетических данных | `paid`, `refunded` |
| Ограничение | Только синтетические данные урока |

```sql
CREATE TABLE sales (
    order_id TEXT PRIMARY KEY,
    quarter TEXT NOT NULL,
    region TEXT NOT NULL,
    status TEXT NOT NULL,
    amount REAL NOT NULL
)
```

## 3. Метрики

| Metric ID | Понятное имя | Определение | SQL-выражение | Обязательные фильтры | Единица |
|---|---|---|---|---|---|
| `paid_revenue` | Оплаченная выручка | Сумма `amount` только для оплаченных заказов | `SUM(amount)` | `status = paid` | RUB |
| `paid_orders` | Число оплаченных заказов | Число строк только с оплаченными заказами | `COUNT(*)` | `status = paid` | orders |

Общее слово «выручка» без контекста не назначается `paid_revenue` автоматически. Если в рабочей области существуют валовая, оплаченная и чистая выручка, вопрос требует уточнения.

## 4. Измерения и фильтры

| Dimension ID | Понятное имя | Колонка | Можно группировать | Можно фильтровать |
|---|---|---|---|---|
| `region` | Регион | `region` | Да | Нет в учебном компиляторе |
| `quarter` | Квартал | `quarter` | Да | Да |

| Filter ID | Колонка | Допустимый тип | Пример |
|---|---|---|---|
| `quarter` | `quarter` | Строка | `Q2` |
| `status` | `status` | Строка | `paid` |

Имена таблиц, колонок и SQL-выражения берутся только из проверенного контракта. Пользовательские значения фильтров передаются параметрами, а не вставляются в SQL-строку.

## 5. Контракт intent

```json
{
  "metric": "paid_revenue",
  "dimensions": ["region"],
  "filters": {
    "quarter": "Q2"
  }
}
```

- `metric` — один существующий Metric ID.
- `dimensions` — только разрешённые Dimension ID.
- `filters` — только разрешённые Filter ID и значения.
- Обязательные фильтры метрики добавляет компилятор; конфликт с ними отклоняется.
- Неизвестные поля, метрики, измерения и фильтры не угадываются.

## 6. Политика неоднозначности

| Вопрос | Решение | Почему |
|---|---|---|
| «Оплаченная выручка по регионам в Q2» | Компилировать `paid_revenue × region`, `quarter=Q2` | Метрика, разрез и период однозначны |
| «Выручка по регионам» | `needs clarification` | Не указано, какая именно выручка и за какой период |
| «Выручка по менеджерам» | `needs clarification` | Измерения `manager` нет в контракте |
| «Возвраты по регионам» | `needs clarification` | Метрика возвратов не определена |

Новую метрику или колонку сначала добавляет и проверяет владелец контракта. Модель не расширяет слой по собственной инициативе.

## 7. Контракт исполнения

| Граница | Учебное правило | Что проверить перед переносом |
|---|---|---|
| Запрос | Один `SELECT` без нескольких выражений | Разрешённые типы запросов и SQL-диалект |
| Источник | Только синтетическая таблица `sales` | Разрешённые схемы, представления и версии |
| Значения | Параметры `?`, отдельно от текста SQL | Способ параметризации драйвера БД |
| Права | SQLite `PRAGMA query_only = ON` после загрузки fixture | Отдельная read-only роль БД |
| Ресурсы | Шесть учебных строк | Timeout, row limit и cost limit |
| Доказательства | Intent, SQL, params, результат, сверка | Query ID, план запроса и журнал доступа |

Учебная SQLite показывает принцип минимальных полномочий, но не является моделью производственной безопасности. Для рабочей БД нужны её собственные роли, политики и ограничения.

## 8. Проверочные случаи

### Основной случай

```text
Вопрос: оплаченная выручка по регионам в Q2.
Intent: metric=paid_revenue; dimensions=[region]; filters={quarter: Q2}.
Обязательный фильтр контракта: status=paid.
Ожидаемый SQL: SELECT + WHERE quarter=? AND status=? + GROUP BY region.
Ожидаемые параметры: Q2, paid.
Ожидаемые группы: Москва=150, Питер=30, Казань=20.
Ожидаемый полный итог: 200 RUB.
Решение: accept, если источник, версия контракта и права подтверждены.
```

### Негативные случаи

- `metric=revenue` → отклонить как неизвестную метрику.
- `dimensions=[manager]` → запросить уточнение или согласованное расширение контракта.
- `status=refunded` для `paid_revenue` → отклонить конфликт с обязательным фильтром.
- SQL `UPDATE ...` → не исполнять.
- Группы не сходятся с полным итогом `200` → отклонить результат и диагностировать расхождение.

## 9. Приёмка и передача

Контракт готов к передаче, если другой человек может:

1. назвать grain и доступные поля источника;
2. объяснить смысл, единицу и обязательные фильтры каждой метрики;
3. отличить Metric ID от произвольной пользовательской формулировки;
4. получить SQL только из разрешённых частей;
