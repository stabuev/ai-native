Урок 3.2 · Длинные документы: от файла к проверяемому резюме

Фаза 3 — Текст и документы · Результат фазы: строить пайплайны резюмирования и редактуры; собрать базовый RAG над своим корпусом.

Результат урока: после урока студент сможет для извлечённого длинного документа и конкретной задачи выбрать между передачей целиком, многоуровневым резюмированием и поиском только нужных фрагментов; затем разрезать документ с сохранением источника, ограничить размер каждого шага сведения результатов и локализовать потерю или дублирование защищаемого факта.

Опора: бюджет контекста из 1.2, границы доверия из 1.4, внешняя цепочка и gates из 2.3, смысловые инварианты редакторского процесса из 3.1. · Дальше: в 3.3 retrieval — поиск релевантных фрагментов — будет работать с подготовленными здесь частями документа; их ID и происхождение позволят показать источник найденного текста.

Requires: обязательный Build It работает офлайн на Python 3 и pytest. Для содержательной практики достаточно одного разрешённого чата или агента из Фазы 0; если загрузка файлов недоступна, используй учебный Markdown из исходников урока. Платный API и клонирование репозитория не нужны.

Главная мысль. Длинный документ обрабатывают не по одному магическому рецепту. Сначала проверяют, что из файла извлечено, затем выбирают маршрут под задачу, а при сжатии сохраняют границы, происхождение и смысловые проверки на каждом уровне.

Ситуация: документ поместился — задача ещё не решена

Представь отчёт на 120 страниц. Руководителю нужен не любой короткий пересказ, а ответ на три вопроса:

  1. что уже решено;
  2. какое условие способно остановить запуск;
  3. какие вопросы всё ещё открыты.

Просьба «загрузи PDF и сократи» скрывает три независимых риска.

Первый риск — извлечение. PDF является контейнером, а не гарантированно правильной строкой текста. В нём могут находиться сканированные страницы, таблицы, подписи под диаграммами и колонки, которые обычный инструмент извлечения прочитает в неверном порядке.

Второй риск — контекст. Документ, инструкции, история диалога и будущий ответ делят одно контекстное окно. Даже если файл технически помещается, запрос может оказаться дорогим, медленным или плохо решать конкретную задачу. Размер окна зависит от точного идентификатора модели (model ID) и среды, поэтому число вроде «1M» нельзя считать свойством любого Claude, Gemini или другого семейства. Если интерфейс чата не раскрывает точный ID или лимит, это неизвестное нужно зафиксировать, а не заменять догадкой.

Третий риск — сжатие. Если длинный документ разбить и резюмировать по частям, сведение из одной части может исчезнуть до того, как модель увидит остальные. Следующий шаг не восстановит удалённое условие по памяти: у него есть только переданный вход.

Поэтому длина сама по себе не выбирает архитектуру. Нужно знать задачу, качество извлечения, бюджет и цену смысловой ошибки.

Сначала отдели файл от его содержимого

Файл — способ хранения и передачи. Извлечённое представление — текст, таблицы, изображения и метаданные, которые реально увидит следующий шаг.

Gate извлечения отвечает не на вопрос «файл открылся?», а на вопрос «представление достаточно верно для моей задачи?». Если в отчёте важна таблица со сроками, гладко извлечённые абзацы не компенсируют перемешанные строки таблицы.

В этом уроке мы не строим PDF-парсер, OCR и анализатор таблиц. Для Build It получаем уже извлечённый текст. Но в рабочем процессе обязательно сохраняем решение:

какой файл был на входе
→ каким способом получено представление
→ что проверено
→ что не извлечено и не должно интерпретироваться

Три маршрута обработки

После проверки извлечения выбери маршрут по требуемому действию.

Прямой контекст передаёт документ модели целиком. Иерархическое резюмирование сначала сжимает части, а затем сводит промежуточные результаты несколькими уровнями. Retrieval перед каждым ответом ищет только те фрагменты, которые относятся к текущему вопросу.

МаршрутКогда разуменГлавный рискЧто проверить
Прямой контекст — передать релевантный документ целикомнужен глобальный анализ, документ помещается с запасом, прогонов немного«помещается» ошибочно принято за «надёжно используется»бюджет и контрольные вопросы к началу, середине и концу
Иерархическое резюмирование — сжать части и сводить результаты уровняминужен обзор всего документа, а один запрос не подходит по бюджету или ценеранний уровень потерял редкое, но важное сведениеинварианты и происхождение после каждого уровня
Retrieval — на каждый вопрос находить только релевантные фрагментывопросов много, корпус велик, ответу нужны отдельные доказательстванужный фрагмент не найден и модель его не увиделакачество поиска, порог «ничего не найдено», ссылки на источник

Retrieval здесь означает выбор нужных частей перед ответом. Механизм поиска мы построим в 3.3. В этом уроке достаточно подготовить хорошие записи фрагментов и не выдавать retrieval за способ получить полный обзор всего документа.

Маршруты можно комбинировать, но только после ясного решения. Например, retrieval может найти разделы для конкретного вопроса, а короткое сведение — объединить найденные доказательства. Это не делает комбинацию обязательной для каждого файла.

Бюджет из 1.2

Перед прямой загрузкой или выбором размера фрагмента восстанови полный запрос:

системные и служебные инструкции
+ описание задачи и критерии
+ документ или пакет частичных результатов
+ история и метаданные
+ резерв под ответ
+ запас на ошибку оценки
≤ документированный лимит выбранной модели и среды

Не оценивай документ только по страницам или словам: изображения, таблицы и конкретный токенизатор меняют расход. Для меняющейся спецификации проверяй актуальную страницу выбранной модели и, если доступно, счётчик токенов провайдера.

Центральный механизм: chunk → map → reduce

Теперь введём термины в том порядке, в котором они нужны.

Chunk, или чанк, — ограниченный фрагмент извлечённого документа. Chunking — правило, по которому документ превращается в последовательность таких фрагментов.

Полезный чанк — не просто строка. Это запись:

{
  "id": "pilot-report#chunk-0003",
  "source": "pilot-report",
  "word_start": 21,
  "word_end": 31,
  "text": "..."
}

Поля source, id и позиции задают provenance, то есть происхождение результата: можно установить, из какого места документа пришёл фрагмент. Без provenance трудно проверить цитату, различить два похожих утверждения и передать чанк в retrieval.

Map применяет одну операцию независимо к каждому чанку. Для резюмирования это частичное резюме с теми же смысловыми инвариантами, что были в 3.1.

Reduce получает несколько частичных результатов и сводит их в один результат следующего уровня. Количество входов одного reduce-вызова называется fan-in.

извлечённый документ
        │ chunking
        ▼
 [c1] [c2] [c3] [c4] [c5] [c6]
        │ map + gate
        ▼
 [s1] [s2] [s3] [s4] [s5] [s6]
        │ reduce, fan-in = 3
        ▼
       [r1]           [r2]
        │ reduce + gate
        ▼
              [final]

При 64 частичных результатах и fan_in=4 уровни имеют размеры:

64 → 16 → 4 → 1

Каждый reduce получает не более четырёх входов. Именно поэтому схема является иерархической. Вариант «сжать 64 чанка, затем положить все 64 резюме в один финальный запрос» лишь переносит исходное переполнение на следующий шаг.

Ограниченный fan_in тоже не является полной гарантией бюджета: четыре огромных резюме всё ещё могут не поместиться. Контракт map и reduce должен задавать максимальный объём выхода, а собранный пакет нужно оценивать тем же способом, что любой другой промпт.

Что даёт overlap — и чего не даёт

В учебном Build It мы режем по словам. Пусть есть 25 слов w1…w25, size=10, overlap=3.

Overlap, или перекрытие, означает, что соседние чанки повторяют часть текста. Шаг между началами равен size − overlap = 7:

chunk 0 [0:10]   w1  … w10
chunk 1 [7:17]   w8  … w17
chunk 2 [14:24]  w15 … w24
chunk 3 [21:25]  w22 … w25

Позиции записаны как полуинтервал [start:end): начало входит, конец не входит. Так длина первого чанка равна 10 − 0 = 10, а следующий начинается с позиции 7.

Overlap снижает вероятность, что локальная фраза полностью исчезнет из-за одной случайной границы. Но он:

  • не гарантирует сохранение мысли длиннее overlap;
  • не восстанавливает структуру таблицы;
  • повторяет токены и увеличивает стоимость;
  • способен дважды пронести число или событие в reduce;
  • не заменяет проверку частичного резюме по источнику.

Поэтому правило не звучит как «overlap обязателен». Оно звучит так:

Выбери границу по структуре документа; добавляй overlap только против названного риска и заранее реши, как распознавать дубликаты.

В рабочем документе сначала полезно делить по разделам, абзацам, репликам или строкам таблицы, а ограничение в токенах использовать как второй рубеж. Word-based splitter в Build It нужен, чтобы руками увидеть арифметику границ и проверить код, а не как универсальная production-стратегия.

Почему проверка через set недостаточна

Проверка «множество слов в чанках равно множеству слов источника» пропускает ошибки:

источник:  A B B C
чанки:     C B A

Множества одинаковы, но порядок и одно повторение потеряны. Для word-based примера надёжнее реконструировать последовательность:

  1. взять все слова первого чанка;
  2. у каждого следующего отбросить ровно запланированный overlap;
  3. сравнить полученную последовательность с исходной.

Именно такую ошибку теперь ловят тесты Build It.

Смысловой контракт map и reduce

Структурное покрытие доказывает только то, что символы дошли до чанков. Оно не доказывает, что частичное или финальное резюме сохранило смысл.

Перенесём контракт стадии из 3.1.

Контракт map

Для каждого чанка задай:

  • цель частичного результата;
  • задачу и читателя всего документа, а не только тему чанка;
  • защищаемые числа, даты, отрицания, условия и статусы решений;
  • максимальный объём;
  • требование вернуть chunk_id;
  • gate: каждое существенное утверждение подтверждается этим чанком.

Если в чанке нет ответа на глобальный вопрос, корректный map может вернуть «сведений по этому вопросу нет». Он не должен дополнять картину догадкой.

Контракт reduce

Reduce получает частичные результаты и их chunk_ids. Для каждого пакета задай:

  • что объединяется и для какого решения;
  • какие инварианты должны пережить ещё одно сжатие;
  • как распознать сведения, повторённые из-за overlap;
  • максимальный объём выхода;
  • gate по входным частичным результатам;
  • правило остановки после fail.

Reduce не является исправителем map. Если условие исчезло в s2, следующий уровень не должен придумывать его заново. Нужно вернуться к исходному чанку, повторить только проваленный map и затем пересчитать зависимые reduce-пакеты.

Разбор: где исчезает условие запуска

Продолжим учебный сценарий 3.1. В длинном отчёте есть три удалённых друг от друга фрагмента:

chunk A, pilot-report#chunk-0001:
Пилот запускается 18 сентября для 10% пользователей iOS.

chunk B, pilot-report#chunk-0007:
Рита отправит схему до 12 сентября.
Если согласование не получено к 16 сентября, запуск переносится.

chunk C, pilot-report#chunk-0012:
Полный перевод обсуждали, но решения не приняли.
Ответственный за итоговый отчёт пока не назначен.

Задача — подготовить управленческий обзор. До map предскажи наиболее дорогой пропуск. Условие в chunk B встречается один раз и поэтому выглядит менее тематическим, чем повторяющиеся описания пилота.

Получились такие частичные результаты:

sA [chunk-0001]:
Пилот для 10% пользователей iOS запланирован на 18 сентября.

sB [chunk-0007]:
Рита отправит схему на согласование до 12 сентября.

sC [chunk-0012]:
Полный перевод ещё не утверждён; владелец итогового отчёта не назначен.

Все ответы гладкие, но sB провалил gate: исчезло точное условие переноса. Финальный reduce не получит исходный chunk B автоматически и не сможет надёжно восстановить 16 сентября.

Правильная диагностика:

map(chunk B) → fail
→ добавить условие и отрицание в инварианты map
→ повторить map только для chunk B
→ принять исправленное sB
→ пересчитать reduce-пакеты, которые зависели от sB

Увеличение overlap не исправляет уже потерянное при суммаризации сведение. Оно меняет границы входов; смысловой gate меняет правило приёмки результата.

BUILD IT: трассируемые чанки и ограниченный reduce

Задание: реализуй учебный пайплайн с разбиением по словам (word-based), который делает границы и происхождение чанков наблюдаемыми, отклоняет опасные параметры и сводит результаты несколькими ограниченными уровнями.

Работай в course-work/3.2/. Из «Исходников урока»:

  1. скопируй starter_chunking.py как course-work/3.2/chunking.py;
  2. скопируй рядом test_chunking.py;
  3. для содержательной практики скопируй sample_report.md;
  4. эталонный chunking.py до первой собственной попытки не открывай.

Используй только стандартную библиотеку Python.

1. chunk_text(text, size=100, overlap=20, source="document")

Функция должна:

  • принимать строку уже извлечённого текста;
  • требовать положительный целый size;
  • требовать целый overlap с контрактом 0 <= overlap < size;
  • для пустого текста возвращать [];
  • резать слова с шагом size − overlap;
  • возвращать записи с полями id, source, index, word_start, word_end, text;
  • использовать полуинтервальные позиции и стабильные ID вида report#chunk-0000;
  • не создавать пустой хвостовой чанк.

2. map_chunks(chunks, map_fn)

Для каждого чанка:

  • вызови map_fn(chunk["text"]);
  • отклони пустой или нестроковый результат;
  • верни запись с id, исходным chunk_ids, level=0 и text.

Код сохраняет происхождение, но не умеет доказать верность смысла: содержательный gate ты применишь в основной практике.

3. hierarchical_reduce(mapped, reduce_fn, fan_in=4)

Функция должна:

  • требовать целый fan_in >= 2;
  • объединять текущий уровень пакетами не больше fan_in;
  • по возможности распределять пакеты без одиночного хвоста, а неизбежную одиночную запись переносить на следующий уровень без вызова reduce_fn;
  • передавать reduce_fn список текстов одного пакета;
  • переносить в результат все исходные chunk_ids в порядке документа;
  • повторять уровни, пока не останется одна запись;
  • вернуть {"result": ..., "levels": [...]};
  • для пустого входа вернуть {"result": None, "levels": []} без вызова reduce_fn.

Подсказка для распределения без одиночного хвоста: сначала вычисли количество пакетов ceil(n / fan_in), затем распредели n элементов между ними максимально равномерно. Например, пять входов при fan_in=4 лучше разделить как 3 + 2, а не 4 + 1.

4. map_reduce(...)

Это небольшая композиция:

chunks → map_chunks → hierarchical_reduce

Она не должна возвращаться к одноуровневому reduce всех результатов.

Прогон red → green

python -m pytest course-work/3.2/test_chunking.py -q
python course-work/3.2/chunking.py

Готово, когда зелёны 9 тестов. Они проверяют:

  • точные позиции и overlap соседних чанков;
  • восстановление исходной последовательности, а не только множества слов;
  • отрицательный, слишком большой и нецелый overlap/size;
  • стабильные ID и provenance map-результатов;
  • запрет пустого частичного результата;
  • несколько уровней reduce;
  • ограничение размера каждого пакета;
  • сохранение всех chunk_ids;
  • пустой вход и невозможный fan_in=1.

После зелёного прогона объясни своими словами:

  1. почему overlap=-1 теряет данные, хотя цикл Python продолжает работать;
  2. почему set не доказывает сохранение порядка и повторов;
  3. почему ограниченный fan_in не отменяет лимит объёма каждого частичного резюме;
  4. какой смысловой сбой эти тесты принципиально не способны обнаружить.

Если ответы непонятны, зелёные тесты доказывают только прохождение известной спеки. Эталон и тесты-ТЗ доступны ниже в «Исходниках урока».

Основная практика: спроектируй маршрут длинного документа

Скопируй карточку обработки длинного документа в course-work/3.2/long-doc-pipeline.md.

Используй разрешённый рабочий документ или sample_report.md. Учебный файл намеренно короче production-отчёта: его можно проверить вручную и увидеть ошибку. Масштабирование в упражнении создаёт количество чанков и уровней, а не невозможность проверить источник.

Шаг 1. Зафиксируй задачу до выбора архитектуры

Назови читателя, решение и требуемую форму. Отличи:

  • полный обзор документа;
  • сравнение далёких разделов;
  • один конкретный вопрос;
  • серию повторяющихся вопросов по корпусу.

Для учебного отчёта задача: подготовить краткий статус пилота, сохранив принятое решение, gate запуска, метрики и открытые вопросы.

Шаг 2. Проверь извлечение

Для Markdown подтверди начало, конец и порядок заголовков. Если используешь реальный PDF или таблицу, отдельно проверь текстовый слой, строки, единицы, подписи и хотя бы по одному фрагменту из начала, середины и конца.

Зафиксируй неизвестное. Если схема на диаграмме не извлечена, не делай вывод о ней по соседнему абзацу.

Шаг 3. Выпиши инварианты

До генерации сохрани не менее пяти защищённых сведений. Для учебного отчёта обязательно рассмотри:

  • 18 сентября, 10%, iOS;
  • Рита отправляет схему до 12 сентября, но не принимает решение за безопасность;
  • нет согласования к 16 сентября → запуск переносится;
  • полный перевод обсуждался, но не утверждён;
  • две основные метрики;
  • неизвестный порог остановки и неназначенный владелец отчёта.

Шаг 4. Оцени бюджет и выбери маршрут

Для одного доступного инструмента запиши название продукта, показанное имя модели, дату и источник лимита. Для API укажи точный model ID; если чат его не раскрывает, отметь это как ограничение доказательства. Оцени полный запрос с резервом ответа. Затем обоснуй каждый вариант:

direct: подходит / не подходит, потому что…
hierarchical summary: подходит / не подходит, потому что…
retrieval: подходит / не подходит, потому что…

Для управленческого обзора учебного отчёта основной маршрут — иерархическое резюмирование: ответ должен учитывать все разделы. Для вопроса «кто отправляет схему и к какому сроку?» retrieval был бы естественнее, но сам поиск появится в 3.3.

Шаг 5. Предскажи сбой и проверь чанки

Выбери структуру, размер и overlap. До запуска назови:

  • какая связь может разорваться;
  • какой факт способен продублироваться;
  • где word-based граница хуже границы раздела.

Запусти свой chunk_text, просмотри минимум первый, средний и последний чанк, затем реконструируй исходную последовательность с учётом overlap. Для рабочего проекта добавь структурное деление до ограничения размера; переписывать учебный сплиттер в универсальный парсер не требуется.

Шаг 6. Выполни map с provenance

В разрешённом чате обработай чанки по одному либо используй доступный агент. В каждый запрос передавай:

  • общую задачу документа;
  • chunk_id;
  • текст чанка;
  • применимые инварианты;
  • форму и максимальный объём частичного результата;
  • право вернуть «в этом чанке нет сведений по задаче».

Сохрани сырой результат и chunk_id. Не принимай частичное резюме только потому, что оно короткое и гладкое.

Шаг 7. Выполни ограниченный reduce

Выбери fan_in по бюджету и зафиксируй входные ID каждого пакета. На каждом уровне проверяй:

  • все ли защищённые сведения из входных результатов пережили сжатие;
  • не превратилось ли обсуждение в решение;
  • не исчезло ли отрицание или условие;
  • не посчитан ли повтор из overlap дважды;
  • можно ли проследить итог до исходных chunk_ids.

Не продолжай после первого fail.

Шаг 8. Внеси одну дорогую мутацию

Удали условие 16 сентября из одного map-результата или продублируй сумму/событие из overlap. До запуска gate назови, где ошибка должна остановиться.

Если мутация прошла, усили проверку. Затем повтори только проблемный map или reduce-пакет и пересчитай зависящие от него уровни.

Шаг 9. Проверь перенос

Поменяй задачу, не меняя документ: вместо полного обзора задай один точный вопрос. Снова выбери маршрут. Успешный перенос — это не повторить map-reduce, а заметить, что другая задача может требовать direct context или retrieval.

Перенос в доступный инструмент

Если чат или API умеет принимать файлы, не начинай с копирования провайдерского сниппета:

  1. проверь актуальную поддержку конкретного формата и модели;
  2. используй только разрешённые данные;
  3. зафиксируй точный model ID или явно отметь, что интерфейс показывает только имя;
  4. проверь несколько мест извлечённого представления;
  5. сравни результат с заранее выписанными инвариантами;
  6. сохрани не только финал, но и решение о маршруте.

Для длинного промпта рекомендации расположения данных, тегов и вопроса зависят от провайдера и модели. Например, актуальная документация Anthropic советует размещать длинные данные до запроса и сохранять метаданные документов. Это полезная настройка выбранного инструмента, а не доказательство, что direct context всегда лучше иерархического процесса.

Что сознательно осталось за границей

  • Полный PDF-парсер, OCR и восстановление сложных таблиц — отдельные инженерные задачи.
  • Точный токенный splitter провайдера — адаптер поверх того же контракта границ.
  • Embeddings, индекс и оценка retrieval — уроки 3.3–3.5.
  • Универсальные значения size, overlap и fan_in не задаются: они зависят от документа, задачи, модели и измеренного риска.
  • Один успешный прогон не доказывает качество для любого файла; нужен перенос на новый документ или новый вопрос.

Типичные ошибки

  • Чанкить испорченное извлечение. Разбиение сохраняет ошибочный порядок, а не чинит его.
  • Выбирать маршрут только по длине. Короткому корпусу с множеством точечных вопросов может быть нужен retrieval, а длинному глобальному обзору — иерархическое сжатие.
  • Считать overlap гарантией смысла. Он лишь меняет границы и создаёт дубликаты.
  • Терять ID после map. Без происхождения невозможно доказать, откуда взялся вывод.
  • Делать один огромный reduce. Это исходная проблема на новом уровне.
  • Надеяться, что reduce восстановит пропуск map. Следующий шаг не видит удалённое сведение, если источник не передан заново.
  • Проверять только финал. Ошибка становится дорогой и её трудно локализовать.
  • Жёстко писать «окно 1M». Лимит и правила меняются между моделями и средами.
  • Отправлять внутренний файл в неутверждённый сервис. Дробление на чанки не делает данные менее чувствительными.

Проверь себя

Вопросы ниже проверяют выбор маршрута, опасную конфигурацию overlap, дублирование, иерархический reduce, gate извлечения и необратимую потерю сведения на map.

Дополнительное чтение

Не нужно читать всё до практики. Сначала выбери источник под границу, с которой столкнулся в своей карточке.

  • Anthropic — Context windows — для точного контракта открой How the context window works, таблицу размеров по моделям и Token counting; используй её вместо универсальной фразы «у Claude 1M».
  • Anthropic — Long context prompting — практическое продолжение direct context: расположение длинных данных, запросов и метаданных; проверяй рекомендации на выбранной модели.
  • Anthropic — PDF support — открой ограничения, различие текстового и визуального анализа и способы передачи PDF; сопоставь их со своим gate извлечения.
  • LangChain — Text splitters — после учебного word-based сплиттера сравни разбиение по символам, токенам и структуре; выбирай интеграцию только после формулировки риска границы.
  • Liu et al., 2024 — Lost in the Middle — первичное исследование позиционной чувствительности на long-context задачах; используй как источник failure mode и идеи теста, а не как универсальную гарантию поведения любой новой модели.
  • Hsieh et al., 2024 — RULER — факультативное углубление в измерение эффективного длинного контекста задачами сложнее простого needle-in-a-haystack.

Учебные данные

Этот безопасный пример можно использовать вместо рабочего файла.

code/sample_report.md
# Учебный отчёт о пилоте нового платёжного потока

## 1. Контекст и границы пилота

Команда готовит ограниченный пилот нового платёжного потока. Принято решение запустить
его 18 сентября для 10% пользователей iOS. Пользователи Android и веб-версии в этот
этап не входят. Цель пилота — проверить техническую стабильность потока и влияние на
обращения в поддержку до решения о дальнейшем расширении.

Объём 10% выбран как контролируемая стартовая группа. В обсуждении звучали варианты
5% и 20%, но они не были утверждены. Изменение размера пилота требует отдельного
решения владельца продукта после проверки готовности инфраструктуры.

## 2. Доступ и согласование безопасности

До запуска служба безопасности должна согласовать схему доступа к платёжным данным.
Рита отправит схему на согласование до 12 сентября. Рита отвечает за передачу
материалов, но не принимает решение за службу безопасности.

Если согласование не получено к 16 сентября, запуск переносится. Это условие является
обязательным gate запуска, а не рекомендацией. Новая дата в таком случае должна быть
согласована отдельно; в текущем протоколе она не определена.

## 3. План запуска

В день пилота команда планирует включать поток постепенно и следить за техническими
ошибками. При критическом росте неуспешных оплат включение останавливается, после чего
трафик возвращается на прежний поток. Числовой порог критического роста пока не
зафиксирован и должен быть определён до запуска.

Обсудили перевод всех пользователей на новый поток в сентябре, но решения по этому
вопросу не приняли. Полный перевод не является частью утверждённого пилота и не должен
появляться в резюме как запланированный этап.

## 4. Метрики

Для оценки пилота утверждены две основные метрики: доля успешных оплат и число
обращений в поддержку. Дополнительно команда хочет наблюдать время ответа платёжного
сервиса, но порог для этой метрики ещё не согласован.

Метрики следует смотреть отдельно для пилотной группы и контрольного потока. Складывать
обращения двух групп в одно число нельзя: это скроет различие, ради которого проводится
пилот.

## 5. Коммуникация и ответственность

Статус пилота будет публиковаться во внутреннем канале проекта. Рита сообщает только
статус передачи схемы и полученного ответа безопасности. Команда поддержки сообщает
динамику обращений, а техническая команда — ошибки и время ответа.

Ответственный за итоговый отчёт пока не назначен. Владелец продукта должен назначить
его до запуска. Нельзя автоматически считать Риту владельцем итогового отчёта только
потому, что она указана в разделе о согласовании.

## 6. Открытые вопросы

До запуска остаются три открытых вопроса: числовой порог для остановки при росте
неуспешных оплат, порог времени ответа и ответственный за итоговый отчёт. Эти вопросы
не отменяют уже принятого решения о границах пилота, но должны быть явно видны в
операционном плане.

Решение о полном переводе пользователей будет приниматься только после анализа
результатов пилота. Отчёт не содержит обещания завершить полный перевод в сентябре.

def test_hierarchical_reduce_bounds_every_call_and_preserves_provenance():
    chunks = chunk_text(TEXT, size=3, overlap=0, source="report")
    mapped = map_chunks(chunks, lambda text: text)
    observed_batch_sizes = []

    def reduce_fn(parts):
        observed_batch_sizes.append(len(parts))
        return " | ".join(parts)

    trace = hierarchical_reduce(mapped, reduce_fn, fan_in=3)

    assert len(trace["levels"]) > 2
    assert all(2 <= size <= 3 for size in observed_batch_sizes)
    assert trace["result"]["chunk_ids"] == [chunk["id"] for chunk in chunks]
    assert len(trace["levels"][-1]) == 1


def test_map_reduce_composes_and_empty_input_has_no_fake_result():
    chunks = chunk_text(TEXT, size=5, overlap=0)
    observed_batch_sizes = []

    def reduce_lengths(parts):
        observed_batch_sizes.append(len(parts))
        return str(sum(map(int, parts)))

    trace = map_reduce(
        chunks,
        map_fn=lambda text: str(len(text.split())),
        reduce_fn=reduce_lengths,
        fan_in=2,
    )

    assert trace["result"]["text"] == "25"
    assert observed_batch_sizes and set(observed_batch_sizes) == {2}
    assert map_reduce([], str, lambda parts: "unexpected") == {
        "result": None,
        "levels": [],
    }


def test_fan_in_one_cannot_make_progress():
    mapped = map_chunks(
        chunk_text(TEXT, size=5, overlap=0),
        lambda text: text,
    )

"""Traceable chunking and hierarchical reduction for lesson 3.2.

The word-based splitter is deliberately small: it exposes boundaries, overlap,
and provenance without pretending to parse paragraphs, tables, or PDF layout.
"""

from __future__ import annotations

from collections.abc import Iterable
from typing import Any


def _positive_int(value: Any, name: str) -> int:
    if isinstance(value, bool) or not isinstance(value, int) or value <= 0:
        raise ValueError(f"{name} must be a positive integer")
    return value


def chunk_text(text, size=100, overlap=20, source="document"):
    """Split text into overlapping word chunks with positional metadata.

    ``word_start`` is inclusive and ``word_end`` is exclusive.  The returned
    records are suitable for inspection and for carrying source identity into
    later map/reduce or retrieval stages.
    """
    size = _positive_int(size, "size")
    if isinstance(overlap, bool) or not isinstance(overlap, int):
        raise ValueError("overlap must be a non-negative integer smaller than size")
    if overlap < 0 or overlap >= size:
        raise ValueError("overlap must satisfy 0 <= overlap < size")
    if not isinstance(text, str):
        raise TypeError("text must be a string")
    if not isinstance(source, str) or not source.strip():
        raise ValueError("source must be a non-empty string")

    words = text.split()
    if not words:
        return []

    step = size - overlap
    chunks = []
    for index, start in enumerate(range(0, len(words), step)):
        end = min(start + size, len(words))
        chunks.append(
            {
                "id": f"{source}#chunk-{index:04d}",
                "source": source,
                "index": index,
                "word_start": start,
                "word_end": end,
                "text": " ".join(words[start:end]),
            }
        )
        if end == len(words):
            break
    return chunks


def map_chunks(chunks, map_fn):
    """Apply ``map_fn`` to every chunk and preserve chunk provenance."""
    mapped = []
    for chunk in chunks:
        result = map_fn(chunk["text"])
        if not isinstance(result, str) or not result.strip():
            raise ValueError(f"map_fn returned empty text for {chunk['id']}")
        mapped.append(
            {
                "id": f"summary:{chunk['id']}",
                "chunk_ids": [chunk["id"]],
                "level": 0,
                "text": result,
            }
        )
    return mapped


def _balanced_batches(items: list[dict], fan_in: int) -> Iterable[list[dict]]:
    """Balance a level; a singleton is possible only when it cannot be avoided."""
    batch_count = (len(items) + fan_in - 1) // fan_in
    base, larger_batches = divmod(len(items), batch_count)
    start = 0
    for index in range(batch_count):
        batch_size = base + (1 if index < larger_batches else 0)
        yield items[start:start + batch_size]
        start += batch_size


def hierarchical_reduce(mapped, reduce_fn, fan_in=4):
    """Reduce mapped records in bounded batches and return the full trace.

    ``reduce_fn`` receives a list of two to ``fan_in`` texts.  Each reduced
    record carries all original ``chunk_ids``.  For an empty input, ``result``
    is ``None`` and no reduce call is made.
    """
    fan_in = _positive_int(fan_in, "fan_in")
    if fan_in < 2:
        raise ValueError("fan_in must be at least 2")

    current = [dict(item) for item in mapped]
    if not current:
        return {"result": None, "levels": []}

    levels = [current]
    level = 1
    while len(current) > 1:
        reduced = []
        for batch_index, batch in enumerate(_balanced_batches(current, fan_in)):
            if len(batch) == 1:
                carried = dict(batch[0])
                carried.update(
                    {
                        "id": f"carry-l{level}-b{batch_index:04d}",
                        "level": level,
                        "carried_from": batch[0]["id"],
                    }
                )
                reduced.append(carried)
                continue
            result = reduce_fn([item["text"] for item in batch])
            if not isinstance(result, str) or not result.strip():
                raise ValueError(
                    f"reduce_fn returned empty text at level {level}, "
                    f"batch {batch_index}"
                )
            reduced.append(
                {
                    "id": f"reduce-l{level}-b{batch_index:04d}",
                    "chunk_ids": [
                        chunk_id
                        for item in batch
                        for chunk_id in item["chunk_ids"]
                    ],
                    "level": level,
                    "text": result,
                }
            )
        current = reduced
        levels.append(current)
        level += 1

    return {"result": current[0], "levels": levels}


def map_reduce(chunks, map_fn, reduce_fn, fan_in=4):
    """Map chunks, then reduce them hierarchically with a bounded fan-in."""
    return hierarchical_reduce(
        map_chunks(chunks, map_fn),
        reduce_fn,
        fan_in=fan_in,
    )
