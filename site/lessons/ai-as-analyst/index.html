Урок 5.1 · ИИ как аналитик

Фаза 5 — Данные и аналитика · Результат фазы: превращать бизнес-вопрос в проверяемый анализ и NL→SQL, проводить ограниченное BI-расследование и выпускать отчёт по решению quality gate.

Результат урока: после урока студент сможет превратить простой описательный бизнес-вопрос в проверяемый аналитический план: зафиксировать источник, смысл одной строки, период, фильтры, определение метрики, разрез, способ расчёта и проверку; исполнить этот план над табличной выгрузкой и обнаружить расхождение между правдоподобным числом и корректным расчётом.

Опоры: в 2.4 ты отделял постоянный контракт от динамического входа, в 2.5 проверял результат на заранее заданных случаях, а в Фазе 4 фиксировал scope, provenance и приёмку проекта. · Дальше: в 5.2 модель начнёт писать код по такому плану, а изолированная среда — исполнять его.

Requires: Python 3 и pytest для офлайн-практики. Для USE IT нужен только доступ к выбранному AI-инструменту, который умеет работать с загруженным CSV и исполнять код; конкретный провайдер, платный API и новая агентная среда выполнения не обязательны.

Главная мысль. Код точно считает то, что ему поручили. Поэтому сначала проверяем смысл расчёта, затем исполняем и сверяем результат.

Проблема: правильная арифметика может отвечать не на тот вопрос

Команда спрашивает:

Какие регионы принесли больше выручки во втором квартале?

В файле лежат шесть строк:

order_idquarterregionstatusamount
o-1Q2Москваpaid100
o-2Q2Москваpaid50
o-3Q2Питерpaid30
o-4Q2Питерrefunded70
o-5Q2Казаньpaid20
o-6Q1Москваpaid999

Можно написать безошибочный groupby и получить Москву 1149, Питер 100, Казань 20. Арифметика верна для всех строк файла, но ответ неверен для поставленного вопроса: в Москву попал Q1, а в Питер — возврат.

До расчёта остаются решения:

  1. «Выручка» означает все созданные заказы или только оплаченные?
  2. Возвраты вычитаются, исключаются или учитываются отдельной отрицательной строкой?
  3. Период определяется колонкой quarter или датой оплаты?
  4. Одна строка — заказ, товарная позиция или платёж?
  5. Нужен полный результат или только top-N — N групп с наибольшим значением, — и куда попадёт остаток?

ИИ может предложить ответы, но не знает внутреннее определение метрики и не получает право придумать его за владельца процесса. Поэтому первый результат работы ИИ-аналитика — не число и не график, а проверяемый план расчёта.

Центральная модель

Таблица, строка, колонка и grain

CSV — текстовый табличный формат: первая строка обычно содержит названия колонок, остальные — данные. После чтения учебным кодом одна строка представлена словарём:

{
    "order_id": "o-1",
    "quarter": "Q2",
    "region": "Москва",
    "status": "paid",
    "amount": "100",
}
  • Строка — одна единица наблюдения.
  • Колонка — одно свойство этой единицы: регион, статус или сумма.
  • Grain, или гранулярность, — точное значение одной строки: один заказ, одна позиция заказа, один платёж или один пользователь за день.
  • Row ID — колонка, по которой можно отличить одну единицу наблюдения от другой.

Grain нужно назвать до COUNT. Если один заказ занимает три строки товаров, COUNT(*) = 3 означает три позиции, а не три заказа. Дубли одного order_id могут быть ошибкой выгрузки или признаком другого grain — это нужно выяснить, а не молча сложить.

Колонка ещё не является метрикой

Колонка amount хранит значения. Метрика задаёт смысл итогового числа:

название
+ источник и период
+ фильтры включения и исключения
+ формула агрегации
+ единица результата

Для учебного вопроса договоримся:

paid_revenue =
SUM(amount)
WHERE quarter = Q2
  AND status = paid
единица = RUB

Это одно из возможных бизнес-определений. В реальной компании возвраты могут представляться иначе. Важно не угадать «универсально правильную» формулу, а получить подтверждённое определение владельца метрики.

Семь частей простого аналитического плана

В этом уроке рассматриваем только описательные вопросы с групповой агрегацией: сколько, в среднем и как распределено по группам. Такой план содержит:

ЧастьКонтрольный вопрос
Вопрос и границаКакое описательное число нужно и чего оно не доказывает?
Данные и grainОткуда строки и что означает одна строка?
Период и фильтрыКакие строки должны участвовать?
МетрикаКак называются формула и единица результата?
РазрезПо какой колонке сравниваются группы?
Агрегатsum, mean или явно определённый count_rows?
ПроверкаКак заметить потерю строк, дубль, неверный тип или несходящийся итог?

Вопрос «почему продажи упали?» уже не является простой агрегацией. Группировки могут показать, где наблюдается снижение, но не доказывают его причину. Прогноз и причинный вывод также находятся за границей урока.

Модель предлагает, код исполняет, человек принимает

Структурированную запись такого плана дальше называем AnalysisPlan. Разделим три роли:

человек задаёт вопрос и бизнес-границы
                ↓
модель предлагает AnalysisPlan
                ↓
человек проверяет grain, метрику и фильтры
                ↓
код детерминированно исполняет утверждённый план:
одинаковый вход даёт одинаковый результат
                ↓
человек сверяет строки, итоги и границу вывода

Модель не обязана сама исполнять Python. В продукте она может передать код отдельному инструменту. Эту границу разберём в 5.2. Здесь важно другое: даже идеально исполненный код не исправит неверное определение метрики.

Где работает split-apply-combine

После фильтрации групповой расчёт проходит три шага:

split    → разделить выбранные строки по region
apply    → посчитать SUM(amount) внутри каждой группы
combine  → собрать полный результат и только затем выделить top-N

split-apply-combine объясняет механизм групповой агрегации, но не заменяет весь аналитический план: он ничего не решает про grain, период, возвраты и проверку данных.

Разбор одного плана

Шаг 1. Фиксируем вопрос и определение

Вопрос: какие регионы принесли больше оплаченной выручки в Q2?
Grain: одна строка = один заказ.
Row ID: order_id.
Период: quarter = Q2.
Фильтр: status = paid.
Метрика: paid_revenue = SUM(amount), RUB.
Разрез: region.
Формат: top-2, остальные отдельно, полный итог.

Шаг 2. Записываем исполняемый план

PLAN = {
    "question": "Какие регионы принесли больше оплаченной выручки в Q2?",
    "source": "sales.csv",
    "grain": "одна строка = один заказ",
    "row_id": "order_id",
    "period": "Q2",
    "filters": {"quarter": "Q2", "status": "paid"},
    "metric": {
        "name": "paid_revenue",
        "column": "amount",
        "aggregation": "sum",
        "unit": "RUB",
    },
    "group_by": "region",
    "top_n": 2,
}

Это не результат автоматического разбора свободного текста. План может предложить человек или ИИ, но до исполнения каждое поле должно быть проверено. question, source, grain и period сохраняют проверяемый смысл расчёта; filters, metric, group_by и top_n непосредственно управляют учебным исполнителем. Поэтому, например, текстовое поле period="Q2" не заменяет машинный фильтр quarter="Q2".

Шаг 3. Проверяем контракт до расчёта

Исполнитель сначала убеждается, что:

  • обязательные поля плана заполнены;
  • sum входит в разрешённый набор агрегатов;
  • order_id, quarter, status, amount и region существуют;
  • order_id заполнены и уникальны;
  • top_n — положительное целое число.

Неизвестный median, отсутствующая колонка или повторяющийся ID останавливают расчёт. Молчаливая замена ошибки на sum, None или ноль создала бы убедительный ложный ответ.

Шаг 4. Фильтруем до группировки

прочитано: 6 строк
исключено:
  o-4 — status=refunded
  o-6 — quarter=Q1
использовано: 4 строки

После фильтра остаются суммы 100, 50, 30, 20. Если amount содержит unknown, исполнитель останавливается и называет строку: отсутствующее число не равно нулю.

Шаг 5. Выполняем split-apply-combine

split:
  Москва → [100, 50]
  Питер  → [30]
  Казань → [20]

apply SUM:
  Москва → 150
  Питер  → 30
  Казань → 20

combine:
  общий итог → 200

Шаг 6. Не выдаём top-N за полный результат

top-2 = Москва 150 + Питер 30 = 180
other = Казань 20
overall = 200

180 + 20 = 200

Проверять нужно все группы до обрезки. Сумма только top-2 не обязана равняться общему итогу. Такую контрольную сверку частей с общим итогом называют reconciliation check, или сверкой согласованности.

Для mean действует другое правило. Средние групп нельзя просто сложить: группа из двух заказов должна иметь больший вес, чем группа из одного. Поэтому исполнитель сверяет взвешенное среднее групп с общим средним.

BUILD IT

Задание: собери проверяемый исполнитель AnalysisPlan. Он не понимает естественный язык и не вызывает модель: принимает уже проверенный словарь, валидирует его и выполняет одну групповую агрегацию над CSV. Используй только стандартную библиотеку.

Перед запуском. Работай в созданной в фазе 0 папке ai-native-work, а файлы урока клади в course-work/phase-5/ai-analyst/code/. Клонировать курс не нужно. Со страницы сначала скопируй test_analyze.py, затем создай собственный analyze.py.

Реализуй:

  • PlanError — ошибка, при которой расчёт нельзя продолжать убедительно.
  • load_csv(text) — читает непустой CSV с заголовком в список словарей.
  • validate_plan(rows, plan) — проверяет поля плана, допустимый агрегат, нужные колонки, положительный top_n и уникальность row_id.
  • execute_plan(rows, plan) — применяет точные фильтры, блокирует пустой результат и нечисловые значения, считает группы, общий итог, top-N, остаток и контрольную сверку итогов.

До реализации предскажи:

  1. Сколько строк останется после фильтров Q2 + paid?
  2. Почему возврат 70 не должен попасть в результат?
  3. Почему aggregation="median" должен завершиться ошибкой, а не суммой?
  4. Почему top-2 равен 180, а общий итог — 200?
  5. Чем отсутствие числового значения отличается от суммы 0?

Готово, когда восемь тестов подтверждают:

  • CSV сохраняет строки и колонки;
  • период и статус фильтруются до группировки;
  • sum даёт полный результат Москва=150, Питер=30, Казань=20;
  • count_rows считает четыре выбранных заказа; в его поле column укажи уникальный order_id, чтобы явно назвать считаемую единицу;
  • top-2 сохраняет other=20 и сходится с общим итогом 200;
  • mean проверяется с весами;
  • неизвестный агрегат и нечисловая метрика блокируют расчёт;
  • дубли row_id нарушают заявленный grain и блокируют расчёт;
  • отсутствующая колонка и пустой результат фильтра не превращаются в ответ.

После зелёных тестов объясни без кода:

  • какие две строки были исключены и почему;
  • чем amount отличается от метрики paid_revenue;
  • почему техническая исполнимость плана ещё не означает, что бизнес-определение подтверждено.

4D в аналитической задаче

  • Delegation: отдай ИИ предложение плана и написание кода, но не решение о смысле метрики и допустимости данных.
  • Description: зафиксируй grain, период, фильтры, формулу, единицу, разрез, формат и проверки.
  • Discernment: сравни предложенный план с бизнес-вопросом, а результат — со строками, полным итогом и граничными случаями.
  • Diligence: проверь разрешённость данных, сохрани код и план, назови роль ИИ и не отправляй вывод без самостоятельной приёмки.

Реалистичные ошибки

  • Начать с «посмотри, что интересного». Модель сама выберет вопрос, метрику и критерий интересности; сначала задай решение и границу.
  • Назвать колонку метрикой. amount не объясняет период, статусы, формулу и единицу; запиши полное определение.
  • Не определить grain. COUNT(*) может посчитать позиции вместо заказов, а дубль — дважды увеличить сумму.
  • Фильтровать после агрегации. Неподходящие строки уже изменили итог; сначала выбери строки, затем группируй.
  • Превратить отсутствие значения в ноль. Ноль — наблюдение, а пропуск или повреждённый тип — проблема данных.
  • Неизвестный агрегат молча заменить на sum. Правдоподобное число скрывает ошибку плана; останови расчёт.
  • Сложить средние групп. Среднее требует весов; сумма средних не является общим средним.
  • Сверять только top-N. Обрезанный список не равен полному распределению; покажи other и общий итог.
  • Сделать причинный вывод из группировки. Разница между регионами является наблюдением, а не объяснением причины.
  • Считать показанный код гарантией качества. Код делает расчёт аудируемым, но не подтверждает определение метрики и происхождение данных.

Что сознательно осталось за границей

  • Свободный разведочный анализ данных и автоматический поиск «интересных» наблюдений.
  • Графики, корреляции, статистические тесты и регрессия.
  • Причинные выводы и прогнозирование.
  • Очистка произвольных грязных наборов данных.
  • Безопасное исполнение кода модели: это 5.2.
  • SQL и централизованные определения метрик: это 5.3.
  • Автоматизированная проверка аномалий и отчётов: это 5.5.

code/analyze.pyПоказать решение
"""Проверяемый исполнитель простого аналитического плана для урока 5.1.

Модуль не понимает естественный язык и не изображает ИИ. Человек или модель сначала
предлагает AnalysisPlan, человек проверяет определения, а этот код детерминированно
валидирует и исполняет простую групповую агрегацию над CSV.
"""

import csv
import io
from math import isclose


ALLOWED_AGGREGATIONS = {"sum", "mean", "count_rows"}
REQUIRED_PLAN_FIELDS = {
    "question",
    "source",
    "grain",
    "row_id",
    "period",
    "filters",
    "metric",
    "group_by",
    "top_n",
}


class PlanError(ValueError):
    """План или данные не позволяют получить проверяемый результат."""


def load_csv(text):
    """Прочитать непустой CSV-текст в список строк-словарей."""
    reader = csv.DictReader(io.StringIO(text.strip()))
    if not reader.fieldnames:
        raise PlanError("CSV must contain a header")
    rows = list(reader)
    if not rows:
        raise PlanError("CSV must contain at least one data row")
    return rows


def validate_plan(rows, plan):
    """Проверить контракт плана, колонки и заявленный grain до расчёта."""
    if not isinstance(plan, dict):
        raise PlanError("plan must be a mapping")
    missing_fields = sorted(REQUIRED_PLAN_FIELDS - set(plan))
    if missing_fields:
        raise PlanError(f"plan fields missing: {', '.join(missing_fields)}")

    for field in ("question", "source", "grain", "row_id", "period", "group_by"):
        value = plan[field]
        if not isinstance(value, str) or not value.strip():
            raise PlanError(f"plan.{field} must be a non-empty string")

    filters = plan["filters"]
    if not isinstance(filters, dict):
        raise PlanError("plan.filters must be a mapping")

    metric = plan["metric"]
    if not isinstance(metric, dict):
        raise PlanError("plan.metric must be a mapping")
    for field in ("name", "column", "aggregation", "unit"):
        value = metric.get(field)
        if not isinstance(value, str) or not value.strip():
            raise PlanError(f"plan.metric.{field} must be a non-empty string")
    if metric["aggregation"] not in ALLOWED_AGGREGATIONS:
        raise PlanError(
            "plan.metric.aggregation must be one of "
            + ", ".join(sorted(ALLOWED_AGGREGATIONS))
        )

    top_n = plan["top_n"]
    if not isinstance(top_n, int) or isinstance(top_n, bool) or top_n <= 0:
        raise PlanError("plan.top_n must be a positive integer")

    columns = set(rows[0])
    required_columns = {
        plan["row_id"],
        plan["group_by"],
        *filters.keys(),
        metric["column"],
    }
    missing_columns = sorted(required_columns - columns)
    if missing_columns:
        raise PlanError(f"data columns missing: {', '.join(missing_columns)}")

    row_ids = [row.get(plan["row_id"]) for row in rows]
    if any(row_id in (None, "") for row_id in row_ids):
        raise PlanError("row_id contains an empty value")
    if len(row_ids) != len(set(row_ids)):
        raise PlanError("duplicate row ids violate the declared grain")


def _number(value, *, row_id, column):
    try:
        return float(value)
    except (TypeError, ValueError) as exc:
        raise PlanError(
            f"row {row_id} contains a non-numeric value in {column}"
        ) from exc


def execute_plan(rows, plan):
    """Исполнить проверенную групповую агрегацию и вернуть расчёт с проверками."""
    validate_plan(rows, plan)

    filters = plan["filters"]
    selected = [
        row
        for row in rows
        if all(row.get(column) == expected for column, expected in filters.items())
    ]
    if not selected:
        raise PlanError("no rows match the declared filters")

    metric = plan["metric"]
    aggregation = metric["aggregation"]
    metric_column = metric["column"]
    row_id_column = plan["row_id"]
    group_column = plan["group_by"]
    groups = {}

    for row in selected:
        group = row.get(group_column)
        if group in (None, ""):
            raise PlanError(f"row {row[row_id_column]} has an empty group")
        bucket = groups.setdefault(group, {"rows": 0, "values": []})
        bucket["rows"] += 1
        if aggregation != "count_rows":
            bucket["values"].append(
                _number(
                    row.get(metric_column),
                    row_id=row[row_id_column],
                    column=metric_column,
                )
            )

    group_results = []
    all_values = []
    for group, bucket in groups.items():
        values = bucket["values"]
        if aggregation == "count_rows":
            value = bucket["rows"]
        elif aggregation == "sum":
            value = sum(values)
            all_values.extend(values)
        else:
            value = sum(values) / len(values)
            all_values.extend(values)
        group_results.append(
            {"group": group, "value": value, "rows": bucket["rows"]}
        )

    group_results.sort(key=lambda item: (-item["value"], str(item["group"])))
    top = group_results[: plan["top_n"]]

    if aggregation == "count_rows":
        overall = len(selected)
        reconciled = sum(item["value"] for item in group_results) == overall
        other_value = overall - sum(item["value"] for item in top)
        reconciliation_rule = "sum of all group counts equals selected row count"
    elif aggregation == "sum":
        overall = sum(all_values)
        reconciled = isclose(
            sum(item["value"] for item in group_results),
            overall,
            rel_tol=1e-12,
            abs_tol=1e-12,
        )
        other_value = overall - sum(item["value"] for item in top)
        reconciliation_rule = "sum of all group values equals overall sum"
    else:
        overall = sum(all_values) / len(all_values)
        weighted = sum(item["value"] * item["rows"] for item in group_results)
        reconciled = isclose(
            weighted / len(selected),
            overall,
            rel_tol=1e-12,
            abs_tol=1e-12,
        )
        other_value = None
        reconciliation_rule = "weighted group mean equals overall mean"

    return {
        "question": plan["question"],
        "metric": metric["name"],
        "unit": metric["unit"],
        "rows_read": len(rows),
        "rows_used": len(selected),
        "rows_excluded": len(rows) - len(selected),
        "groups": group_results,
        "top": top,
        "overall": overall,
        "other_value": other_value,
        "checks": {
            "row_ids_unique": True,
            "required_values_valid": True,
            "reconciled": reconciled,
            "reconciliation_rule": reconciliation_rule,
        },
    }


CSV_DEMO = """order_id,quarter,region,status,amount
o-1,Q2,Москва,paid,100
o-2,Q2,Москва,paid,50
o-3,Q2,Питер,paid,30
o-4,Q2,Питер,refunded,70
o-5,Q2,Казань,paid,20
o-6,Q1,Москва,paid,999
"""

DEMO_PLAN = {
    "question": "Какие регионы принесли больше оплаченной выручки в Q2?",
    "source": "sales.csv",
    "grain": "одна строка = один заказ",
    "row_id": "order_id",
    "period": "Q2",
    "filters": {"quarter": "Q2", "status": "paid"},
    "metric": {
        "name": "paid_revenue",
        "column": "amount",
        "aggregation": "sum",
        "unit": "RUB",
    },
    "group_by": "region",
    "top_n": 2,
}


if __name__ == "__main__":
    report = execute_plan(load_csv(CSV_DEMO), DEMO_PLAN)
    print("Строк прочитано / использовано:", report["rows_read"], "/", report["rows_used"])
    print("Все группы:", report["groups"])
    print("Топ-2:", report["top"], "Остальные:", report["other_value"])
    print("Общий итог:", report["overall"])
    print("Проверки:", report["checks"])

outputs/analysis-request-template.md
# Артефакт: проверяемый аналитический brief

Этот brief — краткий паспорт смысла и исполнения расчёта — фиксирует договорённости до того, как ИИ напишет код. Скопируй шаблон в свою
папку, замени учебный пример собственным вопросом и приложи исполненный план с
проверками. Механика офлайн-исполнителя — [`code/analyze.py`](../code/analyze.py).

## 1. Решение и граница вопроса

| Поле | Что зафиксировать |
|---|---|
| Решение | Какое действие будет принято по результату |
| Описательный вопрос | Какое число или сравнение нужно получить |
| Не исследуем | Причины, прогнозы и другие выводы, которых этот расчёт не доказывает |
| Владелец определения | Кто подтверждает смысл метрики и фильтров |

Если вопрос звучит как «почему продажи упали?» или «что произойдёт дальше?», простой
групповая агрегация может подготовить наблюдения, но не доказать причину и не дать
надёжный прогноз.

## 2. Контракт данных

| Поле | Что зафиксировать |
|---|---|
| Источник | Имя файла, таблицы или системы |
| Период | Какие даты или периоды входят |
| Grain | Что означает одна строка |
| Row ID | Какая колонка отличает одну единицу наблюдения |
| Нужные колонки и типы | Название, смысл, ожидаемый тип |
| Известные ограничения | Пропуски, дубли, неполная выгрузка, часовой пояс, валюта |

Grain проверяется до агрегации. Если одна строка означает позицию заказа, `COUNT(*)`
считает позиции, а не уникальные заказы.

## 3. Определение метрики

| Поле | Что зафиксировать |
|---|---|
| Название | Понятное бизнес-имя |
| Формула | Например `SUM(amount)` |
| Фильтры | Какие строки включаются и исключаются |
| Разрез | По какой колонке сравниваются группы |
| Единица | Рубли, заказы, проценты, минуты |
| Top-N | Сколько лидеров показать и как показать остаток |

Колонка `amount` сама по себе не является метрикой. Метрика появляется, когда определены
формула, фильтры, период и единица результата.

## 4. План исполнения

```python
PLAN = {
    "question": "...",
    "source": "...",
    "grain": "...",
    "row_id": "...",
    "period": "...",
    "filters": {"column": "expected value"},
    "metric": {
        "name": "...",
        "column": "...",  # для count_rows укажи row_id считаемой единицы
        "aggregation": "sum | mean | count_rows",
        "unit": "...",
    },
    "group_by": "...",
    "top_n": 5,
}
```

ИИ может предложить этот план, но владелец вопроса проверяет его до исполнения. Не проси
модель угадывать неизвестное определение метрики.

## 5. Проверки результата

- [ ] Прочитанное число строк совпадает с выгрузкой.
- [ ] Видно, сколько строк использовано и исключено фильтрами.
- [ ] Row ID заполнен и уникален согласно заявленному grain.
- [ ] Нужные колонки существуют, а значения метрики имеют ожидаемый тип.
- [ ] Для `sum` и `count_rows` итог всех групп сходится с общим итогом.
- [ ] Для `mean` среднее групп проверяется с весами, а не простым сложением.
- [ ] Top-N не выдаётся за полный итог: остаток показан отдельно.
- [ ] Вывод не выходит за границу описательного вопроса.

## Заполненный учебный пример

### Вопрос

Какие регионы принесли больше оплаченной выручки в Q2?

### Контракт

| Поле | Значение |
|---|---|
| Источник | `sales.csv` |
| Grain | Одна строка = один заказ |
| Row ID | `order_id` |
| Период | `quarter = Q2` |
| Метрика | `paid_revenue = SUM(amount)` |
| Фильтры | `quarter = Q2`, `status = paid`; возвраты и другие периоды исключаются |
| Разрез | `region` |
| Единица | RUB |
| Формат | Top-2 региона, остальные отдельно, полный итог и проверки |

### План

```python
PLAN = {
    "question": "Какие регионы принесли больше оплаченной выручки в Q2?",
    "source": "sales.csv",
    "grain": "одна строка = один заказ",
    "row_id": "order_id",
    "period": "Q2",
    "filters": {"quarter": "Q2", "status": "paid"},
    "metric": {
        "name": "paid_revenue",
        "column": "amount",
        "aggregation": "sum",
        "unit": "RUB",
    },
    "group_by": "region",
    "top_n": 2,
}
```

### Ожидаемый результат

| Показатель | Значение |
|---|---:|
| Строк прочитано | 6 |
| Строк использовано | 4 |
| Москва | 150 |
| Питер | 30 |
| Остальные регионы | 20 |
| Общая оплаченная выручка Q2 | 200 |

Проверка выполняется по всем группам до обрезки top-2:

```text
150 + 30 + 20 = 200
top-2 = 180
other = 20
180 + 20 = 200
```

Этот расчёт показывает распределение оплаченной выручки по регионам. Он не доказывает,
почему один регион сильнее другого и сохранится ли результат в следующем квартале.
