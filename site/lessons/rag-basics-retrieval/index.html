Урок 3.3 · Основы RAG: retrieval

Фаза 3 — Текст и документы · Результат фазы: строить пайплайны резюмирования и редактуры; собрать базовый RAG над своим корпусом.

Результат урока: после урока студент сможет построить офлайн TF-IDF retriever над трассируемыми чанками из 3.2, проверить его на наборе вопрос → ожидаемые ID, вернуть найденный текст вместе с источником и остановить RAG-цепочку, если лексических доказательств нет.

Опора: контекстное окно и границы доверия из 1.2–1.4, проверяемые ожидания из 2.5, чанки с id, source и позициями из 3.2. · Дальше: в 3.4 цикл проиндексировать → найти станет компонентом с состоянием и персистентностью, а стабильный ID останется связью с исходной записью; в 3.5 появятся гибридный поиск, слияние рангов (rank fusion) и сравнительная оценка нескольких retriever.

Requires: Python 3 и pytest. Урок, Build It и проверка mini-RAG работают офлайн, без API-ключа, сети и клонирования репозитория.

Главная мысль. Retrieval не отвечает на вопрос. Он решает, какие доказательства увидит следующий шаг, и обязан уметь сказать: «подходящих доказательств не найдено».

Ситуация: нужный фрагмент существует, но модель его ещё не видит

В 3.2 мы превратили учебный отчёт о пилоте в записи такого вида:

{
  "id": "sample_report.md#chunk-0002",
  "source": "sample_report.md",
  "word_start": 120,
  "word_end": 190,
  "text": "Если согласование не получено к 16 сентября, запуск переносится..."
}

Теперь представь ассистента по этому отчёту. Пользователь спрашивает:

Что произойдёт, если согласование безопасности не будет получено к 16 сентября?

Модель не получает весь корпус автоматически. Есть три плохих варианта:

  1. не передать ей документ — тогда ответ будет опираться на встроенные знания и догадку, а не на внутренний отчёт;
  2. каждый раз передавать весь корпус — на большом наборе документов это расходует контекст и затрудняет проверку источника;
  3. передать первые несколько чанков — нужное условие может оказаться в другом месте.

Нужна отдельная операция: по вопросу выбрать несколько подходящих записей и только после этого собирать запрос модели. Эта операция называется retrieval, или извлечение релевантных фрагментов.

Слово релевантный здесь не означает «вообще похожий на тему». Фрагмент релевантен конкретному вопросу, если содержит доказательство, полезное для ответа на него. Раздел про метрики относится к тому же пилоту, но не отвечает на вопрос о согласовании.

Где retrieval находится внутри RAG

RAG — retrieval-augmented generation, то есть генерация с контекстом, найденным перед ответом. Для этого урока полезно разделять три операции:

вопрос
  │
  ▼
RETRIEVE: найти записи корпуса
  │        результат: чанки + ID + источник + score
  ▼
AUGMENT: собрать из них пакет контекста и инструкции
  │        результат: проверяемый промпт
  ▼
GENERATE: получить ответ по переданному контексту
           результат: ответ со ссылками на ID

Это разделение нужно не ради терминов, а ради диагностики:

НаблюдениеГде искать сбой
Нужного ID нет среди найденных чанковretrieval не нашёл доказательство
ID найден, но потерялся при сборке промптаaugmentation отбросил доказательство
Доказательство есть в промпте, но ответ ему противоречитgeneration или инструкция ответа

Промпт не исправит отсутствующий чанк. Более сильная модель тоже не докажет факт, который retrieval ей не показал. Поэтому в этом уроке мы сначала проверяем поиск отдельно от качества ответа.

Как сравнить вопрос и чанк без нейросети

Человек видит связь по смыслу. Компьютеру нужен способ превратить вопрос и текст в сопоставимые числа. Мы начнём с лексического подхода: совпадение возникает, когда в вопросе и чанке встречаются одинаковые слова.

Учебный механизм состоит из четырёх шагов:

текст
→ токены
→ TF-IDF-вектор
→ косинусная близость вопроса и каждого чанка
→ ранжирование и решение «вернуть / не вернуть»

Шаг 1. Токены и стоп-слова

Токен в этом упражнении — последовательность букв, цифр или _, найденная регулярным выражением \w+. Мы приводим токены к нижнему регистру:

"Запуск переносится 16 сентября"
→ ["запуск", "переносится", "16", "сентября"]

Очень частые служебные слова вроде «и», «в», «на» редко помогают выбрать чанк. Мы удаляем их по короткому, видимому списку STOP_WORDS. Это не универсальный лингвистический анализ: список пригоден для учебного русского корпуса, но для другого языка или домена его нужно проверить заново.

Мы также не приводим слова к нормальной форме. Поэтому перенос, переносится и перенести остаются разными токенами. Эта ограниченность позже станет наблюдаемым типичным сбоем.

Шаг 2. TF-IDF: вес слова внутри корпуса

После токенизации каждому слову нужен вес. Простое «слово встретилось» плохо различает характерный термин и слово, которое есть почти везде. TF-IDF соединяет две величины.

TF — term frequency, частота слова в одном чанке:

TF(term, chunk) = число term в чанке / число оставшихся токенов чанка

Если запуск встречается два раза среди 20 токенов, TF = 2 / 20 = 0.1.

DF — document frequency, количество чанков корпуса, содержащих слово хотя бы один раз. Если запуск встретился в трёх чанках, DF = 3, даже если в одном из них слово повторено пять раз.

IDF — inverse document frequency, коэффициент редкости слова по корпусу. В коде используется сглаженная формула:

IDF(term) = log((N + 1) / (DF + 1)) + 1

N — количество чанков. Чем меньше DF, тем выше IDF и тем сильнее редкое совпадение влияет на поиск.

Наконец:

TF-IDF(term, chunk) = TF(term, chunk) × IDF(term)

Важная точность: в выбранной сглаженной формуле слово, которое есть во всех чанках, получает IDF = 1, а не ноль. IDF уменьшает влияние частых слов относительно редких, но сам по себе не обязан удалить «и» или «в». Поэтому мы отдельно используем STOP_WORDS; говорить, что эта формула «почти зануляет» любое частое слово, было бы неверно.

Шаг 3. Разреженный вектор

Весь словарь корпуса можно представить как набор координат:

["16", "безопасность", "запуск", "метрики", "пилот", ...]

Для каждого чанка TF-IDF задаёт значение по каждой координате. Большинство слов в конкретном чанке отсутствует, поэтому хранить тысячи нулей незачем. Используем разреженный вектор — словарь только ненулевых весов:

{
    "16": 0.08,
    "безопасность": 0.12,
    "запуск": 0.06,
}

Это всё ещё вектор, просто компактно записанный как {слово: вес}. Слова запроса, которых вообще нет в словаре корпуса, получают вес 0 и не создают совпадения.

TF-IDF превращает текст в вектор, но в современном RAG словом embedding обычно называют обученное плотное представление. Чтобы не спутать механизмы, наш учебный вектор будем называть точнее: разреженное лексическое представление. Плотные нейросетевые embeddings появятся как другой способ построить вектор, а не как другое определение retrieval.

Шаг 4. Косинусная близость

Нужно сравнить направление вектора вопроса с направлением вектора чанка. Для этого используется косинусная близость:

cosine(a, b) = (a · b) / (||a|| × ||b||)
  • a · b — скалярное произведение: сумма произведений совпадающих координат;
  • ||a|| и ||b|| — длины векторов;
  • результат 1 означает одинаковое направление;
  • результат 0 означает отсутствие общих ненулевых координат.

Мини-пример по двум словам:

a = [1, 0]
b = [1, 1]

a · b = 1×1 + 0×1 = 1
||a|| = 1
||b|| = √2 ≈ 1.41
cosine(a, b) = 1 / 1.41 ≈ 0.71

Деление на длины важно: без него длинный чанк мог бы получать большой score только из-за большего числа слов. Но cosine не является вероятностью правильного ответа. 0.33 не означает «33% уверенности», а значения из разных корпусов нельзя механически сравнивать.

От score к решению

После вычисления cosine для каждого чанка retriever сортирует записи по убыванию. Top-k означает «не больше k первых результатов».

Однако top-k сам по себе не гарантирует релевантность. Если все scores равны нулю, «лучшие три» всё равно были бы случайными тремя чанками. Поэтому контракт search двухступенчатый:

  1. отбросить score 0 и всё ниже min_score;
  2. вернуть не больше k оставшихся записей.

При min_score=0 функция принимает любое положительное лексическое совпадение, но никогда не возвращает нулевое. Это безопаснее слепого top-k, но ещё не доказывает, что фрагмент отвечает на вопрос: одно совпавшее слово может быть шумом.

Универсального min_score нет. Он зависит от корпуса, разбиения, запросов и представления. Порог выбирают не по красивому числу, а по примерам, где заранее известно, что должно быть найдено и где правильный результат — ничего не вернуть.

k тоже является решением с ценой:

  • слишком маленький k может не включить второй необходимый фрагмент;
  • слишком большой k добавляет шум и расходует контекст;
  • изменение k не исправляет нулевое совпадение синонимов.

Предскажи результаты до запуска

В исходниках есть семь чанков того же sample_report.md, подготовленных в 3.2 с size=70 и overlap=10.

Сначала не запускай код. Для каждого запроса предскажи результат:

ЗапросОжидание
согласование получено 16 сентября запуск переноситсяпервым должен быть chunk-0002
какой рекламный бюджет[]: таких слов и факта в корпусе нет
кто автор финального документалексический промах: в корпусе написано «ответственный за итоговый отчёт»
и в на[]: после удаления стоп-слов запрос пуст

Реальный результат первого запроса:

0.331  sample_report.md#chunk-0002
0.205  sample_report.md#chunk-0001

Первым найден чанк с точным условием переноса. Соседний chunk-0001 тоже содержит слова о согласовании и безопасности, а overlap повторил границу между чанками. Это не ошибка: иногда для ответа нужны оба фрагмента. Их ID и позиции позволяют увидеть повторение и не выдавать два соседних чанка за два независимых доказательства.

Нерелевантный запрос и запрос только из стоп-слов возвращают []. Запрос про «автора финального документа» тоже возвращает [], но по другой причине: доказательство в корпусе есть, однако слова запроса и документа не совпали. Первый случай — правильное воздержание, второй — ошибка лексического retrieval. Одинаковая пустая выдача требует разной интерпретации, и различить их можно только по размеченным ожиданиям.

Минимальная оценка retrieval

Создадим маленький набор случаев:

EVAL_CASES = [
    {
        "query": "когда запускается пилот iOS",
        "expected_ids": ["sample_report.md#chunk-0000"],
    },
    {
        "query": "какой рекламный бюджет",
        "expected_ids": [],
    },
]

Непустой expected_ids означает: среди первых k должен встретиться хотя бы один из этих ID. Так мы получаем учебный Hit@k:

Hit@k = доля ответимых запросов,
        где top-k содержит хотя бы один ожидаемый ID

Пустой expected_ids означает no-answer случай: успешен только пустой результат. evaluate() считает его отдельно как точность воздержания. Смешивать эти два типа в одну красивую цифру опасно: retriever, который всегда возвращает [], идеально «воздерживается», но ничего не находит.

Этот набор не доказывает production-качество. Он нужен, чтобы:

  • воспроизвести конкретный удачный и неудачный запрос;
  • сравнить k и min_score на одних ожиданиях;
  • не улучшить один пример ценой незаметной поломки другого;
  • локализовать лексический промах до вызова модели.

Сравнение lexical/dense/hybrid, rank fusion и граница оценки ответа появятся в 3.5. Здесь одного простого Hit@k достаточно, чтобы сделать решение наблюдаемым.

BUILD IT: трассируемый TF-IDF retriever

Задание: реализуй индекс, поиск с честной пустой выдачей и минимальную оценку на подготовленных чанках.

Работай в course-work/3.3/. Из «Исходников урока»:

  1. скопируй starter_retriever.py как course-work/3.3/retriever.py;
  2. скопируй рядом sample_chunks.py и test_retriever.py;
  3. скопируй mini_rag.py из блока «Артефакт» в ту же папку;
  4. эталонный retriever.py до первой собственной попытки не открывай.

Используй только стандартную библиотеку Python.

1. _tokens(text)

Функция должна:

  • принимать строку, иначе выбрасывать TypeError;
  • находить \w+ в нижнем регистре;
  • удалять токены из заданного STOP_WORDS;
  • возвращать list[str];
  • для пустой строки и строки из стоп-слов возвращать [].

2. _tfidf(tokens, idf) и _cosine(a, b)

_tfidf должна:

  • считать TF как долю токена среди оставшихся токенов;
  • умножать TF на IDF из словаря;
  • игнорировать слово, которого нет в idf;
  • для пустого входа возвращать {}.

_cosine должна:

  • принимать два разреженных словаря;
  • считать скалярное произведение только по общим ключам;
  • делить его на произведение норм;
  • возвращать 0.0, если хотя бы одна норма равна нулю.

3. build_index(chunks)

Каждый чанк обязан содержать непустые строки id, source, text. Функция должна:

  • отклонять строку вместо коллекции записей;
  • отклонять запись без обязательного поля;
  • отклонять повторяющиеся ID;
  • сохранить все поля исходной записи, включая позиции;
  • токенизировать text;
  • посчитать DF по set(tokens) каждого чанка;
  • построить сглаженный IDF и TF-IDF-векторы;
  • вернуть {"chunks": ..., "idf": ..., "vectors": ...}.

4. search(query, index, k=3, min_score=0.0)

Функция должна:

  • требовать положительный целый k, причём True не считается допустимым числом;
  • требовать числовой min_score в диапазоне [0, 1];
  • построить TF-IDF-вектор запроса по словарю корпуса;
  • вернуть [] для пустого запроса, запроса только из стоп-слов и полностью неизвестного запроса;
  • ранжировать по cosine;
  • при равных scores сохранять исходный порядок чанков;
  • отбросить нулевые scores и всё ниже min_score;
  • вернуть не больше k копий исходных записей с добавленным округлённым score.

Сравнивай с порогом полный score, а округляй только значение для выдачи. Иначе число 0.04996, округлённое до 0.05, может пройти или не пройти порог из-за формата отображения.

5. evaluate(cases, index, k=3, min_score=0.0)

Для каждого случая:

  • запусти search;
  • сохрани expected_ids и реальные retrieved_ids;
  • для ответимого запроса поставь passed=True, если множества пересекаются;
  • для expected_ids=[] поставь passed=True только при пустой выдаче.

Итог должен отдельно содержать:

  • answerable.hit_rate_at_k;
  • no_answer.accuracy;
  • подробности каждого случая, включая провалы.

Готово, когда тесты зелёные и в отчёте виден намеренный лексический промах, а не искусственные 100%.

cd course-work/3.3
pytest -q
python retriever.py
python mini_rag.py

Тесты проверяют не только счастливый путь, но и provenance, пустой результат, запрос только из стоп-слов, порог, некорректные параметры, дубликаты ID, стабильные ничьи, Hit@k и запрет вызова генератора без доказательств.

Подсказка. Для DF обновляй Counter множеством set(tokens) каждого чанка. Для стабильного ранжирования удобно сортировать пары (score, position) по ключу (-score, position).

SHIP IT: пакет доказательств для mini-RAG

Артефакт: outputs/mini_rag.py

Скрипт не копирует реализацию retrieval, а импортирует готовые build_index и search. Он добавляет две операции:

prepare_request
  ├─ нет hits → status=insufficient_context, prompt=None
  └─ есть hits → evidence с provenance + проверяемый prompt

answer_with
  ├─ insufficient_context → фиксированный ответ, модель не вызывается
  └─ evidence_found → один вызов переданного generate(prompt)

Пакет контекста включает id, source, позиции, score и текст. Инструкция просит указывать ID после проверяемых утверждений. Это не делает ответ автоматически верным, но позволяет увидеть, на какой фрагмент он опирается.

Здесь важны два уровня отказа:

  1. retriever не нашёл ни одного положительного совпадения — генератор не вызывается;
  2. retriever нашёл тематически похожий текст, но в нём нет ответа — инструкция модели требует сказать «Недостаточно контекста для ответа».

Второй уровень нельзя надёжно проверить одним cosine-score: это уже проверка содержания ответа, к которой мы вернёмся в 3.5.

Что изменится с нейросетевыми embeddings

TF-IDF видит совпадение поверхностных форм слов. Плотный нейросетевой embedding строит вектор фиксированной длины из обученного представления текста. Такой retriever часто лучше находит перефразы и смысловую близость, поэтому может связать «автора финального документа» с «ответственным за итоговый отчёт».

Но слово «может» здесь принципиально:

  • модель embeddings может плохо знать язык или домен;
  • короткий запрос может иметь несколько смыслов;
  • плохой chunking портит вход для любого представления;
  • top-k всё равно может пропустить нужный фрагмент;
  • высокий score не является доказательством ответа.

Поэтому смена TF-IDF на нейросетевой способ представления не отменяет expected_ids, негативные запросы, provenance и решение «ничего не найдено». В 3.4 мы заменим одноразовый словарь на сохраняемое хранилище и подключим готовые embeddings; сам контракт проверки останется тем же.

Типичные ошибки

  • Индексировать строки без ID и источника. Найденный текст нельзя связать с местом документа и проверить.
  • Всегда возвращать ровно k записей. При нулевых scores это случайные чанки, а не доказательства.
  • Считать score вероятностью истины. Cosine измеряет близость представлений и ничего не гарантирует о правильности будущего ответа.
  • Назначить универсальный порог. 0.3 не становится хорошим значением без проверки на запросах конкретного корпуса.
  • Подбирать порог по одному удачному вопросу. Так легко улучшить демонстрацию и сломать остальные случаи.
  • Считать пустую выдачу всегда правильной. Иногда вопрос действительно вне корпуса, а иногда лексический retriever пропустил существующий синоним.
  • Оценивать только финальный ответ. Без ожидаемых ID невозможно понять, поиск не нашёл доказательство или генератор проигнорировал его.
  • Считать соседние overlap-чанки независимыми подтверждениями. Проверяй позиции и повторяющийся текст.
  • Переходить к vector DB до проверки retrieval. Хранилище ускорит и сохранит индекс, но не исправит неверный критерий релевантности.

Что сознательно осталось за границей

  • Chroma, FAISS, pgvector, add/query, персистентность и приближённый поиск по индексу — урок 3.4.
  • Выбор конкретного API и модели embeddings — практический перенос 3.4.
  • Морфологический анализ, полнотекстовый BM25 и языковые анализаторы — возможные улучшения lexical retrieval, но не нужны для первого наблюдаемого механизма.
  • Hybrid retrieval, RRF, сравнительный retrieval-eval и граница оценки ответа — урок 3.5.
  • Универсальные k и min_score не задаются: их выбирают по своему корпусу и проверочному набору.

"""Traceable lexical retrieval for lesson 3.3.

The implementation is deliberately small and offline.  It keeps the provenance
records produced in lesson 3.2, ranks them with TF-IDF and cosine similarity,
abstains when there is no lexical evidence, and evaluates retrieval separately
from answer generation.
"""

from __future__ import annotations

import math
import re
from collections import Counter
from collections.abc import Iterable, Mapping, Sequence
from numbers import Real
from typing import Any


# A short, inspectable list is enough for the exercise.  It prevents a query
# such as "и в на" from becoming evidence.  It is not a universal language
# model or a production Russian stop-word list.
STOP_WORDS = frozenset(
    {
        "а",
        "без",
        "в",
        "во",
        "для",
        "до",
        "за",
        "и",
        "из",
        "или",
        "к",
        "как",
        "на",
        "не",
        "но",
        "о",
        "об",
        "от",
        "по",
        "с",
        "со",
        "у",
        "что",
        "это",
    }
)

REQUIRED_CHUNK_FIELDS = ("id", "source", "text")


def _tokens(text: str) -> list[str]:
    """Return lowercase word tokens without the exercise stop words."""
    if not isinstance(text, str):
        raise TypeError("text must be a string")
    return [
        token
        for token in re.findall(r"\w+", text.lower())
        if token not in STOP_WORDS
    ]


def _tfidf(tokens: Sequence[str], idf: Mapping[str, float]) -> dict[str, float]:
    """Build a sparse TF-IDF vector represented as ``{term: weight}``."""
    counts = Counter(tokens)
    total = sum(counts.values())
    if total == 0:
        return {}
    return {
        term: (count / total) * idf.get(term, 0.0)
        for term, count in counts.items()
        if term in idf
    }


def _validated_chunk(chunk: Any, position: int) -> dict[str, Any]:
    if not isinstance(chunk, Mapping):
        raise TypeError(f"chunk at position {position} must be a mapping")

    record = dict(chunk)
    missing = [field for field in REQUIRED_CHUNK_FIELDS if field not in record]
    if missing:
        raise ValueError(
            f"chunk at position {position} is missing fields: {', '.join(missing)}"
        )
    for field in REQUIRED_CHUNK_FIELDS:
        if not isinstance(record[field], str) or not record[field].strip():
            raise ValueError(
                f"chunk at position {position} has invalid {field!r}"
            )
    return record


def build_index(chunks: Iterable[Mapping[str, Any]]) -> dict[str, Any]:
    """Build an in-memory TF-IDF index and preserve every chunk field."""
    if isinstance(chunks, (str, bytes)) or not isinstance(chunks, Iterable):
        raise TypeError("chunks must be an iterable of traceable records")

    records = [
        _validated_chunk(chunk, position)
        for position, chunk in enumerate(chunks)
    ]
    ids = [record["id"] for record in records]
    if len(ids) != len(set(ids)):
        raise ValueError("chunk ids must be unique")

    tokenized = [_tokens(record["text"]) for record in records]
    document_frequency: Counter[str] = Counter()
    for tokens in tokenized:
        document_frequency.update(set(tokens))

    count = len(records)
    idf = {
        term: math.log((count + 1) / (frequency + 1)) + 1
        for term, frequency in document_frequency.items()
    }
    return {
        "chunks": records,
        "idf": idf,
        "vectors": [_tfidf(tokens, idf) for tokens in tokenized],
    }


def _cosine(a: Mapping[str, float], b: Mapping[str, float]) -> float:
    """Return cosine similarity for two sparse vectors."""
    common = set(a) & set(b)
    dot = sum(a[term] * b[term] for term in common)
    norm_a = math.sqrt(sum(value * value for value in a.values()))
    norm_b = math.sqrt(sum(value * value for value in b.values()))
    return dot / (norm_a * norm_b) if norm_a and norm_b else 0.0


def _validate_search_params(k: int, min_score: float) -> None:
    if isinstance(k, bool) or not isinstance(k, int) or k <= 0:
        raise ValueError("k must be a positive integer")
    if (
        isinstance(min_score, bool)
        or not isinstance(min_score, Real)
        or not 0 <= min_score <= 1
    ):
        raise ValueError("min_score must be a number between 0 and 1")


def search(
    query: str,
    index: Mapping[str, Any],
    k: int = 3,
    min_score: float = 0.0,
) -> list[dict[str, Any]]:
    """Return at most ``k`` positive lexical matches with provenance.

    ``min_score=0`` means "accept any positive lexical evidence", not "return
    zero-score chunks".  A higher threshold must be selected against an
    evaluation set for the actual corpus.
    """
    if not isinstance(query, str):
        raise TypeError("query must be a string")
    _validate_search_params(k, min_score)

    query_vector = _tfidf(_tokens(query), index["idf"])
    if not query_vector:
        return []

    scored = [
        (_cosine(query_vector, vector), position)
        for position, vector in enumerate(index["vectors"])
    ]
    # The original chunk order is the explicit tie-breaker.
    scored.sort(key=lambda item: (-item[0], item[1]))

    hits = []
    for score, position in scored:
        if score <= 0 or score < min_score:
            continue
        hit = dict(index["chunks"][position])
        hit["score"] = round(score, 4)
        hits.append(hit)
        if len(hits) == k:
            break
    return hits


def evaluate(
    cases: Iterable[Mapping[str, Any]],
    index: Mapping[str, Any],
    k: int = 3,
    min_score: float = 0.0,
) -> dict[str, Any]:
    """Evaluate expected IDs and expected abstentions on a small query set."""
    _validate_search_params(k, min_score)

    details = []
    answerable_total = 0
    answerable_hits = 0
    no_answer_total = 0
    correct_abstentions = 0

    for position, case in enumerate(cases):
        if not isinstance(case, Mapping):
            raise TypeError(f"case at position {position} must be a mapping")
        query = case.get("query")
        expected_ids = case.get("expected_ids")
        if not isinstance(query, str) or not query.strip():
            raise ValueError(f"case at position {position} needs a non-empty query")
        if (
            isinstance(expected_ids, (str, bytes))
            or not isinstance(expected_ids, Sequence)
            or any(not isinstance(item, str) for item in expected_ids)
        ):
            raise ValueError(
                f"case at position {position} needs expected_ids as a list of strings"
            )

        expected = set(expected_ids)
        hits = search(query, index, k=k, min_score=min_score)
        retrieved_ids = [hit["id"] for hit in hits]
        if expected:
            answerable_total += 1
            passed = bool(expected & set(retrieved_ids))
            answerable_hits += int(passed)
        else:
            no_answer_total += 1
            passed = not retrieved_ids
            correct_abstentions += int(passed)

        details.append(
            {
                "query": query,
                "expected_ids": list(expected_ids),
                "retrieved_ids": retrieved_ids,
                "passed": passed,
            }
        )

    total = len(details)
    passed_total = answerable_hits + correct_abstentions
    return {
        "k": k,
        "min_score": min_score,
        "total": total,
        "passed": passed_total,
        "accuracy": round(passed_total / total, 3) if total else 0.0,
        "answerable": {
            "total": answerable_total,
            "hits": answerable_hits,
            "hit_rate_at_k": (
                round(answerable_hits / answerable_total, 3)
                if answerable_total
                else 0.0
            ),
        },
        "no_answer": {
            "total": no_answer_total,
            "correct_abstentions": correct_abstentions,
            "accuracy": (
                round(correct_abstentions / no_answer_total, 3)
                if no_answer_total
                else 0.0
            ),
        },
        "cases": details,
    }


if __name__ == "__main__":

def _location(hit: Mapping[str, Any]) -> str:
    start = hit.get("word_start")
    end = hit.get("word_end")
    if isinstance(start, int) and isinstance(end, int):
        return f"слова {start}:{end}"
    return "позиция не указана"


def build_prompt(query: str, evidence: list[dict[str, Any]]) -> str:
    """Build a grounded prompt from non-empty traceable evidence."""
    if not evidence:
        raise ValueError("evidence must be non-empty")

    blocks = []
    for hit in evidence:
        blocks.append(
            f"[{hit['id']}]\n"
            f"Источник: {hit['source']}, {_location(hit)}, score={hit['score']}\n"
            f"Текст: {hit['text']}"
        )
    context = "\n\n".join(blocks)
    return (
        "Ответь на вопрос только по фрагментам ниже. "
        "После каждого проверяемого утверждения укажи ID фрагмента в квадратных "
        "скобках. Если найденные фрагменты не содержат ответа, прямо скажи: "
        "«Недостаточно контекста для ответа».\n\n"
        f"Фрагменты:\n{context}\n\n"
        f"Вопрос: {query}\n"
        "Ответ:"
    )


def prepare_request(
    query: str,
    index: Mapping[str, Any],
    k: int = 3,
    min_score: float = 0.0,
) -> dict[str, Any]:
    """Retrieve evidence and prepare a request without calling a model."""
    evidence = search(query, index, k=k, min_score=min_score)
    if not evidence:
        return {
            "status": "insufficient_context",
            "query": query,
            "evidence": [],
            "prompt": None,
        }
    return {
        "status": "evidence_found",
        "query": query,
        "evidence": evidence,
        "prompt": build_prompt(query, evidence),
    }


def answer_with(
    query: str,
    index: Mapping[str, Any],
    generate: Callable[[str], str],
    k: int = 3,
    min_score: float = 0.0,
) -> dict[str, Any]:
    """Call ``generate`` only when retrieval produced positive evidence."""
    if not callable(generate):
        raise TypeError("generate must be callable")

    request = prepare_request(query, index, k=k, min_score=min_score)
    if request["status"] == "insufficient_context":
        return {
            **request,
            "answer": "Недостаточно контекста для ответа.",
            "generator_called": False,
        }

    answer = generate(request["prompt"])
    if not isinstance(answer, str) or not answer.strip():
        raise ValueError("generate must return a non-empty string")
    return {
        **request,
        "answer": answer,
        "generator_called": True,
    }
