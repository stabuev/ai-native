Урок 6.1 · Tool use / function calling изнутри

Фаза 6 — Инструменты и протоколы (MCP) · Результат фазы: Объяснить tool use изнутри и поднять собственный MCP-сервер с контролем доступа.

Результат урока: собрать офлайн client-side tool-use runtime, в котором модель получает пользовательский запрос и публичные схемы, возвращает связанный идентификатором tool_call, а локальный код проверяет allowlist и аргументы до исполнения, возвращает tool_result и останавливает цикл по финалу или лимиту; затем доказать границу исполнения успешным и отклонённым trace.

Requires: обязательный маршрут работает с Python 3 и pytest, без сети и API-ключа. Сопоставление с одним реальным provider API в конце факультативно и требует только того доступа, который у тебя уже есть.

Это вход в Фазу 6 — переход от локальных функций к инструментам модели. В 5.5 Python-код сам вызывал validate_packet, detect_current_anomaly и build_report. Модель могла предложить объяснение, но не выбирала эти функции и не формировала запрос на их исполнение. Теперь между моделью и локальным кодом появится явный протокол.

MOTTO. Модель предлагает вызов; runtime решает, можно ли его исполнить.

PROBLEM — почему «модель сходила в базу» мешает отладке

Фраза «модель вызвала функцию и получила решение отчёта» склеивает несколько разных действий. Из-за этого трудно ответить на практические вопросы:

  • кто видел пользовательский запрос;
  • откуда модель узнала о доступных инструментах;
  • кто проверил имя и аргументы;
  • какой код действительно исполнился;
  • к какому вызову относится результат;
  • что произойдёт при ошибке или бесконечном повторе.

Для пользовательского client-side инструмента модель не получает Python-функцию и не исполняет её. Приложение передаёт модели только публичное описание. Модель возвращает структурированное предложение вызова, а контролируемая часть приложения — далее будем называть её runtime — проверяет предложение и лишь затем может вызвать разрешённую функцию.

У провайдеров бывают и server-side инструменты, которые исполняет их инфраструктура. Это другой маршрут. В Build It мы сознательно собираем client-side вариант: именно в нём видна граница между недетерминированным предложением модели и локальным исполнением.

CONCEPT — шесть объектов одного цикла

1. Пользовательский запрос

Цикл начинается не с пустой истории, а с задачи человека. Например:

Какое решение у запуска phase-5-paid-revenue-q2?

Без этого объекта учебная «модель» может заранее знать, что надо вызвать, и практика скроет выбор инструмента внутри stub-кода.

2. Публичная спецификация инструмента

Инструмент в этом уроке — разрешённая runtime операция, которую модель может предложить вызвать. Модель видит только:

  • name — стабильное имя;
  • description — что операция делает и когда её выбирать;
  • input_schema — допустимую форму аргументов.
{
  "name": "get_release_decision",
  "description": "Получить сохранённое решение quality gate по точному run_id",
  "input_schema": {
    "type": "object",
    "properties": {
      "run_id": {"type": "string"}
    },
    "required": ["run_id"],
    "additionalProperties": false
  }
}

Схема опирается на JSON Schema из 2.4, но учебный валидатор 6.1 поддерживает только объявленное подмножество верхнего уровня: type: object, properties, required, additionalProperties и enum. Мы не называем небольшой Python-код универсальной реализацией стандарта.

3. Локальный реестр

Реестр, или allowlist, — словарь разрешённых инструментов внутри приложения. В нём публичный контракт связан с настоящей Python-функцией:

get_release_decision
├── description
├── input schema
└── fn = _get_release_decision    ← остаётся только в runtime

Модель не должна получать fn. Иначе учебный интерфейс перестаёт показывать границу доверия: публичная схема смешивается с исполняемым объектом процесса.

4. tool_call

Если модель считает инструмент нужным, она возвращает не результат, а предложение:

{
  "type": "tool_call",
  "id": "call-release-1",
  "name": "get_release_decision",
  "arguments": {"run_id": "phase-5-paid-revenue-q2"}
}

id нужен не для красоты. Один ответ может содержать несколько вызовов, а история — много результатов. Идентификатор позволяет доказать, какому вызову соответствует конкретный tool_result. В обязательной практике вызовы последовательные, но связь уже явная.

5. Проверка и исполнение в runtime

Dispatcher — функция-переключатель между предложением модели и локальным кодом. До исполнения она последовательно проверяет:

есть непустой call ID?
→ имя находится в локальном allowlist?
→ arguments имеют форму object?
→ обязательные поля присутствуют?
→ типы, enum и запрет лишних полей соблюдены?
→ только после этого fn(**arguments)

Схема не доказывает, что действие разрешено пользователю, безопасно для данных или семантически разумно. Полный контроль прав, write-операций и подтверждений будет в 6.5. Здесь схема решает более узкую задачу: кривой вызов не должен дойти до Python-функции.

6. tool_result и следующий ход

После успешного исполнения runtime создаёт связанный результат:

{
  "type": "tool_result",
  "call_id": "call-release-1",
  "ok": true,
  "content": {
    "decision": "publish",
    "metric_id": "paid_revenue",
    "as_of": "2026-07-01"
  }
}

Этот объект добавляется в историю и снова передаётся модели. Теперь она может вернуть:

  • новый tool_call, если нужен ещё один разрешённый шаг;
  • final, если данных достаточно;
  • исправленный вызов, если предыдущий результат был ok: false.

Runtime, а не модель, считает число вызовов. Если новый вызов превышает max_tool_calls, он блокируется до исполнения.

Полный инвариант

user request
    │
    ├── public tool specs: name + description + input_schema
    ▼
model_fn(history, tool_specs)
    │
    ├── final ─────────────────────────────────────────────► stop
    │
    └── tool_call(id, name, arguments)
              │
              ▼
       runtime / dispatcher
       1. call ID
       2. local allowlist
       3. declared schema subset
       4. max_tool_calls
              │
       rejected│                         accepted
              ▼                             ▼
 tool_result(ok=false, error)    fn(**arguments)
              │                             │
              └──────────────┬──────────────┘
                             ▼
                 tool_result(call_id, ...)
                             │
                             └──────────────► model_fn

У разных провайдеров поля называются по-разному, но проверяемый инвариант одинаков: публичный контракт → связанный вызов → контролируемое исполнение → связанный результат → продолжение или финал.

ПРЕДСКАЖИ TRACE ДО КОДА

Не запускай демо сразу. Сначала ответь:

  1. Получит ли модель Python-функцию _get_release_decision?
  2. Что исполнится раньше: проверка run_id или тело функции?
  3. Какие два поля должны совпасть у вызова и результата?
  4. Увидит ли модель результат, если runtime не добавит его в историю?
  5. Может ли publish из 5.5 быть придуман моделью заново?

Правильная модель:

  • модель видит спецификацию, но не callable;
  • аргументы проверяются до исполнения;
  • tool_call.id == tool_result.call_id;
  • невозвращённый результат для следующего хода не существует;
  • инструмент только читает сохранённое решение, а policy 5.5 остаётся

детерминированной.

РАЗБОР УСПЕШНОГО TRACE

В эталонном демо есть два инструмента: add как простая проверка механики и get_release_decision как мост из Фазы 5. Детерминированный stub заменяет LLM: это тестовый двойник, который всегда возвращает известные ответы. Он не измеряет качество реальной модели, зато позволяет проверить runtime без сети.

1. history = [user request]
2. model_fn получает history и public specs без fn
3. model_fn → tool_call(id=call-release-1,
                        name=get_release_decision,
                        arguments={run_id: phase-5-paid-revenue-q2})
4. dispatch → allowlist PASS → schema PASS → локальная функция
5. runtime → tool_result(call_id=call-release-1, ok=true, content=...)
6. model_fn видит result → final("Решение: publish ...")

Модель не вычислила quality gate. Она выбрала read-only инструмент и сформировала аргументы. Решение publish взято из локальной проверенной фикстуры.

РАЗБОР ОТКЛОНЁННОГО ВЫЗОВА

Пусть модель забудет обязательный run_id:

{
  "type": "tool_call",
  "id": "call-bad",
  "name": "get_release_decision",
  "arguments": {}
}

Dispatcher не вызывает функцию и возвращает в историю:

{
  "type": "tool_result",
  "call_id": "call-bad",
  "ok": false,
  "error": "невалидные аргументы: нет обязательного аргумента: run_id"
}

Следующий ход модели может предложить исправленный вызов с новым ID. В тесте отдельно проверяется, что функция реально исполняется только один раз — после исправления. Так мы отличаем красивое сообщение об ошибке от доказанного отсутствия побочного эффекта.

BUILD IT — собери runtime с нуля

Работай в личном репозитории, курс клонировать не нужно. Из корня ai-native-work создай:

course-work/phase-6/6.1-tool-use/
├── code/
│   ├── function_calling.py
│   └── test_function_calling.py
└── tool-contract-and-trace.md

Скопируй тесты из блока «Исходники урока». Затем реализуй четыре границы.

Шаг 1. Отдели public specs от локального реестра

Создай Tool(name, description, schema, fn) и функцию:

public_tool_specs(registry) -> list[dict]

Она возвращает только name, description и глубокую копию input_schema. Callable не должен попасть в список, передаваемый модели; изменение возвращённой схемы не должно менять локальный реестр.

Шаг 2. Реализуй ограниченный валидатор

validate_args(args, schema) -> list[str]

Поддержи только явно нужное уроку подмножество:

  • type: object для всего arguments;
  • properties верхнего уровня;
  • required;
  • простые типы string, number, integer, boolean, array, object, null;
  • enum;
  • additionalProperties: false.

Учти Python-ловушку: isinstance(True, int) возвращает True, но JSON boolean не должен проходить как integer или number. NaN и бесконечность тоже не являются допустимым JSON number для этого runtime.

Шаг 3. Построй dispatcher

dispatch(tool_call, registry) -> tool_result

До fn(**arguments) проверь ID, имя, allowlist и аргументы. Успех возвращает {type, call_id, ok, content}. Неизвестный инструмент и невалидный вызов поднимают ToolError. Failure-тест с функцией-шпионом должен доказать, что её тело не выполнялось.

Шаг 4. Собери bounded loop

run(model_fn, registry, user_request, *, max_tool_calls=3)
    -> (answer, trace)

Требования:

  1. История начинается с явного user_request.
  2. model_fn получает копии history и public specs.
  3. Допустимы только tool_call и final.
  4. Вызов записывается отдельно от связанного результата.
  5. Ошибка allowlist или schema превращается в tool_result(ok=false) и может быть

исправлена следующим вызовом.

  1. Исключение внутри уже разрешённой Python-функции не маскируется под schema error.
  2. Новый вызов сверх max_tool_calls блокируется до исполнения.

Критерий готовности к переносу

python -m pytest course-work/phase-6/6.1-tool-use/code -q
python course-work/phase-6/6.1-tool-use/code/function_calling.py

Зелёными должны быть 11 behavioral tests. Они проверяют public/private границу, поддерживаемое подмножество схемы, bool как отдельный тип, call ID, allowlist, отсутствие исполнения после отказа, явный user request, порядок trace, исправленный повтор, неизвестный envelope и лимит вызовов.

После тестов объясни своими словами:

  1. почему schema compliance ещё не является разрешением на действие;
  2. почему call_id входит в корректность, а не только в логирование;
  3. какое утверждение доказывает failure-тест с функцией-шпионом;
  4. что stub доказывает о runtime и чего не доказывает о реальной модели.

Внизу, в «Исходниках урока», остаются три пути выполнения: собрать самому, подсмотреть эталон или делегировать черновик ИИ. Критерии приёмки одинаковы.

САМОСТОЯТЕЛЬНЫЙ ПЕРЕНОС

add и get_release_decision показывают механизм. Теперь спроектируй один собственный read-only инструмент, не копируя их контракт.

Предпочтительный перенос из своей работы Фазы 5:

  • get_failed_checks(run_id) — вернуть сохранённые проваленные проверки;
  • get_metric_definition(metric_id) — прочитать локальный semantic contract;
  • другой безопасный lookup над собственной нечувствительной фикстурой.

Если Фаза 5 пройдена офлайн без сохранённых данных, создай маленькую вымышленную фикстуру lookup_status(item_id). Не подключай реальную БД и не копируй чувствительные данные: в этом уроке оценивается протокол, а не интеграция.

Для собственного инструмента:

  1. сформулируй ситуацию, когда его нужно и не нужно выбирать;
  2. напиши public spec без callable;
  3. добавь его в локальный allowlist;
  4. сохрани один успешный trace;
  5. намеренно сломай аргумент и сохрани отклонённый trace;
  6. докажи, что при отказе функция не исполнилась;
  7. вернись к корректному вызову и повтори прогон.

Если делегируешь проектирование ИИ, используй рамку 4D:

  • Delegation: отдай черновик description, схемы или тестовых случаев, но не решение о фактическом исполнении.
  • Description: передай назначение функции, реальные доступные поля, read-only границу, поддерживаемое подмножество схемы и формат trace.
  • Discernment: проверь, не выдуманы ли поля, ловит ли описание неверный выбор, связаны ли call/result и доказан ли отказ до side effect.
  • Diligence: реализуй принятый контракт локально, запусти success/failure tests и сохрани ответственность за allowlist.

ФАКУЛЬТАТИВНО — сопоставь core envelope с одним API

Обязательный результат уже доказан офлайн. Если у тебя есть подходящий API-ключ, выбери одного провайдера и сопоставь его поля с учебным envelope. Не пытайся запускать все варианты.

ЧАСТЫЕ ОШИБКИ

  • Начинать history пустой. Тогда stub скрыто хранит исходную задачу, и студент не видит полный интерфейс цикла.
  • Передавать модели реестр вместе с fn. Модели нужен публичный контракт, а callable остаётся в доверенной части процесса.
  • Называть мини-валидатор JSON Schema validator. Он проверяет только задокументированное подмножество и не заменяет промышленную библиотеку.
  • Исполнять до проверки. Сообщение об ошибке после побочного эффекта уже не делает вызов безопасным.
  • Не связывать call и result ID. При двух вызовах результаты можно перепутать даже при правильных значениях.
  • Считать bool числом из-за Python. Типы runtime должны следовать JSON-контракту, а не случайной иерархии классов языка.
  • Не возвращать failure result модели. Без структурированной ошибки она не может исправить аргументы в следующем ходе.
  • Считать stub проверкой качества LLM. Детерминированный двойник проверяет оркестрацию; выбор инструментов реальной моделью требует отдельного eval.
  • Делать API-ветку обязательной. Контракт урока должен завершаться без платного доступа и сети.
  • Переносить право решения quality gate в модель. Инструмент может прочитать решение 5.5, но не переписать policy или объявить publish без gate.

ЧТО СОЗНАТЕЛЬНО НЕ ВХОДИТ В УРОК

"""Минимальный client-side tool-use runtime для урока 6.1.

Модель получает пользовательский запрос и только публичные описания инструментов.
Она может вернуть ``tool_call`` или ``final``. Runtime сопоставляет вызов с локальным
allowlist, проверяет аргументы, исполняет Python-функцию и возвращает связанный
``tool_result``. Детерминированный stub заменяет сеть и LLM, но не скрывает протокол.

Валидатор ниже поддерживает намеренно ограниченное подмножество JSON Schema:
``type: object``, ``properties``, ``required``, ``additionalProperties`` и ``enum``
для полей верхнего уровня. Это учебная граница, а не реализация стандарта целиком.
"""

from collections.abc import Callable, Mapping
from copy import deepcopy
from dataclasses import dataclass
import json
import math
from typing import Any


@dataclass(frozen=True)
class Tool:
    """Публичный контракт инструмента и скрытая локальная реализация."""

    name: str
    description: str
    schema: dict[str, Any]
    fn: Callable[..., Any]


class ToolError(Exception):
    """Вызов нельзя безопасно передать локальному инструменту."""


def public_tool_specs(registry: Mapping[str, Tool]) -> list[dict[str, Any]]:
    """Вернуть только name, description и input schema — без Python callable."""

    return [
        {
            "name": tool.name,
            "description": tool.description,
            "input_schema": deepcopy(tool.schema),
        }
        for tool in registry.values()
    ]


def _matches_json_type(value: Any, expected: str) -> bool:
    """Проверить базовый JSON-тип без Python-ловушки ``bool`` как ``int``."""

    if expected == "string":
        return isinstance(value, str)
    if expected == "number":
        return (
            isinstance(value, (int, float))
            and not isinstance(value, bool)
            and math.isfinite(value)
        )
    if expected == "integer":
        return isinstance(value, int) and not isinstance(value, bool)
    if expected == "boolean":
        return isinstance(value, bool)
    if expected == "array":
        return isinstance(value, list)
    if expected == "object":
        return isinstance(value, dict)
    if expected == "null":
        return value is None
    return False


def validate_args(args: Any, schema: Mapping[str, Any]) -> list[str]:
    """Проверить аргументы по объявленному учебному подмножеству JSON Schema."""

    if not isinstance(args, Mapping):
        return ["arguments: ожидался object"]
    if schema.get("type", "object") != "object":
        return ["schema: поддерживается только type=object"]

    errors: list[str] = []
    properties = schema.get("properties", {})
    required = schema.get("required", [])

    for name in required:
        if name not in args:
            errors.append(f"нет обязательного аргумента: {name}")

    if schema.get("additionalProperties") is False:
        for name in args:
            if name not in properties:
                errors.append(f"неизвестный аргумент: {name}")

    for name, value in args.items():
        rule = properties.get(name)
        if not isinstance(rule, Mapping):
            continue
        expected = rule.get("type")
        if expected and not _matches_json_type(value, expected):
            errors.append(f"{name}: ожидался {expected}")
            continue
        if "enum" in rule and value not in rule["enum"]:
            allowed = ", ".join(map(str, rule["enum"]))
            errors.append(f"{name}: значение не входит в enum [{allowed}]")

    return errors


def dispatch(
    tool_call: Mapping[str, Any], registry: Mapping[str, Tool]
) -> dict[str, Any]:
    """Проверить allowlist и аргументы, затем вернуть связанный tool_result."""

    if not isinstance(tool_call, Mapping):
        raise ToolError("tool_call должен быть object")

    call_id = tool_call.get("id")
    name = tool_call.get("name")
    arguments = tool_call.get("arguments", {})
    if not isinstance(call_id, str) or not call_id.strip():
        raise ToolError("tool_call.id обязателен")
    if not isinstance(name, str) or not name.strip():
        raise ToolError("tool_call.name обязателен")
    if name not in registry:
        raise ToolError(f"неизвестный инструмент: {name}")

    errors = validate_args(arguments, registry[name].schema)
    if errors:
        raise ToolError("невалидные аргументы: " + "; ".join(errors))

    content = registry[name].fn(**dict(arguments))
    return {
        "type": "tool_result",
        "call_id": call_id,
        "ok": True,
        "content": content,
    }


def run(
    model_fn: Callable[[list[dict[str, Any]], list[dict[str, Any]]], Mapping[str, Any]],
    registry: Mapping[str, Tool],
    user_request: str,
    *,
    max_tool_calls: int = 3,
) -> tuple[Any, list[dict[str, Any]]]:
    """Вести model → tool_call → tool_result до final с ограничением вызовов."""

    if not isinstance(user_request, str) or not user_request.strip():
        raise ValueError("user_request должен быть непустой строкой")
    if (
        not isinstance(max_tool_calls, int)
        or isinstance(max_tool_calls, bool)
        or max_tool_calls < 1
    ):
        raise ValueError("max_tool_calls должен быть положительным целым")

    history: list[dict[str, Any]] = [
        {"type": "user", "content": user_request}
    ]
    tool_specs = public_tool_specs(registry)
    used_calls = 0

    while True:
        step = model_fn(deepcopy(history), deepcopy(tool_specs))
        if not isinstance(step, Mapping):
            raise ToolError("модель должна вернуть object")
        step = dict(step)

        if step.get("type") == "final":
            if "answer" not in step:
                raise ToolError("final должен содержать answer")
            history.append(deepcopy(step))
            return step["answer"], history

        if step.get("type") != "tool_call":
            raise ToolError("ожидался ответ type=tool_call или type=final")

        call_id = step.get("id")
        if not isinstance(call_id, str) or not call_id.strip():
            raise ToolError("tool_call.id обязателен для связи с result")
        if used_calls >= max_tool_calls:
            raise ToolError("превышен лимит max_tool_calls")

        used_calls += 1
        history.append(deepcopy(step))
        try:
            result = dispatch(step, registry)
        except ToolError as error:
            result = {
                "type": "tool_result",
                "call_id": call_id,
                "ok": False,
                "error": str(error),
            }
        history.append(result)


REPORTS = {
    "phase-5-paid-revenue-q2": {
        "decision": "publish",
        "metric_id": "paid_revenue",
        "as_of": "2026-07-01",
    },
    "phase-5-unfinished": {
        "decision": "block",
        "metric_id": "paid_revenue",
        "as_of": "2026-07-01",
    },
}


def _add(a: float, b: float) -> float:
    return a + b


def _get_release_decision(run_id: str) -> dict[str, str]:
    return deepcopy(REPORTS[run_id])


REGISTRY = {
    "add": Tool(
        name="add",
        description="Сложить два числа, когда пользователю нужен точный расчёт суммы.",
        schema={
            "type": "object",
            "properties": {
                "a": {"type": "number"},
                "b": {"type": "number"},
            },
            "required": ["a", "b"],
            "additionalProperties": False,
        },
        fn=_add,
    ),
    "get_release_decision": Tool(
        name="get_release_decision",
        description=(
            "Получить сохранённое решение quality gate по точному run_id; "
            "использовать для чтения результата, но не для изменения policy."
        ),
        schema={
            "type": "object",
            "properties": {
                "run_id": {
                    "type": "string",
                    "enum": list(REPORTS),
                }
            },
            "required": ["run_id"],
            "additionalProperties": False,
        },
        fn=_get_release_decision,
    ),
}


DEMO_REQUEST = "Какое решение у запуска phase-5-paid-revenue-q2?"


def _demo_model(
    history: list[dict[str, Any]], tool_specs: list[dict[str, Any]]

    """Детерминированный protocol stub: не оценивает качество реальной LLM."""

    available = {spec["name"] for spec in tool_specs}
    results = [event for event in history if event.get("type") == "tool_result"]

    if not results:
        if "get_release_decision" not in available:
            return {"type": "final", "answer": "Инструмент недоступен."}
        return {
            "type": "tool_call",

    result = results[-1]
    if not result["ok"]:
        return {"type": "final", "answer": f"Вызов отклонён: {result['error']}"}

    report = result["content"]
    return {
        "type": "final",
        "answer": (
            f"Решение: {report['decision']} "
            f"для {report['metric_id']} на {report['as_of']}."
        ),
    }


if __name__ == "__main__":
    answer, trace = run(_demo_model, REGISTRY, DEMO_REQUEST)

## 8. Рубрика приёмки

Артефакт принят, если одновременно выполнены критерии:

- пользовательская задача требует внешнего read-only результата, а не просто генерации;
- public spec не содержит callable, секретов и выдуманных полей;
- `description` различает ситуацию применения и похожий неверный выбор;
- схема соответствует фактической сигнатуре и поддерживаемому подмножеству валидатора;
- успешный trace начинается с user request и заканчивается final после result;
- `tool_call.id` совпадает с `tool_result.call_id` в обоих trace;
- failure case правдоподобен и доказанно не исполняет функцию;
- после одного исправления сохранён успешный повтор;
- вывод не приписывает stub качество реальной LLM и не превращает schema в permission;
- handoff сохраняет конкретную задачу и capability для архитектурного решения 6.2.
