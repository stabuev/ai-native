Урок 2.4 · Машинный контракт ответа: инструкция, схема и проверки

Фаза 2 — Промпт-инжиниринг · Результат фазы: Писать воспроизводимые промпты и измерять их качество через eval-harness. Результат урока: после урока студент сможет разделить постоянную инструкцию, динамический вход и схему ответа; выбрать режим ответа по схеме (structured output) вместо просьбы «верни JSON» или запроса на вызов функции; обработать завершённый, отклонённый и прерванный ответ; отличить правильную форму от правильного смысла и не передать непроверенные данные следующему шагу. Опора: проверяемый промпт-контракт из 2.1, граница источника из 1.4 и промежуточный артефакт с gate из 2.3 · Дальше: стабильная форма результатов позволит в 2.5 прогонять одни и те же случаи и считать метрики.

Requires (только для переноса в реальный API): платный API-ключ одного провайдера. Обязательный Build It работает офлайн, без ключей и сети.

В 2.3 мы разделили подготовку статуса на два шага. Сначала модель извлекала из заметок таблицу фактов, gate проверял её, и лишь затем принятая таблица переходила в редакторский шаг. Пока процесс выполняет человек в чате, Markdown-таблицы достаточно. Но программа не должна угадывать, как сегодня модель назвала столбец, чем обозначила неизвестный срок и добавила ли пояснение перед таблицей.

Теперь промежуточный артефакт становится машинным интерфейсом. Мы зададим его структуру отдельно от инструкции, проверим ответ послойно и остановим даже идеально оформленный объект, если его смысл не подтверждён заметками.

Главная мысль. Схема ограничивает форму ответа. Источник и правила проверяют его смысл. Одно не заменяет другое.

Почему команды «верни JSON» недостаточно

Допустим, следующий шаг ждёт такой объект:

{
  "facts": [
    {
      "category": "decision",
      "statement": "Пилот запускается 18 сентября для 10% пользователей iOS.",
      "evidence": "Пилот решили запустить 18 сентября для 10% пользователей iOS.",
      "owner": null,
      "deadline": "18 сентября"
    }
  ]
}

Если просто дописать к промпту «верни JSON», возможны разные сбои:

  • модель обернёт объект в тройные обратные кавычки или добавит вступление;
  • вместо массива facts вернёт один объект;
  • назовёт поле type, а не category;
  • пропустит owner либо запишет строку "не указан" вместо согласованного null;
  • сохранит правильную форму, но напишет, что пилот запускается для всех пользователей, хотя в источнике указано 10%.

Первые четыре ошибки относятся к форме. Последняя — к смыслу. Они требуют разных механизмов, поэтому сначала разделим контракт запроса на части.

Три части одного запроса

1. Постоянная инструкция

Системная инструкция — правила поведения модели, заданные разработчиком отдельно от меняющихся пользовательских данных. Часто говорят *system prompt*, но это не одно универсальное имя поля: у API разные названия.

Для нашего шага постоянная инструкция выглядит так:

Извлекай из заметок только явно сказанные решения, действия, условия,
открытые вопросы и метрики. Не превращай обсуждение в решение.
Для каждого утверждения сохраняй точный подтверждающий фрагмент источника.
Неизвестные owner и deadline возвращай как null: не придумывай значения.
Форма ответа задаётся отдельно переданной JSON Schema.

Она описывает работу и границы смысла. В неё не нужно копировать всю схему и заклинание «СТРОГО JSON БЕЗ ЕДИНОЙ ЛИШНЕЙ БУКВЫ»: специальный режим API надёжнее текстовой просьбы ограничивает форму. Инструкция направляет модель, но не является ни математической гарантией истины, ни защитной границей от недоверенных данных.

2. Динамический вход

Это конкретные заметки встречи, письмо, тикет или другой источник, меняющийся от вызова к вызову. Он передаётся как пользовательский ввод, а не склеивается с постоянными правилами без явной границы.

Разделение даёт практическую пользу:

  • постоянные правила можно версионировать и сравнивать;
  • один и тот же контракт применяется к разным входам;
  • исходный текст не маскируется под инструкцию разработчика;
  • в трейсе видно, что изменилось: правила, источник или схема.

3. Схема ответа

JSON Schema — стандартный JSON-документ, описывающий допустимую структуру другого JSON-документа. Здесь важны шесть конструкций:

  • type задаёт вид значения: объект, массив, строка или null;
  • properties перечисляет поля объекта и схемы их значений;
  • required перечисляет поля, которые должны присутствовать;
  • enum ограничивает значение явным списком допустимых вариантов;
  • anyOf разрешает соответствие одной из нескольких схем — например, строке или null;
  • additionalProperties: false запрещает незаявленные поля.

Упрощённый фрагмент нашей схемы:

{
  "type": "object",
  "properties": {
    "facts": {
      "type": "array",
      "items": {
        "type": "object",
        "properties": {
          "category": {
            "type": "string",
            "enum": [
              "decision",
              "action",
              "condition",
              "open_question",
              "metric"
            ]
          },
          "statement": {"type": "string"},
          "evidence": {"type": "string"},
          "owner": {
            "anyOf": [{"type": "string"}, {"type": "null"}]
          },
          "deadline": {
            "anyOf": [{"type": "string"}, {"type": "null"}]
          }
        },
        "required": [
          "category",
          "statement",
          "evidence",
          "owner",
          "deadline"
        ],
        "additionalProperties": false
      }
    }
  },
  "required": ["facts"],
  "additionalProperties": false
}

Это настоящая JSON Schema, а не учебный словарь вида {"priority": {"type": "integer", "required": true}}. Провайдеры поддерживают не весь стандарт, а его документированное подмножество, поэтому перед реальным запуском схему проверяют на выбранном API. В Build It схема уже дана: задача урока — не написать универсальный интерпретатор стандарта, а построить безопасную границу потребления ответа.

Четыре режима, которые легко перепутать

Structured output — режим API, в котором генерация ограничивается переданной схемой. Для успешно завершённого ответа поддерживаемая часть схемы обеспечивает нужные поля, типы и допустимые значения. Это сильнее текстовой просьбы и JSON mode.

Function calling, или вызов функции, — другой режим: модель не просто возвращает данные, а формирует структурированную просьбу приложению вызвать функцию с заданными аргументами. Приложение может проверить, исполнить или отклонить эту просьбу.

МеханизмЧто он даётЧего не даёт
Просьба «верни JSON»Направляет обычную генерациюНе гарантирует даже синтаксически корректный JSON
JSON modeСинтаксически корректный JSONНе гарантирует конкретные поля, типы и enum
Structured outputСоответствие поддерживаемой JSON Schema для нормального завершённого ответаНе доказывает истинность значений и не отменяет refusal/incomplete
Function callingСтруктурированную просьбу модели к приложению выполнить функциюСамо приложение всё равно решает, выполнять ли действие; это не просто формат финального ответа

Function calling понадобится позже, когда модель будет выбирать действие и передавать аргументы инструменту. Сейчас модель ничего не исполняет: нам нужен структурированный промежуточный результат. Поэтому основной механизм урока — response structured output, а не tool use.

OpenAI прямо разделяет function calling и text.format; Google — function calling и форматирование финального ответа; Anthropic — JSON outputs и strict tool use. Значит, общее слово «схема» ещё не делает эти операции взаимозаменяемыми: OpenAI, Google, Anthropic.

Почему одной схемы всё равно мало

Полезно рассматривать границу как четыре последовательных gate:

Gate 1: сначала статус, потом парсинг

Structured output действует не во всех исходах вызова. Модель может отказаться отвечать, а генерация может прерваться из-за лимита или фильтра. Такой результат нельзя пытаться «дочинить» вызовом json.loads.

Например:

{"status": "refusal", "reason": "safety policy"}
{"status": "incomplete", "reason": "max_output_tokens"}

Оба ответа должны остановиться на status gate. OpenAI возвращает статус incomplete и отдельные refusal-блоки, Anthropic — stop_reason вроде refusal или max_tokens; конкретные поля нормализует адаптер приложения. В офлайн-упражнении мы используем простой общий конверт, чтобы не смешивать причинную модель с каталогом SDK.

Gate 2: форма — это не самописный стандарт

В реальном приложении используй structured output провайдера и штатный типизированный парсер SDK — функцию, которая превращает ответ в объект языка по заданному типу и сообщает о несовпадении, — либо зрелую библиотеку проверки JSON Schema. Не нужно писать собственный универсальный валидатор стандарта.

Однако приложение всё равно отвечает за свою границу:

  • проверить статус до доступа к содержимому;
  • убедиться, что SDK действительно вернул ожидаемый тип;
  • применить ограничения предметной области, которые отсутствуют в схеме или не поддерживаются провайдером;
  • корректно обработать сохранённый старый ответ, тестовую фикстуру или данные из другого адаптера.

Поэтому Build It содержит точную предметную проверку объекта meeting facts. Она сознательно не называется реализацией JSON Schema.

Gate 3: присутствие доказательства

Для каждого факта мы сохраняем поле evidence с дословным фрагментом заметок. Простая детерминированная проверка может убедиться, что этот фрагмент действительно встречается в исходном тексте.

evidence = "для 10% пользователей iOS"

Если такого фрагмента нет, следующий шаг останавливается. Это полезная проверка, но не доказательство правильной интерпретации.

Gate 4: правильная форма может скрывать ложь

Рассмотрим объект:

{
  "facts": [
    {
      "category": "decision",
      "statement": "Пилот запускается для всех пользователей iOS.",
      "evidence": "для 10% пользователей iOS",
      "owner": null,
      "deadline": "18 сентября"
    }
  ]
}

Он является валидным JSON. Все поля и типы правильные. category входит в разрешённый enum. evidence дословно присутствует в заметках. И всё же утверждение ложно: 10% подменены всеми пользователями.

Именно поэтому успешные машинные проверки возвращают решение review, а не continue. Смысл проверяет человек, предметное правило или отдельный надёжно протестированный механизм. Google прямо рекомендует обрабатывать schema-compliant, но семантически неверные ответы; OpenAI и Anthropic отдельно документируют refusal и незавершённые ответы.

Разбор на сценарии из 2.3

Возьмём те же заметки:

Пилот решили запустить 18 сентября для 10% пользователей iOS.
До запуска служба безопасности должна согласовать схему доступа.
Рита отправит схему доступа на согласование до 12 сентября.
Если согласование не получено к 16 сентября, запуск переносится.
Обсудили перевод всех пользователей на новый поток в сентябре,
но решения по этому вопросу не приняли.

Последняя строка принципиальна. Если все ошибки объявить «ошибками JSON», студент научится доверять форме больше, чем источнику.

Неизвестное значение — не значение по умолчанию

В заметках не назначен ответственный за отчёт. Нельзя молча подставить условного владельца, priority=3 или urgent=false: валидная схема лишь сделает выдумку аккуратно оформленной.

Контракт должен явно различать:

  • значение известно → передать его;
  • значение допустимо не знать → передать null;
  • без значения продолжать опасно → остановить процесс или поставить needs_review;
  • бизнес действительно утвердил default → применить его и назвать правило, а не приписывать значение источнику.

В нашей схеме owner и deadline всегда присутствуют, но могут быть null. Так потребителю не приходится различать «модель забыла поле» и «в источнике нет значения».

BUILD IT: собери boundary gate

Задание: реализуй офлайн-модуль, который принимает нормализованный ответ провайдера, проводит машинные gates и не разрешает продолжение без зафиксированного смыслового решения.

Перед запуском. Создай в личном workspace папку course-work/2.4/. Из блока «Исходники урока» скопируй туда starter_structured_output.py под именем structured_output.py, а рядом — test_structured_output.py. Эталонный structured_output.py пока не открывай. Нужны Python 3 и pytest; сеть и API-ключ не требуются.

Готовыми даны:

  • SOURCE_NOTES — заметки из сценария 2.3;
  • SYSTEM_INSTRUCTION — постоянные правила извлечения;
  • OUTPUT_SCHEMA — настоящая JSON Schema для передачи провайдеру;
  • ALLOWED_CATEGORIES и FACT_FIELDS — предметные ограничения.

Реализуй четыре функции.

1. validate_structure(data) -> list[str]

Проверь точный контракт объекта:

  • корень — объект только с полем facts;
  • facts — непустой массив;
  • каждый элемент — объект ровно с category, statement, evidence, owner, deadline;
  • category входит в разрешённый набор;
  • statement и evidence — непустые строки;
  • owner и deadline — непустая строка либо None.

Верни все найденные ошибки. Пустой список означает только правильную форму.

2. validate_evidence(data, source) -> list[str]

Для каждого факта проверь, что evidence дословно входит в source. Верни путь ошибки вида facts[0].evidence: not found in source.

Не пытайся этой функцией доказать, что statement правильно истолковывает цитату. Это отдельный meaning gate.

3. inspect_response(response, source) -> dict

Поддержи три нормализованных вида ответа:

{"status": "completed", "output_text": "..."}
{"status": "refusal", "reason": "..."}
{"status": "incomplete", "reason": "..."}

Порядок проверок является частью контракта:

  1. не-completed ответ → decision="stop", stage="status";
  2. completed без корректного голого JSON → stop/syntax;
  3. ошибка предметной структуры → stop/structure;
  4. evidence отсутствует в источнике → stop/source;
  5. все машинные проверки пройдены → review/meaning, но не continue.

Возвращай единый отчёт:

{
    "decision": "stop | review | continue",
    "stage": "status | syntax | structure | source | meaning | accepted",
    "errors": [],
    "data": None
}

4. finish_semantic_review(report, approved, reason) -> dict

Функцию можно вызвать только для отчёта с decision="review". Непустой reason обязателен и при принятии, и при отклонении:

  • approved=True → continue/accepted;
  • approved=False → stop/meaning;
  • попытка пропустить проваленный машинный gate → ValueError.

Так в трейсе остаётся не только решение, но и его обоснование.

Прогон red → green

python -m pytest course-work/2.4 -q          # сначала красное
python course-work/2.4/structured_output.py  # затем демонстрация двух решений gate

Готово, когда зелёны 11 тестов. Они проверяют настоящую закрытую JSON Schema, refusal и incomplete до парсинга, fenced JSON, пропуски и лишние поля, null, доказательство вне источника, обязательный meaning review, отклонение семантически ложного объекта и запрет обходить проваленный gate.

После зелёного прогона объясни своими словами три утверждения:

  1. почему fenced JSON в этом упражнении считается ошибкой, хотя его можно было бы очистить строковым кодом;
  2. почему validate_structure(...) == [] не разрешает продолжение;
  3. почему finish_semantic_review нельзя применять к incomplete-ответу.

Если ответы непонятны, одних зелёных тестов недостаточно. Эталонное решение и тесты-ТЗ доступны ниже в «Исходниках урока».

USE IT: перенеси контракт в один доступный API

Не нужно вызывать всех провайдеров. Выбери один доступный API и сохрани точный model ID, SDK и дату прогона. Названия полей меняются, но разделение ответственности остаётся.

Минимальная форма запроса выглядит так; конкретный model ID выбери в актуальном каталоге своего провайдера:

# OpenAI Responses
response = OpenAI().responses.create(
    model=MODEL_ID,
    instructions=SYSTEM_INSTRUCTION,
    input=SOURCE_NOTES,
    text={"format": {
        "type": "json_schema",
        "name": "meeting_facts",
        "strict": True,
        "schema": OUTPUT_SCHEMA,
    }},
)
# Anthropic Messages
response = Anthropic().messages.create(
    model=MODEL_ID,
    max_tokens=2048,
    system=SYSTEM_INSTRUCTION,
    messages=[{"role": "user", "content": SOURCE_NOTES}],
    output_config={"format": {
        "type": "json_schema",
        "schema": OUTPUT_SCHEMA,
    }},
)
# Google Interactions API
response = genai.Client().interactions.create(
    model=MODEL_ID,
    system_instruction=SYSTEM_INSTRUCTION,
    input=SOURCE_NOTES,
    response_format={
        "type": "text",
        "mime_type": "application/json",
        "schema": OUTPUT_SCHEMA,
    },
)

Эти фрагменты показывают размещение трёх частей контракта, а не универсальный адаптер ответа. Для своего провайдера:

  1. сначала обработай отказ, incomplete и API error по его документации;
  2. только затем получи структурированное содержимое;
  3. нормализуй его в учебный конверт либо передай typed object в предметные проверки;
  4. проверь evidence и смысл;
  5. сохрани status, model ID, решение gate и причину.

Если API использует Pydantic, Zod или другой typed parser, применяй его вместо самописной повторной реализации JSON Schema. Собственный код должен добавлять предметные и смысловые ограничения, а не конкурировать со стандартом.

Самостоятельная практика и перенос

После готового Build It измени один аспект сценария, чтобы не копировать демонстрацию.

Вариант A: продолжить цепочку 2.3

Добавь в корректный объект все решения, действия, условия, открытые вопросы и метрики из заметок. Затем подготовь четыре мутации:

  1. удали обязательное поле;
  2. добавь неизвестное поле;
  3. замени evidence фразой, отсутствующей в источнике;
  4. оставь evidence настоящим, но искази смысл statement.

До запуска назови первый gate, который должен остановить каждую мутацию. Затем проверь прогноз кодом и вручную.

Вариант B: перенести в свою безопасную задачу

Выбери повторяемое извлечение или классификацию, где ответ действительно пойдёт в код. Не используй чувствительные данные в неутверждённом сервисе.

Спроектируй:

  • постоянную инструкцию без меняющихся данных;
  • небольшой реальный JSON Schema;
  • политику отсутствующих значений;
  • status, structure, source и meaning gates;
  • действие для stop, review и continue;
  • один schema-invalid и один schema-valid-but-wrong пример.

Если результат нужен только человеку как текст, structured output может быть лишним. Сильное решение начинается с вопроса о потребителе, а не с желания везде использовать JSON.

Типичные ошибки

  • Дублировать схему криком в системной инструкции. Инструкция объясняет задачу и смысловые границы; форма передаётся в schema-параметре.
  • Путать structured output с function calling. Формат ответа и просьба выполнить действие решают разные задачи.
  • Парсить до проверки статуса. Refusal или обрезанный ответ не становится обычным результатом только потому, что код вызвал json.loads.
  • Называть несколько isinstance реализацией JSON Schema. Предметный валидатор полезен, но не реализует стандарт.
  • Считать schema-valid ответ истинным. Схема не знает, было в источнике 10% или все пользователи.
  • Придумывать defaults для отсутствующих фактов. Используй null, review или остановку, если бизнес явно не утвердил правило по умолчанию.
  • Сразу писать в БД/API. Сначала пройди все применимые gates и сохрани основание решения.
  • Тестировать только счастливый путь. Refusal, incomplete и schema-valid-but-wrong — обязательные случаи этой границы.

Дополнительное чтение

Читать весь список не нужно: сначала пройди вводный материал по JSON Schema, затем выбери документацию того API, с которым работаешь. Последние два источника — необязательная практика и техническое углубление.

  • JSON Schema — Creating your first schema — базовое продолжение урока: прочитай Introduction to JSON Schema, Define properties и Validate JSON data against the schema; обрати внимание на различие между схемой и экземпляром и на то, что properties само по себе не делает поля обязательными.
  • OpenAI — Structured model outputs — если используешь OpenAI, сопоставь со своей карточкой разделы When to use Structured Outputs via function calling vs via text.format, Structured Outputs vs JSON mode и Refusals; отдельно проверь обработку незавершённого ответа.
  • Anthropic — Structured outputs — если используешь Claude, прочитай JSON outputs, JSON Schema limitations и Invalid outputs; используй актуальный параметр output_config.format, а output_format считай переходной формой SDK.
  • Google Gemini — Structured outputs — если используешь Gemini, открой JSON schema support, Structured outputs versus function calling и Best practices; перенеси в свой контракт оговорку о поддерживаемом подмножестве схемы и отдельной проверке значений.
  • Pydantic — JSON Schema — практическое углубление для Python: в разделе Generating JSON Schema посмотри, как получить одну схему из типизированной модели и не дублировать контракт вручную; помни, что успешная валидация модели ещё не доказывает истинность данных.
  • Willard, Louf, 2023 — Efficient Guided Generation for Large Language Models — факультативно о механике constrained decoding: достаточно аннотации и описания метода с регулярными выражениями и контекстно-свободными грамматиками, чтобы понять, почему генератор может гарантировать форму, но не смысл ответа.

Модуль не пытается реализовать JSON Schema. Провайдер и его SDK отвечают за
соответствие поддерживаемой части схемы. Здесь видны проверки, которые всё равно
остаются у приложения: статус ответа, синтаксис на границе, точный контракт
конкретного объекта, наличие доказательств в источнике и осознанное решение о смысле.
"""

from __future__ import annotations

import json
from typing import Any


SOURCE_NOTES = """\
Пилот решили запустить 18 сентября для 10% пользователей iOS.
До запуска служба безопасности должна согласовать схему доступа.
Рита отправит схему доступа на согласование до 12 сентября.

Ответственный за итоговый отчёт пока не назначен.
"""


SYSTEM_INSTRUCTION = """\
Извлекай из заметок только явно сказанные решения, действия, условия,

Форма ответа задаётся отдельно переданной JSON Schema.
"""


# Это настоящая JSON Schema, передаваемая провайдеру. Все поля объекта fact
# обязательны, а отсутствие owner/deadline выражается null, а не выдуманным значением.

    "type": "object",
    "properties": {
        "facts": {
            "type": "array",
            "items": {
                "type": "object",
                "properties": {
                    "category": {
                        "type": "string",
                        "enum": [
                            "decision",
                            "action",
                            "condition",
                            "open_question",
                            "metric",

                    "evidence": {"type": "string"},

                    },

                        "anyOf": [{"type": "string"}, {"type": "null"}]
                    },
                },

                    "category",
                    "statement",
                    "evidence",
                    "owner",
                    "deadline",
                ],
                "additionalProperties": False,
            },
        }
    },
    "required": ["facts"],
    "additionalProperties": False,
}


ALLOWED_CATEGORIES = {
    "decision",
    "action",
    "condition",
    "open_question",
    "metric",
}
FACT_FIELDS = {"category", "statement", "evidence", "owner", "deadline"}


def _result(
    decision: str,
    stage: str,
    errors: list[str],
    data: Any = None,
) -> dict[str, Any]:
    """Собрать единообразный результат gate."""
    return {
        "decision": decision,
        "stage": stage,
        "errors": errors,
        "data": data,
    }


def validate_structure(data: Any) -> list[str]:
    """Проверить точный контракт объекта meeting facts.

    Это намеренно предметная проверка, а не универсальный интерпретатор JSON
    Schema. Возвращает все найденные ошибки; пустой список означает, что форма
    подходит для следующей проверки, но ещё не доказывает истинность значений.
    """
    if not isinstance(data, dict):
        return ["root: expected object"]

    errors: list[str] = []
    root_fields = set(data)
    if root_fields != {"facts"}:
        missing = {"facts"} - root_fields
        extra = root_fields - {"facts"}
        if missing:
            errors.append("root: missing field facts")
        if extra:
            errors.append(f"root: unexpected fields {sorted(extra)}")

    facts = data.get("facts")
    if not isinstance(facts, list):
        errors.append("facts: expected array")
        return errors
    if not facts:
        errors.append("facts: expected at least one item")

    for index, fact in enumerate(facts):
        path = f"facts[{index}]"
        if not isinstance(fact, dict):
            errors.append(f"{path}: expected object")
            continue

        fields = set(fact)
        missing = FACT_FIELDS - fields
        extra = fields - FACT_FIELDS
        if missing:
            errors.append(f"{path}: missing fields {sorted(missing)}")
        if extra:
            errors.append(f"{path}: unexpected fields {sorted(extra)}")

        category = fact.get("category")
        if category not in ALLOWED_CATEGORIES:
            errors.append(f"{path}.category: unsupported value {category!r}")

        for field in ("statement", "evidence"):
            value = fact.get(field)
            if not isinstance(value, str) or not value.strip():
                errors.append(f"{path}.{field}: expected non-empty string")

        for field in ("owner", "deadline"):
            value = fact.get(field)
            if value is not None and (
                not isinstance(value, str) or not value.strip()
            ):
                errors.append(f"{path}.{field}: expected non-empty string or null")

    return errors


def validate_evidence(data: dict[str, Any], source: str) -> list[str]:
    """Проверить, что каждое evidence дословно присутствует в источнике."""
    errors = []
    for index, fact in enumerate(data["facts"]):
        if fact["evidence"] not in source:
            errors.append(f"facts[{index}].evidence: not found in source")
    return errors


def inspect_response(
    response: dict[str, Any],
    source: str,
) -> dict[str, Any]:
    """Провести машинные gates над нормализованным ответом провайдера.

    ``response`` имеет один из видов:

    - ``{"status": "completed", "output_text": "..."}``;
    - ``{"status": "refusal", "reason": "..."}``;
    - ``{"status": "incomplete", "reason": "..."}``.

    Машинно пригодный результат получает decision=review: к следующему рабочему
    шагу его можно допустить только после отдельной смысловой проверки.
    """
    status = response.get("status")
    if status == "refusal":
        reason = response.get("reason") or "no reason provided"
        return _result("stop", "status", [f"provider refusal: {reason}"])
    if status == "incomplete":
        reason = response.get("reason") or "unknown reason"
        return _result("stop", "status", [f"incomplete response: {reason}"])
    if status != "completed":
        return _result("stop", "status", [f"unsupported status: {status!r}"])

    output_text = response.get("output_text")
    if not isinstance(output_text, str):
        return _result("stop", "syntax", ["output_text: expected string"])

    try:
        data = json.loads(output_text)
    except json.JSONDecodeError as error:
        return _result(
            "stop",
            "syntax",
            [f"invalid JSON at line {error.lineno}, column {error.colno}"],
        )

    errors = validate_structure(data)
    if errors:
        return _result("stop", "structure", errors, data)

    errors = validate_evidence(data, source)
    if errors:
        return _result("stop", "source", errors, data)

    return _result("review", "meaning", [], data)


def finish_semantic_review(
    report: dict[str, Any],
    approved: bool,
    reason: str,
) -> dict[str, Any]:
    """Зафиксировать внешнее смысловое решение после машинных gates.

    ``reason`` обязателен и при принятии, и при отклонении: решение должно
    оставаться объяснимым в трейсе.
    """
    if report.get("decision") != "review":
        raise ValueError("semantic review requires decision='review'")
    if not isinstance(reason, str) or not reason.strip():
        raise ValueError("semantic review requires a non-empty reason")

    if approved:
        result = _result("continue", "accepted", [], report["data"])
    else:
        result = _result("stop", "meaning", [reason.strip()], report["data"])
    result["review_reason"] = reason.strip()
    return result


def _json_response(data: dict[str, Any]) -> dict[str, str]:
    """Собрать учебный completed-response для локальной демонстрации."""
    return {
        "status": "completed",
        "output_text": json.dumps(data, ensure_ascii=False),
    }

## 9. Критерии приёмки карточки

Карточка готова, если другой человек без устных пояснений может:

- объяснить, почему выбран structured output, а не проза или function calling;
- собрать один запрос из трёх раздельных частей;
- проверить поддержку использованных keywords JSON Schema;
- обработать refusal и incomplete до парсинга содержимого;

- понять, почему машинный успех заканчивается review, если истина ещё не доказана;
- определить владельца окончательного решения и запрещённый до него следующий шаг.
