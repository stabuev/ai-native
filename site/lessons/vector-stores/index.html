Урок 3.4 · Векторные хранилища

Фаза 3 — Текст и документы · Результат фазы: строить пайплайны резюмирования и редактуры; собрать базовый RAG над своим корпусом.

Результат урока: после урока студент сможет превратить набор трассируемых чанков и их векторов в локальное хранилище, добавить новую запись без пересчёта старых, сохранить состояние, восстановить его после перезапуска и отклонить несовместимый индекс до начала поиска.

Опора: чанки с id, source и позициями из 3.2; retrieval, cosine, top-k, положительный score и no-answer случаи из 3.3. · Дальше: в 3.5 сохранится тот же контракт записей и проверочных запросов, а lexical, dense и hybrid retrieval будут сравниваться через RRF и один eval-набор.

Requires: Python 3 и pytest. Объяснение, Build It и doc-assistant работают офлайн, без API-ключа, сети и клонирования репозитория. Для необязательного переноса на Chroma понадобится пакет chromadb; установка требует доступа к сети, платный ключ не нужен.

Главная мысль. Векторное хранилище не создаёт смысл из текста. Оно отвечает за совместимое состояние: какую запись мы сохранили, каким способом получили её вектор и можно ли безопасно искать по этому индексу после перезапуска.

Ситуация: поиск работает, пока живёт процесс

В 3.3 мы построили TF-IDF retriever над чанками sample_report.md. Один из них выглядел так:

{
  "id": "sample_report.md#chunk-0002",
  "source": "sample_report.md",
  "word_start": 120,
  "word_end": 190,
  "text": "Если согласование не получено к 16 сентября, запуск переносится..."
}

Retriever один раз вычислял представления корпуса и затем переиспользовал их для нескольких вопросов. Но состояние находилось в памяти Python:

процесс запущен → индекс существует → поиск работает
процесс завершён → индекс исчез

На следующем запуске пришлось бы снова читать все документы и пересчитывать весь индекс. Пока корпус учебный, это почти незаметно. В рабочем ассистенте возникают конкретные проблемы:

  • индекс строится дольше одного запроса;
  • новые документы появляются между запусками;
  • найденный вектор без исходного source невозможно проверить;
  • смена способа векторизации может сделать старые и новые векторы несравнимыми.

Нам нужен компонент с состоянием: он принимает новые записи, хранит их вместе с векторами, возвращает исходные метаданные и умеет восстановить совместимое состояние с диска. В этом уроке такой компонент называется векторным хранилищем.

Четыре компонента, которые нельзя смешивать

Прежде чем писать класс, разделим обязанности.

                    │ «как текст стал числами?»   │
                    └─────────────────────────────┘

traceable record ─────────────────────┼──────────────┐

                              └─────────────────────────────┘

1. Запись, или record

Запись — единица, которую можно найти и затем проверить. В нашем случае это чанк:

  • id однозначно отличает его от остальных;
  • text содержит доказательство;
  • source связывает доказательство с документом;
  • word_start и word_end показывают место внутри документа;
  • дополнительные поля могут хранить автора, дату, раздел или права доступа.

Вектор без такой записи отвечает только на вопрос «какие числа оказались близки», но не позволяет показать пользователю источник.

2. Embedding adapter

Embedding adapter, или адаптер векторизации, — функция либо модель, которая превращает текст фиксированным способом в вектор фиксированной длины.

В учебной практике используется готовая функция:

vector = hash_embed(record["text"])

Она раскладывает одинаковые слова по одинаковым координатам. Это лексическое представление: совпали слова — векторы могут быть близки. Оно не понимает, что «автор» и «ответственный» могут обозначать похожую роль.

В отличие от TF-IDF, координаты этого адаптера не зависят от всего корпуса: новое слово всегда попадает в бакет, вычисленный стабильным алгоритмом BLAKE2. Поэтому новый чанк можно векторизовать отдельно, не меняя старые vectors. Частые служебные слова удаляются тем же коротким списком, что и в 3.3.

Цена фиксированного пространства — коллизия: два разных слова иногда попадают в одну координату и создают слабое случайное сходство. Значит, даже положительный score нужно проверять на размеченных запросах. Для учебного урока этот компромисс позволяет наблюдать инкрементальное добавление без сети; production-качество он не обещает.

Название алгоритма и его версия входят в контракт не меньше, чем размерность:

embedding_id = "hash-bow-v1"
dimension    = 512

Если завтра hash-bow-v1 заменить моделью dense-model-v2, старые векторы документов нельзя молча сравнивать с новыми векторами вопросов. Корпус нужно переиндексировать или загрузить совместимый адаптер.

3. Векторный индекс

Векторный индекс организует поиск ближайших векторов. В Build It используется самый прозрачный вариант: сравнить вопрос со всеми сохранёнными векторами по cosine и отсортировать результат.

Это точный перебор: мы действительно рассматриваем каждую запись. Он достаточен для маленького учебного корпуса и позволяет видеть весь механизм. На большом корпусе готовая система может использовать приближённый индекс, чтобы проверять не все кандидаты. Эта оптимизация не меняет требования к ID, provenance и совместимости.

4. Векторное хранилище и retriever

Векторное хранилище соединяет записи, векторы, индекс и сохранённое состояние. Retriever использует его как часть RAG-процесса:

вопрос
→ embedding adapter
→ vector store.query(vector)
→ traceable records
→ evidence package

Поэтому учебный API намеренно разделён:

store.add(record, vector)
store.query(query_vector, k=3, min_score=0.1)

VectorStore не получает сырой текст вопроса и не вызывает hash_embed внутри. Это делает скрытую зависимость явной: документы и вопросы обязан векторизовать один и тот же совместимый адаптер.

Контракт состояния: что должно оставаться истинным

Хранилище считается корректным не потому, что у него есть методы с красивыми названиями. До и после сохранения должны выполняться одни и те же инварианты — условия, которые система не разрешает нарушить.

Уникальный ID

Один ID обозначает одну сохранённую запись. В нашей минимальной реализации, или baseline, действует простая политика:

новый ID       → добавить
существующий ID → ValueError

Это не единственная возможная политика. Production-система может иметь отдельные add, update и upsert. Важна явность: повторная индексация не должна незаметно создать две версии одного чанка.

Одинаковая размерность

Cosine сравнивает координату с соответствующей координатой. Векторы длиной 512 и 768 не являются двумя вариантами одного объекта — у них разные пространства.

Поэтому add и query проверяют:

len(vector) == store.dimension

Молчаливое сравнение только первых координат выглядело бы как работающий поиск, но давало бы бессмысленный результат.

Одна версия векторизации

Одинаковая длина ещё не гарантирует совместимость. Две разные модели могут обе возвращать 512 чисел, но координаты будут означать разное. Поэтому в manifest сохраняются и dimension, и embedding_id.

Сохранённый provenance

Результат query возвращает копию исходной записи с добавленным score:

{
  "id": "sample_report.md#chunk-0002",
  "source": "sample_report.md",
  "word_start": 120,
  "word_end": 190,
  "text": "Если согласование не получено...",
  "score": 0.2993
}

Хранилище не должно превращать запись в пару id + text и терять остальные поля. Именно provenance позволит doc-assistant сослаться на доказательство.

Пустая выдача остаётся допустимым результатом

Как и в 3.3, top-k означает «не больше k», а не «обязательно k». Нулевой вектор и кандидаты с cosine 0 не являются доказательствами:

нет положительного совпадения → []

min_score дополнительно отбрасывает слабые совпадения. Он не является универсальным: порог выбирают по запросам конкретного корпуса, включая размеченные no-answer случаи.

Как хранилище переживает перезапуск

Сохранённое представление называется manifest: это не только данные, но и описание контракта, по которому их можно прочитать.

{
  "schema_version": 1,
  "embedding": {
    "id": "hash-bow-v1",
    "dimension": 512
  },
  "items": [
    {
      "record": {
        "id": "sample_report.md#chunk-0002",
        "source": "sample_report.md",
        "word_start": 120,
        "word_end": 190,
        "text": "..."
      },
      "vector": [0.0, 1.0, 0.0]
    }
  ]
}

В сокращённом примере vector показан из трёх чисел; реальный hash-bow-v1 содержит 512 координат.

Жизненный цикл выглядит так:

1. VectorStore(embedding_id, dimension)
2. add(record, vector)
3. query(query_vector)
4. save("store.json")

   процесс завершился

5. VectorStore.load("store.json", expected embedding_id, expected dimension)
6. проверка manifest и каждой записи
7. query(тот же query_vector)
8. те же ID, scores и provenance

load не должен просто присвоить содержимое JSON полю items. Он повторно проводит данные через те же проверки, что и add. Иначе повреждённый файл обойдёт контракт обычного API.

Если schema_version, embedding_id или dimension не совпали с ожидаемыми, правильный результат — понятная ошибка до поиска. Переиндексация безопаснее правдоподобной, но неверной выдачи.

Предскажи поведение до запуска

В исходниках урока лежат четыре записи из того же sample_report.md, что использовался в 3.3. Не запускай код сразу. Сначала предскажи результат каждого сценария.

На учебном корпусе при min_score=0.1 первый запрос даёт:

После сохранения и загрузки результат совпадает целиком. Запрос про рекламный бюджет возвращает [].

При этом запрос кто автор финального документа тоже возвращает [], хотя нужный фрагмент в корпусе есть: там написано «ответственный за итоговый отчёт». Это не поломка хранилища, а известное ограничение учебного лексического адаптера. Хранилище сохраняет и ищет векторы; оно не улучшает их смысловое качество.

BUILD IT: persistent vector store с проверяемым manifest

Задание: реализуй хранилище трассируемых записей, которое отклоняет несовместимое состояние и доказывает одинаковую выдачу после перезапуска.

Работай в course-work/3.4/. Из «Исходников урока»:

  1. скопируй starter_vector_store.py как course-work/3.4/vector_store.py;
  2. скопируй рядом sample_records.py и test_vector_store.py;
  3. эталонный vector_store.py до первой собственной попытки не открывай.

Используй только стандартную библиотеку Python. hash_embed и cosine уже реализованы в starter: в 3.3 ты строил механизм ранжирования, а здесь работаешь с состоянием.

1. VectorStore.__init__(embedding_id, dimension)

Конструктор должен:

  • требовать непустой строковый embedding_id;
  • требовать положительную целую dimension, причём True не считается числом;
  • создать пустой список items;
  • создать множество уже использованных ID.

2. add(record, vector)

Метод должен:

  • требовать mapping (например, dict) с непустыми строками id, source, text;
  • сохранить все дополнительные JSON-совместимые поля: строки, числа, true/false, null, списки и объекты;
  • если указана одна граница чанка, требовать и вторую;
  • требовать целые позиции 0 <= word_start <= word_end;
  • отклонять повторный ID;
  • требовать ровно dimension конечных чисел: без NaN («не число») и бесконечности;
  • не изменять переданный словарь;
  • сохранить нормализованные record и vector.

Baseline поддерживает только добавление новых ID. Обновление и удаление сознательно остаются за границей урока.

3. query(vector, k=3, min_score=0.0)

Метод должен:

  • проверять размерность и числовые значения query vector;
  • требовать положительный целый k;
  • требовать min_score в диапазоне [0, 1];
  • вернуть [] для нулевого вектора;
  • точно сравнить запрос со всеми сохранёнными векторами;
  • при равных scores сохранить порядок добавления записей;
  • отбросить score 0 и всё ниже min_score;
  • вернуть не больше k копий исходных records с округлённым score.

С порогом сравнивай полный score, округляй только значение в выдаче.

4. to_manifest() и save(path)

Manifest должен содержать:

  • schema_version = 1;
  • embedding.id;
  • embedding.dimension;
  • список items с records и vectors.

save записывает этот объект как читаемый UTF-8 JSON. Атомарная замена файла, конкурентная запись и резервные копии относятся к production-эксплуатации и в Build It не входят.

5. VectorStore.load(path, embedding_id, dimension)

Метод класса должен:

  • прочитать JSON;
  • проверить, что корень manifest — объект;
  • принять только поддерживаемый schema_version;
  • сравнить сохранённые и ожидаемые embedding_id и dimension;
  • потребовать список items;
  • восстановить каждую запись через обычный add, а не в обход проверок;
  • отклонить дубликат, повреждённую запись и вектор неверной длины.

Готово, когда 25 тестов зелёные, демонстрация печатает один и тот же результат до и после восстановления, а ты можешь объяснить, почему несовпадение embedding_id обнаруживается даже при одинаковой размерности.

cd course-work/3.4
pytest -q
python vector_store.py

Тесты проверяют основной сценарий и реалистичные поломки: provenance, мутацию входа, дубликаты, позиции чанков, размерность, NaN, нулевой запрос, слабый score, некорректные параметры, стабильную ничью, manifest, неизвестную схему, несовместимый embedding и инкрементальное добавление после load.

Подсказка. Храни ID в отдельном set, а при загрузке создавай пустой store и вызывай add для каждого элемента manifest. Так один контракт защищает и обычную запись, и восстановление с диска.

Внизу, в «Исходниках урока», сайт покажет starter, учебные records, тесты-ТЗ, свёрнутое эталонное решение и готовый doc-assistant. На любом из трёх путей — самостоятельном, с подсказкой или с делегированием ИИ — критерии приёмки остаются одинаковыми.

USE IT: перенеси контракт в Chroma

Учебный VectorStore полезен для понимания состояния, но не должен изображать все готовые системы одинаковыми. Для переноса возьмём одну конкретную — Chroma.

Соответствие полей:

Учебный storeChroma
record["id"]ids
record["text"]documents
source, позиции и другие поляmetadatas
document vectorembeddings
query vectorquery_embeddings
kn_results
локальный JSONкаталог PersistentClient

Чтобы видеть границу компонентов, передадим уже вычисленные vectors и не позволим Chroma выбирать скрытую embedding function:

import chromadb

from vector_store import hash_embed

client = chromadb.PersistentClient(path="./chroma-db")
collection = client.get_or_create_collection(
    name="pilot-report",
    embedding_function=None,
)

collection.add(
    ids=[record["id"] for record in records],
    documents=[record["text"] for record in records],
    metadatas=[
        {
            "source": record["source"],
            "word_start": record["word_start"],
            "word_end": record["word_end"],
        }
        for record in records
    ],
    embeddings=[hash_embed(record["text"]) for record in records],
)

query = "что произойдёт без согласования безопасности?"
result = collection.query(
    query_embeddings=[hash_embed(query)],
    n_results=3,
    include=["documents", "metadatas", "distances"],
)

Синтаксис похож, но контракты не идентичны:

  • Chroma требует уникальные строковые IDs, но повторный add существующего ID игнорирует; наш baseline намеренно выдаёт ошибку;
  • Chroma проверяет размерность векторов коллекции;
  • Chroma возвращает distance, а учебный store — cosine similarity: направление и шкалу нельзя считать одинаковыми без проверки конфигурации;
  • PersistentClient сам сохраняет состояние в указанном каталоге;
  • если не передать vectors и embedding function, Chroma может использовать локальную модель по умолчанию и скачать её файлы.

В реальном проекте замени hash_embed на выбранную dense embedding model, дай версии стабильный embedding_id и переиндексируй весь корпус. Затем повтори eval из 3.3: проверь ожидаемые ID, no-answer запросы и сохранённый provenance. Сам факт переезда в готовую базу не доказывает улучшение retrieval.

FAISS и pgvector решают соседние, но не идентичные задачи. FAISS — библиотека индексов над матрицами векторов; связь с текстом и metadata нужно организовать отдельно. pgvector — расширение PostgreSQL, где векторы хранятся в таблицах и ищутся SQL-запросом. Они остаются в дополнительном чтении, а не превращаются в три параллельных API внутри основной практики.

  "какой рекламный бюджет?" \
  --k 3 --min-score 0.1

Первый запрос должен вернуть evidence_found, ID pilot.md#chunk-0001, источник, позиции и prompt с требованием цитат. Второй — insufficient_context и prompt=null. Команда ask запускается отдельным процессом, поэтому успешный результат одновременно проверяет сохранение и загрузку.

Свой корпус подготовь тем же способом, что в 3.2: один JSON-объект на чанк, стабильный ID, источник и позиции. Для новых ID используй:

python assistant.py add new_records.json store.json

Типичные ошибки и способ их распознать

  • Векторизовать документы одной моделью, а вопрос другой. Одинаковая размерность не спасает; проверяй embedding_id, а при смене модели переиндексируй корпус.
  • Сохранять только vectors. Поиск вернёт близкие числа без текста и источника; проверяй наличие provenance в результате после load.
  • Молча добавлять повторный ID. Повторный прогон создаёт дубликаты или неявно заменяет данные; зафиксируй отдельную политику add/update/upsert.
  • Доверять JSON только потому, что он читается. Валидный JSON может содержать неизвестную схему, дубликаты и векторы неправильной длины; восстанавливай через обычные проверки.
  • Всегда возвращать ровно k записей. Нулевые кандидаты не становятся доказательствами от попадания в top-k.
  • Считать score вероятностью ответа. Он измеряет близость в выбранном представлении; найденный фрагмент всё равно может не содержать нужного факта.
  • Ожидать от vector store улучшения смысла. Хранилище сохраняет и ищет переданные vectors. Качество зависит от vectorizer, корпуса, chunking и eval.
  • Считать FAISS, Chroma и pgvector одним API. При переносе явно сопоставляй записи, vectors, metadata, persistence и политику обновления.

def hash_embed(text: str) -> list[float]:
    """Return a deterministic lexical hashing vector."""
    if not isinstance(text, str):
        raise TypeError("text must be a string")

    vector = [0.0] * HASH_DIMENSION
    tokens = re.findall(r"\w+", text.lower())
    for token in tokens:
        if token in STOP_WORDS:
            continue
        digest = hashlib.blake2s(token.encode("utf-8"), digest_size=4).digest()
        bucket = int.from_bytes(digest, byteorder="big") % HASH_DIMENSION
        vector[bucket] += 1.0
    return vector


def cosine(a: Sequence[float], b: Sequence[float]) -> float:
    """Return cosine similarity for two dense vectors of equal length."""
    if len(a) != len(b):
        raise ValueError("vectors must have equal dimensions")
    dot = sum(x * y for x, y in zip(a, b))
    norm_a = math.sqrt(sum(x * x for x in a))
    norm_b = math.sqrt(sum(y * y for y in b))
    return dot / (norm_a * norm_b) if norm_a and norm_b else 0.0

class VectorStore:
    """Store traceable records and compatible vectors with exact search."""

    def __init__(self, *, embedding_id: str, dimension: int):
        if not isinstance(embedding_id, str) or not embedding_id.strip():
            raise ValueError("embedding_id must be a non-empty string")
        _validate_dimension(dimension)

        self.embedding_id = embedding_id
        self.dimension = dimension
        self.items: list[dict[str, Any]] = []
        self._ids: set[str] = set()

    def __len__(self) -> int:
        return len(self.items)

    def add(self, record: Mapping[str, Any], vector: Sequence[float]) -> None:
        """Add one new record; reject duplicate IDs and incompatible vectors."""
        normalized_record = _normalize_record(record)
        record_id = normalized_record["id"]
        if record_id in self._ids:
            raise ValueError(f"duplicate record id: {record_id}")

        normalized_vector = _normalize_vector(vector, self.dimension)
        self.items.append(
            {"record": normalized_record, "vector": normalized_vector}
        )
        self._ids.add(record_id)

    def query(
        self,
        vector: Sequence[float],
        *,
        k: int = 3,
        min_score: float = 0.0,
    ) -> list[dict[str, Any]]:
        """Return at most ``k`` positive matches with their provenance."""
        _validate_query_params(k, min_score)
        query_vector = _normalize_vector(vector, self.dimension)
        if not any(query_vector):
            return []

        scored = [
            (cosine(query_vector, item["vector"]), position)
            for position, item in enumerate(self.items)
        ]
        scored.sort(key=lambda pair: (-pair[0], pair[1]))

        hits = []
        for score, position in scored:
            if score <= 0 or score < min_score:
                continue
            hit = dict(self.items[position]["record"])
            hit["score"] = round(score, 4)
            hits.append(hit)
            if len(hits) == k:
                break
        return hits

    def to_manifest(self) -> dict[str, Any]:
        """Return the JSON-compatible state persisted by ``save``."""
        return {
            "schema_version": SCHEMA_VERSION,
            "embedding": {
                "id": self.embedding_id,
                "dimension": self.dimension,
            },
            "items": [
                {
                    "record": dict(item["record"]),
                    "vector": list(item["vector"]),
                }
                for item in self.items
            ],
        }

    def save(self, path: str | Path) -> None:
        """Persist records, vectors and their compatibility contract as JSON."""
        target = Path(path)
        with target.open("w", encoding="utf-8") as file:
            json.dump(
                self.to_manifest(),
                file,
                ensure_ascii=False,
                indent=2,
                allow_nan=False,
            )

    @classmethod
    def load(
        cls,
        path: str | Path,
        *,
        embedding_id: str,
        dimension: int,
    ) -> "VectorStore":
        """Load state only when schema and embedding contracts are compatible."""
        target = Path(path)
        with target.open(encoding="utf-8") as file:
            manifest = json.load(file)

        if not isinstance(manifest, Mapping):
            raise ValueError("store manifest must be an object")
        if manifest.get("schema_version") != SCHEMA_VERSION:
            raise ValueError(
                f"unsupported schema_version: {manifest.get('schema_version')!r}"
            )

        embedding = manifest.get("embedding")
        if not isinstance(embedding, Mapping):
            raise ValueError("store manifest needs embedding metadata")
        if embedding.get("id") != embedding_id:
            raise ValueError(
                "embedding id mismatch: "
                f"stored={embedding.get('id')!r}, expected={embedding_id!r}"
            )
        if embedding.get("dimension") != dimension:
            raise ValueError(
                "embedding dimension mismatch: "
                f"stored={embedding.get('dimension')!r}, expected={dimension!r}"
            )

        items = manifest.get("items")
        if not isinstance(items, list):
            raise ValueError("store manifest needs an items list")

        store = cls(embedding_id=embedding_id, dimension=dimension)
        for position, item in enumerate(items):
            if not isinstance(item, Mapping):
                raise ValueError(f"item at position {position} must be an object")
            if "record" not in item or "vector" not in item:
                raise ValueError(
                    f"item at position {position} needs record and vector"
                )
            store.add(item["record"], item["vector"])
        return store

# doc-assistant

Используй этот скилл, когда ответ должен опираться на предоставленный пользователем
корпус, а не на общие знания модели.

## Что делает скилл

```text
traceable records
→ одинаковая векторизация документов и запроса
→ persistent vector store
→ evidence с id/source/позициями
→ grounded prompt или честный отказ
```

Учебный адаптер `hash_embed` работает офлайн и видит совпадения слов, а не смысл.
Перефразировка может не найти существующее доказательство; положительный score тоже не
гарантирует, что фрагмент отвечает на вопрос.

## Подготовка корпуса

На входе нужен JSON-массив чанков. Каждая запись обязана содержать:

```json
{
  "id": "report.md#chunk-0001",
  "source": "report.md",
  "word_start": 70,
  "word_end": 140,
  "text": "Текст чанка..."
}
```

`id` должен быть уникальным и стабильным. Дополнительные JSON-поля сохраняются.

Создай новый индекс:

```bash
python assistant.py index sample_records.json store.json
```

Добавь новые записи без повторной векторизации уже сохранённых:

```bash
python assistant.py add new_records.json store.json
```

Повторный ID отклоняется. Обновление и удаление в baseline не реализованы: если
содержание существующего чанка изменилось, собери новый индекс или дай ему новый
версионный ID.

## Вопрос к корпусу

```bash
python assistant.py ask store.json \
  "что произойдёт без согласования безопасности?" \
  --k 3 --min-score 0.1
```

Команда возвращает JSON:

- `status=evidence_found` — есть найденные записи и готовый `prompt`;
- `status=insufficient_context` — доказательств нет, `prompt=null`;
- `evidence` всегда сохраняет ID, источник, позиции и score.

`min-score` нельзя переносить между корпусами как универсальную константу. Подбери его
на размеченных запросах, включая случаи, где правильный результат — пустая выдача.

## Как формировать ответ

1. Если `status=insufficient_context`, не вызывай генерацию и ответь:
   «Недостаточно контекста для ответа».
2. Если evidence есть, отвечай только по его тексту.
3. После каждого проверяемого утверждения указывай ID соответствующего чанка.
4. Не считай высокий score доказательством самого факта.
5. Если найденные фрагменты тематически близки, но не содержат ответа, всё равно
   воздержись.

## Проверка

После индексации проверь минимум три сценария:

1. ответимый запрос возвращает ожидаемый ID;
2. запрос вне корпуса возвращает `insufficient_context`;
3. после нового запуска `ask` возвращает те же ID и provenance.

    """Return a deterministic lexical hashing vector."""

            if score <= 0 or score < min_score:
                continue
            hit = dict(self.items[position]["record"])
            hit["score"] = round(score, 4)
            hits.append(hit)
            if len(hits) == k:
                break
        return hits

    def to_manifest(self) -> dict[str, Any]:
        return {
            "schema_version": SCHEMA_VERSION,
            "embedding": {
                "id": self.embedding_id,
                "dimension": self.dimension,
            },
            "items": [
                {
                    "record": dict(item["record"]),
                    "vector": list(item["vector"]),
                }
                for item in self.items
            ],
        }

    def save(self, path: str | Path) -> None:
        with Path(path).open("w", encoding="utf-8") as file:
            json.dump(
                self.to_manifest(),
                file,
                ensure_ascii=False,
                indent=2,
                allow_nan=False,
            )

    @classmethod
    def load(
        cls,
        path: str | Path,
        *,
        embedding_id: str,
        dimension: int,
    ) -> "VectorStore":
        with Path(path).open(encoding="utf-8") as file:
            manifest = json.load(file)

        if not isinstance(manifest, Mapping):
            raise ValueError("store manifest must be an object")
        if manifest.get("schema_version") != SCHEMA_VERSION:
            raise ValueError(
                f"unsupported schema_version: {manifest.get('schema_version')!r}"
            )

        embedding = manifest.get("embedding")
        if not isinstance(embedding, Mapping):
            raise ValueError("store manifest needs embedding metadata")
        if embedding.get("id") != embedding_id:
            raise ValueError(
                "embedding id mismatch: "
                f"stored={embedding.get('id')!r}, expected={embedding_id!r}"
            )
        if embedding.get("dimension") != dimension:
            raise ValueError(
                "embedding dimension mismatch: "
                f"stored={embedding.get('dimension')!r}, expected={dimension!r}"
            )

        items = manifest.get("items")
        if not isinstance(items, list):
            raise ValueError("store manifest needs an items list")

        store = cls(embedding_id=embedding_id, dimension=dimension)
        for position, item in enumerate(items):
            if not isinstance(item, Mapping):
                raise ValueError(f"item at position {position} must be an object")
            if "record" not in item or "vector" not in item:
                raise ValueError(
                    f"item at position {position} needs record and vector"
                )
            store.add(item["record"], item["vector"])
        return store
