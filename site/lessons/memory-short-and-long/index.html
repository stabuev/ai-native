Урок 4.2 · Память: короткая и длинная

Фаза 4 — Скиллы, память и проекты · Результат фазы: упаковывать способности в SKILL.md, хранить контекст в памяти и собирать рабочие проекты.

Результат урока: после урока студент сможет различить контекст текущего запроса, историю чата и долговременную память; решить, какие сведения стоит сохранять; собрать файловое хранилище с источниками, версиями, сроком жизни, поиском и удалением; проверить, что исправленный факт заменяет старый, лишнее не попадает в контекст, а память одного владельца не смешивается с памятью другого.

Опоры: в 1.2 ты увидел контекстное окно и его ограничения; в 3.4–3.5 извлекал релевантные фрагменты из внешнего корпуса и проверял retrieval; в 4.1 отделил skill «как действовать» от изменяющегося состояния «что уже известно и решено». · Дальше: в 4.3 отличишь память от постоянной инструкции и доверенной базы знаний проекта, а в 4.4 решишь, сколько найденной памяти помещать в ограниченный контекст.

Requires: Python 3 и pytest для исполняемой практики. API-ключ, платный сервис, сеть и клонирование курса не нужны.

Главная мысль. Память агента — не склад всей переписки и не магическое свойство модели. Это управляемый цикл: решить, что сохранить, записать с границами и источником, найти нужное, проверить актуальность, добавить в контекст, а затем исправить или забыть.

От умения к состоянию

В 4.1 ты создал skill — переиспользуемый ответ на вопрос «как выполнять процесс?». Например: как проверить документ, как собрать отчёт или как провести ревью.

Но в повторяемой работе одного skill недостаточно. Между запусками меняется состояние:

  • пользователь выбрал новый формат отчёта;
  • команда утвердила бюджет;
  • задача перешла на следующий этап;
  • старый дедлайн отменили;
  • найденная ошибка больше не должна повторяться.

Это уже не способ действия, а ответ на вопрос «что сейчас известно и действительно?». Его и хранит память.

Сравни четыре механизма:

Что нужно сохранитьКуда относитсяПример
Способ выполнять повторяемую задачуSkill«При аудите сначала проверь outcome, потом практику»
Постоянная роль и доверенные документыПроект«Ты ассистент поддержки; вот действующий регламент возврата»
Изменяющийся факт, решение или состояниеПамять«Клиент теперь просит отвечать по-английски»
Детали одной беседыИстория текущего чата«В третьем сообщении мы сравнивали два черновика»

Если положить изменяющееся предпочтение в skill, переносимый процесс станет зависеть от одного пользователя. Если складывать регламент компании в память, агент сможет случайно заменить доверенный документ собственной догадкой. Граница между механизмами важнее их названий.

Проблема: «помнить» недостаточно

Представь ассистента, который готовит еженедельный отчёт.

В понедельник пользователь сказал:

Присылай отчёт таблицей.

В среду он уточнил:

Таблица неудобна. Теперь нужен короткий список.

В пятницу ассистент должен подготовить новый отчёт. Если просто сохранить обе фразы, в памяти появится противоречие. Если подать модели всю переписку, она потратит контекст и всё равно может выбрать старое указание. Если всегда брать самую свежую запись, случайная новая догадка сможет победить проверенный факт.

Правильная память должна ответить минимум на пять вопросов:

  1. Стоило ли вообще сохранять эту информацию?
  2. К какому пользователю или проекту она относится?
  3. Откуда она взялась?
  4. Действует ли она сейчас или уже заменена либо просрочена?
  5. Нужна ли она для текущего запроса?

Поэтому память — это не только save() и search(). Хранение без политики записи, версий и удаления создаёт устойчивые ошибки.

Три слоя, которые легко перепутать

1. Контекст текущего запроса

Модель генерирует ответ из токенов, переданных в текущем вызове: system prompt, сообщений, результатов инструментов, документов и найденных записей памяти. Этот набор называют контекстом. Его часто сравнивают с рабочей памятью, но важно понимать границу аналогии: контекст не лежит внутри модели после завершения вызова.

Если следующий вызов должен «помнить» предыдущую реплику, приложение снова передаёт её или её краткое содержание.

2. История чата или сессии

Приложение может сохранять сообщения диалога и возвращать их в последующие запросы. Пользователь видит непрерывный разговор, хотя модель каждый раз получает заново собранный контекст.

История полезна для локальной связности, но это сырой журнал:

  • в ней много повторов и промежуточных рассуждений;
  • старые и новые решения могут противоречить друг другу;
  • она может быть длиннее доступного окна;
  • не каждую реплику разрешено или полезно переносить в будущие задачи.

3. Долговременная память

Долговременная память хранится вне текущего запроса: в файлах, базе данных или сервисе платформы. Это не обязательно полный чат. Сильная память содержит отобранные записи, которые можно посмотреть, исправить, ограничить по сроку и удалить.

история взаимодействия
        │
        ▼
кандидат на память
        │  политика записи: полезно? подтверждено? безопасно? чья это память?
        ▼
долговременное хранилище
        │  действует? не просрочено? относится к запросу?
        ▼
несколько выбранных записей
        │
        ▼
контекст текущего запроса

Контекст, история и долговременная память связаны, но не взаимозаменяемы.

Что запоминать, а что не запоминать

Для учебного модуля используем консервативную политику.

Обычно стоит сохранять:

  • явно подтверждённые устойчивые предпочтения;
  • принятые решения и текущее состояние задачи;
  • результат, который понадобится в следующей сессии;
  • исправление ошибки, если без него агент повторит неверное действие;
  • временный факт с явным сроком действия.

Обычно не стоит сохранять автоматически:

  • пароли, API-ключи, токены и другие секреты;
  • всю стенограмму «на всякий случай»;
  • неподтверждённую догадку модели о человеке;
  • одноразовую деталь, нужную только в текущем запросе;
  • доверенный регламент, который должен жить в доступной только для чтения

(read-only) базе знаний проекта;

  • инструкцию «как действовать», если ей место в skill.

Это не универсальная политика для любой организации. В реальном продукте правила зависят от назначения, прав пользователя, требований к данным и срока хранения. Но решение до записи обязательно: поиск не исправит факт, который вообще не следовало сохранять.

Минимальная модель записи

Каждая запись нашего MemoryStore имеет поля:

ПолеЗачем нужно
idСтабильно отличить одну версию от другой
keyСвязать версии одного изменяющегося факта, например report.format
textСамо сохранённое содержание
sourceПонять, откуда взялся факт: сообщение пользователя, календарь, решение встречи
created_atПосчитать возраст и восстановить последовательность
expires_atНе возвращать временную запись после окончания срока
activeИсключить заменённую версию из поиска
superseded_atУвидеть, когда старая версия перестала действовать

Владелец owner хранится на уровне всего хранилища. Так файл памяти одного пользователя или проекта нельзя незаметно загрузить как память другого.

Почему нужен стабильный key

Свежесть не разрешает противоречие надёжно. Запись «формат отчёта — короткий список» может быть новее записи «формат отчёта — таблица», но новизна сама по себе не доказывает, что произошло исправление. Возможно, речь шла о разных отчётах.

Стабильный ключ выражает предметное решение:

report.weekly.format = "таблица"          active=False
report.weekly.format = "короткий список"  active=True

Новая версия того же ключа явно заменяет прежнюю. Если факты независимы, у них разные ключи:

report.weekly.format
report.monthly.format

Так версионность решает конфликт, а не перекладывает его на формулу ранжирования.

Как выбираются записи

Перед ранжированием recall(query) применяет три фильтра:

  1. запись принадлежит загруженному хранилищу нужного владельца;
  2. запись активна и ещё не просрочена;
  3. текст имеет хотя бы одно совпадающее с запросом слово.

Только после этого активные кандидаты получают score:

score = overlap + recency

overlap = число разных общих слов запроса и записи
recency = 0.5 ** (age_days / half_life_days)

half_life_days — период полураспада свежести в днях. При возрасте 0 дней recency = 1; при возрасте 30 дней и half_life_days = 30 получаем 0.5; при возрасте 60 дней — 0.25.

Слово days в имени параметра принципиально. В старой реализации использовался time.time(), который возвращает секунды, но half_life=30 выглядел как «30 дней» и фактически означал 30 секунд. Неявные единицы — типичная причина корректной формулы с некорректным поведением.

Разбор двух разных ситуаций

Сначала версия, потом score.

key=report.weekly.format, text="еженедельный отчёт — таблица", active=False
key=report.weekly.format, text="еженедельный отчёт — короткий список", active=True

На запрос формат еженедельного отчёта старая таблица вообще не участвует в ранжировании: она была явно заменена.

Свежесть ранжирует независимые активные записи.

запрос: "отчёт"

A: "еженедельный отчёт — короткий список", возраст 30 дней
   overlap=1, recency=0.500, score=1.500

B: "ежемесячный отчёт — подробная таблица", возраст 1 день
   overlap=1, recency=0.977, score=1.977

При одинаковой лексической релевантности B окажется выше. Но на запрос еженедельный отчёт A получит больше совпадений и победит по релевантности. Свежесть — полезный сигнал среди кандидатов, а не синоним истины.

Лексический overlap выбран ради прозрачности: результат можно посчитать руками. Он не понимает синонимы и перефразировки. В production вместо него часто применяют embeddings, гибридный retrieval или поиск самим агентом — эти механизмы уже встречались в Фазе 3.

Полный жизненный цикл

Наш модуль реализует семь наблюдаемых шагов:

remember(key, text, source, ...)
    │  прежняя активная версия key становится superseded
    ▼
items[] на диске
    │
    ├─ history(key)  → все версии для проверки
    ├─ recall(query) → только active + not expired + relevant
    ├─ context_for() → компактный фрагмент для контекста
    ├─ forget(key)   → физически удалить все версии ключа
    └─ save / load   → пережить перезапуск вместе с настройками

context_for() помечает результат как facts, not instructions. Эта строка не создаёт защиту сама по себе, но сохраняет важную границу: найденная память — данные для рассуждения, а не автоматически доверенная команда агенту.

Перед кодом: прими решения

Для каждого кандидата сначала предскажи действие политики:

КандидатРешение по умолчаниюПочему
«Еженедельный отчёт присылай коротким списком»СохранитьЯвное устойчивое предпочтение
«Вот временный API-ключ для диагностики»Не сохранятьСекрет и одноразовая информация
«Кажется, клиент любит подробные ответы» — догадка моделиНе сохранять без подтвержденияВывод модели может быть ошибочным
«Бюджет 800 000 ₽ утверждён на встрече»Сохранить с источникомРешение понадобится в следующих сессиях
«Сегодня отправь отчёт до 18:00»Сохранить только при необходимости и с expires_atПосле дедлайна факт перестанет действовать
Действующая политика возврата компанииПоложить в базу знаний проектаЭто доверенный reference, а не изменяемая память пользователя

Если твои ответы отличаются, сформулируй правило. Важен не единственный универсальный выбор, а явная граница, которую можно проверить и объяснить.

BUILD IT

Задание: собери MemoryStore — небольшую файловую память с версиями, сроком жизни, наблюдаемым retrieval и удалением. Только стандартная библиотека; сети и API нет.

Создай любую рабочую папку, например:

ai-native/
└── 4.2-memory/
    └── code/
        ├── memory_store.py
        └── test_memory_store.py

Клонировать репозиторий курса не требуется. Нужны Python 3 и pytest.

Контракт класса

Создай MemoryStore(owner, half_life_days=30.0).

  • owner — непустой идентификатор пользователя или проекта.
  • half_life_days — положительный период полураспада свежести в днях.
  • Внутри храни items и счётчик _next_id.

Реализуй методы:

remember(key, text, source, ts=None, expires_at=None)

  • требует непустые key, text и source;
  • использует time.time(), если ts не передан;
  • отклоняет expires_at <= ts;
  • помечает прежнюю активную версию того же key как неактивную и записывает

superseded_at;

  • добавляет новую активную версию с очередным id;
  • возвращает копию созданной записи.

recall(query, k=3, now=None)

  • рассматривает только активные и непросроченные записи;
  • пропускает записи с нулевым пересечением слов;
  • переводит возраст из секунд в дни;
  • считает overlap, recency и score;
  • возвращает не более k копий записей по убыванию score;
  • добавляет к возвращаемым копиям наблюдаемые поля overlap и score, но не сохраняет

их в JSON как часть исходной памяти.

history(key)

  • возвращает все версии ключа, новые первыми;
  • не скрывает заменённые версии: этот метод нужен для диагностики.

forget(key)

  • физически удаляет все версии ключа;
  • возвращает количество удалённых записей.
  • чтобы удалить их и из уже существующего JSON-файла, после forget вызови save.

context_for(query, k=3, now=None)

  • использует recall;
  • формирует компактный текстовый блок;
  • показывает key, source и text;
  • не включает нерелевантные и заменённые записи.

save(path) и MemoryStore.load(path, expected_owner=None)

  • сохраняют не только items, но и schema_version, owner, half_life_days и

_next_id;

  • save сначала пишет временный файл, затем заменяет целевой;
  • load отклоняет неизвестную версию схемы;
  • при переданном expected_owner отклоняет файл другого владельца.

Что должны доказать тесты

Тесты являются спецификацией поведения, а не проверкой факта запуска:

  1. поиск возвращает только релевантную активную запись;
  2. новая версия ключа явно заменяет прежнюю;
  3. просроченная запись не извлекается;
  4. свежий, но нерелевантный факт не попадает в context_for;
  5. forget удаляет все версии ключа;
  6. save → load сохраняет записи, владельца, единицы времени и следующий id;
  7. загрузка памяти другого владельца завершается ошибкой.

Запусти цикл red → green:

pytest code -q
python code/memory_store.py

В демо должны существовать две версии report.format: старая «таблица» и новая «короткий список». На запрос формат отчёта в контекст попадает только новая версия, а свежая запись о поездке в Казань не попадает.

Подсказка. Для токенизации достаточно set(re.findall(r"\w+", text.lower())). Возраст в днях:

age_days = max(0.0, now - created_at) / 86_400

Эталон и тесты находятся в «Исходниках урока». Упражнение можно собрать самостоятельно, подсмотреть решение или делегировать код агенту, но критерии приёмки одинаковы для всех трёх путей.

Что именно доказала практика

После зелёных тестов можно утверждать:

  • записи переживают перезапуск процесса;
  • конфликт одного ключа разрешается явно;
  • просроченное и нерелевантное не попадает в контекст;
  • пользователь может удалить факт;
  • файл памяти нельзя незаметно принять за память другого владельца;
  • причина выбора наблюдаема через source, overlap и score.

Нельзя утверждать:

  • что лексический поиск понимает смысл;
  • что любой кандидат был правильно выбран для записи;
  • что локальный JSON безопасен для чувствительных данных;
  • что модуль выдерживает конкурентную запись нескольких процессов;
  • что он автоматически защищает от внедрённой в сохранённый текст вредоносной

инструкции (prompt injection);

  • что пройденные тесты доказывают качество памяти конкретной платформы.

Так выглядит дисциплина проверки: доказательство ограничено тем контрактом, который действительно наблюдался.

USE IT: как это соотносится с платформами

Платформы реализуют разные продукты, поэтому нельзя говорить, что каждая «под капотом делает ровно наш MemoryStore».

  • ChatGPT Memory может использовать сохранённые сведения и информацию из прошлых

чатов в зависимости от текущих настроек и доступности функции. Пользователь управляет памятью в Personalization, может исправлять и удалять сведения или открыть Temporary Chat. Точный интерфейс меняется, поэтому проверяй актуальный Memory FAQ.

  • Claude Memory tool для API даёт модели файловые операции над каталогом памяти, но

само хранилище исполняет и контролирует приложение разработчика. Это близко к файловому жизненному циклу урока, однако требует отдельной защиты путей, лимитов, чувствительных данных и срока хранения. См. официальный контракт.

  • Gemini Memory может персонализировать ответы на основе прошлых чатов для подходящих

аккаунтов и настроек. При этом функция памяти прошлых чатов не работает внутри Gems: Gem — настроенный ассистент с инструкциями, а не тот же механизм памяти. См. Gemini Apps Help.

При сравнении платформ задавай одни и те же вопросы:

ВопросЧто выяснить
ЗаписьЧто сохраняется автоматически, а что только по явной просьбе?
КонтрольМожно ли посмотреть, исправить, удалить и временно отключить память?
ScopeРазделены ли пользователи, проекты и рабочие пространства?
СрокКогда запись обновляется, забывается или истекает?
RetrievalПочему конкретный факт оказался в ответе?
ДанныеГде хранится память и какие правила доступа к ней действуют?

Названия кнопок и доступность меняются быстрее центральной модели. Поэтому урок учит проверяемому жизненному циклу, а не запоминанию интерфейса одного провайдера.

Артефакт: изолированный модуль памяти с версиями и сроком жизни → outputs/memory_module.py

Модуль можно использовать как прозрачный прототип при проектировании памяти рабочего ассистента. Он показывает необходимые точки решения, но не объявляется готовым production-хранилищем.

В 4.3 ты отделишь изменяемую память от постоянной инструкции и доверенной базы знаний проекта. В 4.4 найденные записи станут одним из кандидатов на место в контексте. В Фазе 7 вернётся общий цикл remember → recall → act, но уже внутри агента с планированием.

Где здесь 4D

4DРешение при работе с памятью
DelegationОпределить, что агент может сохранять автоматически, а где обязан запросить подтверждение человека
DescriptionЗадать схему записи, область действия (scope), источник, срок жизни, правила замены и удаления
DiscernmentПроверить, почему запись извлечена, не заменена ли она, не истёк ли срок и не возник ли конфликт
DiligenceНе хранить секреты без необходимости, разделять владельцев, давать просмотр и забывание, повторять сценарии ошибок

Слабая память проваливается не только из-за плохого поиска. Она может аккуратно найти сведения, которые не следовало записывать, которые относятся к другому человеку или уже были отменены. Поэтому все четыре компонента работают как один цикл.

Частые ошибки

  • Сохранять всю историю. Сырой журнал содержит шум, противоречия и чувствительные

данные. Сначала выбери кандидата и проверь политику записи.

  • Считать свежесть истиной. Недавняя запись может быть ошибочной. Конфликтующие

значения разрешай стабильным ключом и явной заменой.

  • Хранить текст без источника. Без source невозможно понять, сообщил ли факт

пользователь, взяла ли его система из календаря или придумала модель.

  • Смешивать владельцев. Одинаковый запрос не даёт права читать память другого

пользователя или проекта.

  • Не задавать срок жизни. Временный дедлайн без expires_at превращается в

постоянную ложь.

  • Уметь записывать, но не забывать. Исправление и удаление — часть основного

контракта, а не административное дополнение.

  • Принимать overlap за понимание смысла. Точный лексический поиск пропустит синоним и

может поймать случайное общее слово. Это прозрачная базовая модель (baseline), не семантическая память.

  • Давать агенту произвольный путь к файлу. В учебном модуле путь задаёт приложение.

Если путь контролирует модель, нужны отдельные проверки выхода за разрешённый каталог.

  • Считать зелёные тесты доказательством production-готовности. Они подтверждают

только описанные инварианты учебного модуля.

"""Минимальная управляемая память агента для урока 4.2."""

import json
import re
import time
from pathlib import Path


SECONDS_PER_DAY = 86_400
SCHEMA_VERSION = 1


def _words(text):
    return set(re.findall(r"\w+", text.lower()))


class MemoryStore:
    """Версионируемые записи с поиском, сроком жизни и изоляцией владельца."""

    def __init__(self, owner, half_life_days=30.0):
        if not owner:
            raise ValueError("owner must not be empty")
        if half_life_days <= 0:
            raise ValueError("half_life_days must be positive")
        self.owner = owner
        self.half_life_days = float(half_life_days)
        self.items = []
        self._next_id = 0

    def remember(self, key, text, source, ts=None, expires_at=None):
        """Добавить новую активную версию ключа и заменить прежнюю."""
        if not key or not text or not source:
            raise ValueError("key, text and source must not be empty")

        ts = time.time() if ts is None else float(ts)
        if expires_at is not None:
            expires_at = float(expires_at)
            if expires_at <= ts:
                raise ValueError("expires_at must be later than ts")

        for item in self.items:
            if item["key"] == key and item["active"]:
                item["active"] = False
                item["superseded_at"] = ts

        item = {
            "id": self._next_id,
            "key": key,
            "text": text,
            "source": source,
            "created_at": ts,
            "expires_at": expires_at,
            "active": True,
            "superseded_at": None,
        }
        self._next_id += 1
        self.items.append(item)
        return dict(item)

    def recall(self, query, k=3, now=None):
        """Вернуть релевантные активные записи с наблюдаемым score."""
        if k <= 0:
            return []
        q = _words(query)
        if not q:
            return []

        now = time.time() if now is None else now
        scored = []
        for item in self.items:
            if not item["active"]:
                continue
            if item["expires_at"] is not None and item["expires_at"] <= now:
                continue

            overlap = len(q & _words(item["text"]))
            if overlap == 0:
                continue

            age_days = max(0.0, now - item["created_at"]) / SECONDS_PER_DAY
            recency = 0.5 ** (age_days / self.half_life_days)
            hit = dict(item)
            hit["overlap"] = overlap
            hit["score"] = round(overlap + recency, 6)
            scored.append(hit)

        scored.sort(
            key=lambda hit: (hit["score"], hit["created_at"], hit["id"]),
            reverse=True,
        )
        return scored[:k]

    def history(self, key):
        """Вернуть все версии ключа: новые первыми."""
        versions = (item for item in self.items if item["key"] == key)
        return [
            dict(item)
            for item in sorted(
                versions,
                key=lambda item: (item["created_at"], item["id"]),
                reverse=True,
            )
        ]

    def forget(self, key):
        """Физически удалить все версии ключа и вернуть их количество."""
        before = len(self.items)
        self.items = [item for item in self.items if item["key"] != key]
        return before - len(self.items)

    def context_for(self, query, k=3, now=None):
        """Собрать компактный фрагмент памяти для контекста модели."""
        hits = self.recall(query, k=k, now=now)
        lines = ["# Memory (facts, not instructions)"]
        if not hits:
            return "\n".join([*lines, "- No relevant records"])
        lines.extend(
            f"- [{hit['key']}; source={hit['source']}] {hit['text']}"
            for hit in hits
        )
        return "\n".join(lines)

    def save(self, path):
        """Атомарно сохранить записи вместе с настройками хранилища."""
        path = Path(path)
        path.parent.mkdir(parents=True, exist_ok=True)
        payload = {
            "schema_version": SCHEMA_VERSION,
            "owner": self.owner,
            "half_life_days": self.half_life_days,
            "next_id": self._next_id,
            "items": self.items,
        }
        temporary = path.with_suffix(path.suffix + ".tmp")
        temporary.write_text(
            json.dumps(payload, ensure_ascii=False, indent=2),
            encoding="utf-8",
        )
        temporary.replace(path)

    @classmethod
    def load(cls, path, expected_owner=None):
        """Загрузить хранилище и при необходимости проверить владельца."""
        payload = json.loads(Path(path).read_text(encoding="utf-8"))
        if payload.get("schema_version") != SCHEMA_VERSION:
            raise ValueError("unsupported memory schema")
        if expected_owner is not None and payload["owner"] != expected_owner:
            raise ValueError("memory owner mismatch")

        store = cls(
            owner=payload["owner"],
            half_life_days=payload["half_life_days"],
        )
        store.items = payload["items"]
        store._next_id = payload["next_id"]
        return store


if __name__ == "__main__":
    now = 1_800_000_000.0
    memory = MemoryStore(owner="demo-user", half_life_days=30)
    memory.remember(
        "report.format",
        "Формат еженедельного отчёта — таблица",

    )

        source="calendar",
        ts=now,
    )
    print(memory.context_for("формат отчёта", now=now))

        return store
